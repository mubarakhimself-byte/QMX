Material findings in the initial implementation:

1. **Lost final request snapshot permits provider replay after a durable effect.** Runtime invokes the completion callback, which can register and append a receipt, before persisting the final `agent_request.snapshot`. If this final persist fails or the process dies, restart folds the earlier running snapshot to `interrupted/owner_lost`; ordinary `retry_interrupted` clears the result and queues another provider call. The existing reconciliation path requires `failed/authoring_effect_uncertain` plus a retained result and therefore cannot repair that crash window. Fence observed/completed authoring attempts in restore and retry, preserve the bounded actual output as durable execution evidence, and reconcile without replay. A post-callback refusal converted to failed is insufficient when the failure itself was never snapshotted.

2. **Global registration dedupe has a check/use race.** The host checks `experiments.resolve` before calling `register`, but exposed direct registration callers do not hold Task authority. Another caller can register the same fingerprint between these calls; `register` returns that existing registration. The initial completion path then writes a receipt with its own captured authority. Check the returned RegisteredExperiment's exact spec identity, lease, Task attempt and deployment before issuing the receipt, and fail closed on foreign attribution. This is separate from locking Task reassignment.

3. **Admission retains mutable Task inputs by alias.** `_Admission.task` initially stores the same TaskRecord returned by dispatcher and durable caches. Although the dataclass is frozen, `inputs` may be a mutable dict. Changing an admitted data/environment/config/session/profile pin in place changes both the previous and current view; equality then passes and parsing validates the new pin. Capture immutable host-derived authority/input values or a canonical digest at acceptance and compare them at dispatch/completion. Pinning Task ID alone does not close this window.

4. **Lazy projection cache fill bypasses the new mutex.** `TaskGraphStateService.get` writes `_rows` and `_occupancy` after a SQLite read but initially lacks `@serialized`. A delayed cold-cache read can overwrite a newer persisted graph. With a direct durable terminal change, it could restore a stale RUNNING projection that falsely agrees with the dispatcher. Serialize the complete lazy read/cache-fill operation. The other relevant public projection mutations are decorated; `snapshot` itself does not install a cache entry.

5. **Receipt reconciliation initially trusts potentially incomplete registration caches.** `ExperimentSpecService.register` updates `_specs`, leases and registering metadata before durable writes. `resolve` reads those caches. A durable write exception can therefore leave an apparent registration that vanishes after reopen, while initial reconciliation can issue a success receipt from it. Require exact durable spec/ledger/lease/attempt/deployment readback or fail closed until a reopen/reload proves the registration. This finding was sent separately after the first four were acknowledged.

6. **Request context validation is not serialized with session/grant authority changes.** Completion holds request and Task locks, but inspected ProductSessionService has neither shared lock nor a lifecycle fence around public host_grant/regrant/revoke_grant and restore/mint/cache operations. `revoke_grant` changes HostGrantLedger before journaling. A valid concurrent revocation/retarget can occur after `validate_active_request` and before registration. Fence the session and relevant canonical grant-ledger mutation routes through the effect, or enforce a genuinely immutable admitted context. Checking immediately before a write without a shared authority critical section does not prove rejection after retarget/revocation. Reported promptly after checking these actual routes.

Verified strengths and bounded concurrency assessment:

- `RequestSpec.authoring_task_id` is operator-selected, serialized by the existing request journal, included in the existing dataclass hash, and compared by the bridge against current policy. No renderer Agent/lease/deployment/task authority fields or new public wire capability are introduced.
- Host admission requires a RUNNING dispatcher Task, exact Task/mission/owner lease, canonical current Task Ledger lease and attempt, matching durable projection and the process-owned spawn API's Agent/session/permission. Every Agent admitted by the existing store is frozen at spawn; the store intentionally has no automatic restoration of a running Agent.
- Runtime callbacks run under its reentrant lifecycle lock. Authoring admission/completion/reconciliation acquire runtime first, then shared Task authority. Provider execution remains outside these locks. Cancellation validation uses the actual still-running row/token, so a synthetic provider that ignores cancellation still cannot register after cancellation. Context validation detects a change already visible at that check; finding 6 concerns a later concurrent change.
- Dispatcher constructor binds one `TaskGraphStore.authority_lock` into the composed Task Ledger and TaskGraphStateService. Decorators cover store writes, dispatcher transitions, public ledger appends/grants/reassignment/defer paths, and durable projection/outbox/join mutations. Reassignment attempt increments fence A→B→A. Direct hook ledger mutations and nested graph persistence use these same service locks after composition.
- Actual JobHandle commits hold their own store lock before calling decorated projection/dispatcher paths. Inspected dispatcher/authoring operations do not acquire that JobHandle store lock while holding Task authority, so no inverse edge was found in these paths. Task mutations inspected do not call request runtime. This is a source-level order assessment, not a stress/deadlock proof for every plugin or future host callback. Shared lock binding is a startup composition operation; live rebinding of a shared service to another dispatcher is outside the verified contract.
- For the session-lock correction, inspected ProductSessionService mutators/hydration/persistence call ledger, journal and SQLite without Task/runtime callbacks. Both `ProductSessionService.dispatch_public_call` and `HostGrantLedger.dispatch` can invoke an external execute callback that reaches Task/runtime. Neither outer dispatch function may hold Session authority across that callback; lock evaluation/snapshot/mutation and release before execution. The required new composed order is runtime → Task → session/grant → journal/sqlite. Wire grant locking must remain inside its package boundary rather than importing a daemon helper.
- Recipe parsing rejects unknown and duplicate fields, oversize UTF-8, recursive JSON and Unicode encoding faults, then invokes existing ExperimentSpec validation. Provider output supplies identity proposals, never provenance. Data/environment/config references must match Task pins. Deployment is actual trusted-adapter metadata; tests explicitly use `synthetic:offline-authoring-v1`.
- Output observation precedes registration, receipt follows registration, and observed effect uncertainty is marked distinctly. Ordinary retry refuses an already snapshotted failed uncertain request. Explicit host receipt reconciliation neither calls a provider nor mints a missing registration; after correction it must also prove that existing registration durably.
- Existing paired get adds the authoring receipt only when `content_withheld` is not true. Reconciliation is a trusted host method, not a read query or a new renderer capability. Task terminal status is not manufactured from recipe registration.

## 1. Agent loop / turn execution

- **Task kinds** `core/src/state` + `core/src/tasks/mod.rs`: `TaskKind::{Regular, Compact, Review, UserShell}`. Each implements `trait SessionTask` (`core/src/tasks/mod.rs`) with `run(self, sess, ctx, input, cancellation_token)`. `RegularTask` is the normal agent turn (`core/src/tasks/regular.rs`).
- **Submission loop**: `core/src/session/submission.rs` + `handlers.rs::submission_loop` drives ops; a turn runs as a cancellable tokio task stored in `session.active_turn`.
- **`RegularTask::run`** (`tasks/regular.rs`): emits `TurnStarted`, runs turn-start lifecycle contributors (extensions) at phase `RegularTaskStart`, consumes startup prewarm, then loops calling `run_turn(...)`; after each `run_turn` it re-checks `sess.input_queue.has_pending_input` and loops again if the user steered input in (so one "task" can span several model round-trips).
- **`run_turn`** (`core/src/session/turn.rs`, ~line 164, 3209-line file) is the core engine:
  - Pre-sampling auto-compaction (`run_pre_sampling_compact`), then records user input via `run_hooks_and_record_inputs` (`turn.rs:865`, fires `UserPromptSubmit` hooks + persists).
  - Resolves required MCP servers/plugins from `@mentions` (`required_mcp_servers_for_input`, `crate::plugins::collect_explicit_plugin_ids`).
  - Inner `loop {` (turn.rs:425): drains pending/steered input, captures a **step context** (tools + context snapshot for one request), then `run_sampling_request(...)` which opens the model stream and executes tool calls. After sampling it evaluates `needs_follow_up` (model asked to continue OR pending input), token budget, auto-compaction roll-over (`run_auto_compact`, `CompactionReason::ContextLimit`, `CompactionPhase::MidTurn`), and Stop-hook continuation.
- **Model stream** `run_sampling_request` → `ResponseEvent` match (turn.rs ~2600): `Created`, `OutputItemAdded`, `OutputItemDone` (tool/function calls dispatched here), `OutputTextDelta`, `ToolCallInputDelta`, `ReasoningSummaryDelta/…`, `RateLimits`, `Completed`. Streaming client is `core/src/client.rs` / `client_common.rs`; retry/backoff `core/src/responses_retry.rs` (`ResponsesStreamRetryState`, `handle_response_stream_error`). `parallel_tool_calls: true` set in the request (turn.rs:1577).
- **Interruption**: `CancellationToken` (tokio-util) threaded everywhere; `run_turn` makes child tokens per sampling request. Protocol op `turn/interrupt`; `TurnAbortReason`; mid-stream `stream.interrupt` oneshot (turn.rs:2639). `session.is_interrupted()`.
- **Steering / queued input**: `core/src/session/input_queue.rs` (`InputQueue`, `TurnInputQueue`). Two sources: per-turn `pending_input` (user types while model runs) and a session **mailbox** (`mailbox_pending_mails`, multi-agent messages) delivered via `deliver_mailbox_communication_to_current_turn` / `accept_mailbox_delivery_for_current_turn`. Protocol op `turn/steer`. Steered input is recorded with `PersistContext::SteeredUserInput`.
- **Turn suspension** (`core/src/session/turn_suspension.rs`): `suspend_turn_and_shutdown` only for `TaskKind::Regular` and refuses if the thread has live descendant agents (`list_live_agent_subtree_thread_ids > 1`) → `SuspendTurnOutcome::HasLiveDescendants`.
- **Lifecycle hooks for extensions** (`core/src/tasks/lifecycle.rs`): `emit_turn_start_lifecycle` / `on_turn_start`, `on_turn_stop`, `on_turn_abort`, `on_turn_error`, `on_thread_idle` — in-process extension contributors (distinct from user shell hooks in §3).

## 2. Tool registry & routing

- **Per-turn registry build**: `core/src/tools/spec_plan.rs::build_tool_router` → `build_core_tool_registry` assembles a `ToolRegistry` (`core/src/tools/registry.rs`) fresh for each step (tools depend on model, features, sandbox, environment). Registration: `registry.add(Handler)`, `add_with_exposure(h, ToolExposure::…)`, `register_trusted(_with_exposure)`, `register_external(…)` for MCP/third-party.
- **`ToolExposure`**: `Direct`, `DirectModelOnly`, `Deferred`, `Hidden`, plus code-mode availability. "Deferred" tools are not in the model's initial tool list; they are surfaced via **tool search** (see below). Collisions tracked; `error_on_tool_collisions` can fail the turn (`ToolCollision`).
- **Handler trait**: `trait CoreToolRuntime` / `ToolExecutor<ToolInvocation>` (`registry.rs`). `is_builtin_control_tool()` marks control tools. `supports_parallel_tool_calls`.
- **Router**: `core/src/tools/router.rs::ToolRouter` — `ToolRouter::from_registry` (via `finalize_tool_router`), `build_tool_call(ResponseItem)->Option<ToolCall>`, `dispatch_tool_call_with_state(...)`. `ToolCall{ tool_name: ToolName, call_id, payload: ToolPayload, encrypted_function_args }`. `ToolName` has optional `namespace` (MCP server name, multi-agent namespace, etc.); `flat_tool_name` flattens for wire/hook/telemetry.
- **Tool specs crate** `codex-rs/tools/src/`: `tool_definition.rs`, `tool_spec.rs` (`ToolSpec::Namespace{…}` groups), `json_schema.rs`, `tool_config.rs`, `mcp_tool.rs`, `dynamic_tool.rs`, `responses_api.rs`, `output_schema.rs`.
- **Built-in handlers** (`core/src/tools/handlers/`): `ApplyPatchHandler`, `PlanHandler` (update_plan), `ViewImageHandler`, `CurrentTimeHandler`, `SleepHandler`, `WaitForEnvironmentHandler`, `RequestUserInputHandler` / `RequestUserInputAsyncHandler`, `SendMessageToUserAsyncHandler`, `RequestPermissionsHandler`, `NewContextWindowHandler` + `GetContextRemainingHandler` (token budget), `ListMcpResourcesHandler` / `ListMcpResourceTemplatesHandler` / `ReadMcpResourceHandler`, `ToolSearchHandler`, `RequestPluginInstallHandler` / `ListAvailablePluginsToInstallHandler`, `TestSyncHandler`, multi-agents (§6). Each has a paired `*_spec.rs` producing the JSON schema. Most are gated behind `Feature::…` flags and `model_info.experimental_supported_tools`.
- **Shell / exec**: unified under **`unified_exec`** (`core/src/unified_exec/`, handlers `handlers/unified_exec/{exec_command,write_stdin}.rs`). `ExecCommandHandler` supports resumable PTY processes (`UnifiedExecProcessManager`, `tty` under `Feature::UnifiedExecTty`) or `::one_shot` when resumable exec is disabled. Approval key `UnifiedExecApprovalKey`.
- **apply_patch**: custom patch format in `codex-rs/apply-patch/` + `core/src/apply_patch.rs`; handler `handlers/apply_patch.rs`; runtime `tools/runtimes/apply_patch.rs`. Model can emit it as a tool OR as a freeform `apply_patch` block (`model_info.apply_patch_tool_type`).
- **MCP tools**: `handlers/mcp.rs`, `core/src/mcp.rs`, `core/src/mcp_tool_call.rs`. Registered as external tools under the server's namespace; `rmcp-client/` is the MCP client impl; `core-plugin` MCP overlays.
- **Tool search (deferred-tool discovery)**: `tools/src/tool_discovery.rs` (`TOOL_SEARCH_TOOL_NAME = "tool_search"`, `TOOL_SEARCH_DEFAULT_LIMIT = 8`), handler `handlers/tool_search.rs` (`ToolSearchHandler`, cached). Only enabled when `model_info.supports_search_tool`; lets the model search the catalog and pull deferred tools in on demand — directly analogous to Claude Code's ToolSearch. `tools/src/tool_search.rs` iterates candidate identities without materializing schemas.
- **Code Mode** (`ToolMode::{Direct, CodeMode, CodeModeOnly}`, `tools/mod.rs::requested_tool_mode`): behind `Feature::CodeMode`/`CodeModeOnly`. Instead of direct function calls, the model writes code calling tools as functions; public dispatcher tool is named **`exec`** with a **`wait`** companion (`code-mode-protocol/src/lib.rs`: `PUBLIC_TOOL_NAME="exec"`, `WAIT_TOOL_NAME="wait"`). Runs in a subprocess host: `code-mode-host/`, `code-mode-runtime/`, `code-mode/` (`GrpcCodeModeSessionProvider`, `ProcessOwnedCodeModeSession`), `v8-poc/`. In-process fallback to `Direct` if unavailable.
- **Parallel tool calls** (`core/src/tools/parallel.rs::ToolCallRuntime`): each call runs on `tokio::spawn` (`AbortOnDropHandle`). A shared `parallel_execution: Arc<RwLock<()>>` gate — parallel-capable tools take a **read** lock (run concurrently); non-parallel tools take a **write** lock (serialized). `router.tool_supports_parallel(&call)` decides. Orchestration in `core/src/tools/orchestrator.rs`.

## 3. Hooks (user-configurable shell/MCP hooks)

- Crate `codex-rs/hooks/`. **Exactly 12 events** (`hooks/src/lib.rs` `HOOK_EVENT_NAMES`): `"PreToolUse"`, `"PermissionRequest"`, `"PostToolUse"`, `"PreCompact"`, `"PostCompact"`, `"SessionStart"`, `"SessionEnd"`, `"UserPromptSubmit"`, `"SubagentStart"`, `"SubagentStop"`, `"Stop"`, `"Interrupt"`. Nine support matchers (`HOOK_EVENT_NAMES_WITH_MATCHERS`) — all but UserPromptSubmit/Stop/Interrupt. Enum `HookEventName` in `protocol`. This is a near-superset of Claude Code's hook model.
- **Config format** (TOML, in `config.toml`; `config/src/config_requirements.rs`, `HookEventsToml`):
  ```toml
  [hooks]
  managed_dir = "/cloud/hooks"      # enterprise/system/MDM managed dir
  [[hooks.PreToolUse]]
  matcher = "^Bash$"                # regex over tool name / trigger
  [[hooks.PreToolUse.hooks]]
  type = "command"
  command = "python3 /path/pre.py"
  ```
  Hooks can be layered from user, project `.codex/`, and managed (cloud/system/MDM) sources with drift rejection (`RequirementSource::*`, "managed_hooks_constraint_rejects_drift").
- **Hook handler types**: `type = "command"` (shell) and MCP tool hooks (`hooks/src/mcp.rs`, `engine/mcp_runner.rs`, `core/src/hook_mcp_executor.rs`): `argument_template` with `${tool_input.*}` / `${…}` placeholder expansion (`expand_mcp_argument_template`) calling an MCP server tool. Engine: `hooks/src/engine/{discovery,dispatcher,matcher,command_runner,mcp_runner,output_parser,schema_loader}.rs`.
- **Blocking semantics** (`hooks/src/events/pre_tool_use.rs`, Claude-Code-compatible): command hook exit code **2** + a reason on **stderr** ⇒ `HookRunStatus::Blocked` with `block_reason` (turn feeds the reason back to the model). Exit 0 may still carry structured JSON on stdout: `PreToolUseCommandOutputWire` has `decision`/`reason` + universal fields `HookUniversalOutputWire{ continue, stopReason, suppressOutput, systemMessage }` (`hooks/src/schema.rs`). Other non-zero exits = non-blocking error. `Stop` hook can request continuation (block + continuation fragments → re-prompt; see turn.rs stop-hook handling).
- JSON input/output schemas are code-generated as fixtures (`hooks/src/schema.rs`, bin `write_hooks_schema_fixtures.rs`): per-event `*.command.input.schema.json` / `.output.schema.json`. Subagent hooks carry `agent_id`/`agent_type` (`SubagentCommandInputFields`).
- `core/src/hook_runtime.rs` runs hooks during a turn; `legacy_notify.rs` maps old `notify` program to `AfterAgent` → `AgentTurnComplete`. Hook events also exposed over app-server (`protocol/v2/config.rs`, `v2/hook.rs`).

## 4. Approvals & sandbox

- **Approval policy** `protocol/src/protocol.rs::AskForApproval` (serde kebab): `UnlessTrusted` (wire `"untrusted"`), `OnRequest` (default; alias `"on-failure"`), `Granular(GranularApprovalConfig)` (wire `"granular"`), `Never`. `GranularApprovalConfig` booleans: `sandbox_approval`, `rules`, `skill_approval`, `request_permissions`, `mcp_elicitations` — each false auto-rejects that class instead of prompting.
- **Sandbox policy** `protocol/src/protocol.rs::SandboxPolicy` (serde tag `type`): `DangerFullAccess` (`"danger-full-access"`), `ReadOnly{network_access}` (`"read-only"`), `ExternalSandbox{network_access: NetworkAccess}` (`"external-sandbox"`, process already externally sandboxed), `WorkspaceWrite{ writable_roots, network_access, exclude_tmpdir_env_var, exclude_slash_tmp }` (`"workspace-write"`). High-level `SandboxMode` enum in `protocol/src/config_types.rs`: `ReadOnly`, `WorkspaceWrite`, `DangerFullAccess`.
- **WritableRoot** carries `read_only_subpaths` + `protected_metadata_names` so even under a writable root, `.git` / `.git/hooks` / `.codex` can't be written (privilege-escalation guard). `NetworkAccess::{Restricted(default), Enabled}`.
- **Review decision** (what an approval returns) `protocol` `ReviewDecision`: `Approved`, `ApprovedForSession`, `ApprovedExecpolicyAmendment{…}`, `ApprovedMcpPolicyAmendment`, `NetworkPolicyAmendment{…}`, `Denied{…}`, `Abort`, `TimedOut`. Approval routing/caching: `core/src/tools/approvals.rs` (`ApprovalContext`, `ApprovalCacheKey::ExecCommand(UnifiedExecApprovalKey)`), `safety.rs` (`core/src/safety.rs`), elicitation `core/src/elicitation.rs`.
- **Permissions model** `protocol/src/permissions.rs` (`PermissionProfile`, `FileSystemSandboxPolicy`) — richer per-path FS policy that legacy `SandboxPolicy` maps onto. `request_permissions` tool (`handlers/request_permissions.rs`) lets the model ask to widen access mid-turn (prompt templates `prompts/templates/permissions/…`).
- **Sandbox backends** (`core/src/sandboxing/`, `tools/sandboxing.rs`, `codex-rs/sandboxing/` `SandboxType`): Linux via `linux-sandbox/` (Landlock + seccomp) and `bwrap/` (bubblewrap); macOS Seatbelt; `mxc-sandbox/` (an "MXC" backend, `windows_mxc_available()`); `external-sandbox` / `ExternalSandbox`.
- **Windows sandbox** `windows-sandbox-rs/` (very large) + `windows-sandbox-service/` (a privileged Windows **service** for provisioning/elevation) + `core/src/windows_sandbox.rs`:
  - **AppContainer / package identity** isolation: `app_package.rs`, `package_identity.rs`, `cap.rs` (capabilities), `identity.rs`, `token.rs`/`token_user.rs` (restricted tokens), `hide_users.rs`, `desktop.rs` (separate desktop).
  - **Filesystem**: ACL-based — `acl.rs`, `workspace_acl.rs`, `file_write.rs`, `deny_read_acl.rs` + `deny_read_resolver/state/walker.rs` (deny-read enforcement), `no_reparse_dir.rs` (reparse/symlink guard), `path_normalization.rs`. `windows_sandbox_read_grants.rs` in core.
  - **Network**: **WFP (Windows Filtering Platform)** — `wfp.rs`/`wfp_setup.rs` installs `FWP_ACTION_BLOCK` filters keyed on `FWPM_CONDITION_ALE_USER_ID` (the sandbox user SID), so outbound traffic is blocked at the kernel filter layer unless policy allows.
  - PTY via `conpty/`; secret storage via `dpapi.rs`; service IPC `windows-sandbox-service/src/ipc.rs`, machine policy `machine_policy.rs`. `WindowsSandboxLevel` + `WindowsSandboxModeToml` select the level; `effective_windows_sandbox_type`. Config/protocol surface: `protocol/v2/windows_sandbox.rs`.
- **Exec policy (rules files)** `codex-rs/execpolicy/` (also `core/src/exec_policy.rs`): a **Starlark**-based policy DSL (parser consumes starlark `Value`s, `UnpackList<Value>`). Primitives (`execpolicy/src/rule.rs`): `PrefixRule{ program, PrefixPattern(Vec<PatternToken>), decision }`, `NetworkRule{ host, NetworkRuleProtocol, decision }`; `PatternToken` = fixed string or alternatives. `Decision` (`execpolicy/src/decision.rs`): `Allow` / `Prompt` / `Forbidden`. Rules carry `match`/`not_match` examples validated at parse time. `codex execpolicy check -r <file>` evaluates a command (`execpolicycheck.rs`). `amend.rs` appends allow-prefix/network rules at runtime when the user approves an amendment. `UnlessTrusted` = everything prompts unless an execpolicy rule allows it.
- **Network policy at runtime**: `core/src/network_policy_decision.rs` + `core/src/tools/network_approval.rs` (per-host approval for sandboxed network), `network-proxy/` (an egress proxy), `responses-api-proxy/`, `tcp-tunnel/`. Network item in protocol: `item/.../NetworkAccess`.

## 8. Memories

- Real, substantial feature. Crates `codex-rs/memories/{read,write}` (`codex-memories-read`, `codex-memories-write`) + runtime orchestration `core/src/context/memory.rs`, `core/src/memory_usage.rs`. Overview: `memories/README.md`.
- **Trigger**: on **root** session start, async in background, only if session is not ephemeral, memory feature enabled, not a sub-agent session, and the **state DB** is available.
- **Storage**: SQLite **state DB** (`codex-rs/state/`, `state_db_bridge.rs`) for stage-1 records + leasing/claim coordination; **filesystem** artifacts under `~/.codex/memories/`, which is a **git-baselined** dir (`~/.codex/memories/.git` via `codex-git-utils`). Artifacts: `raw_memories.md`, `rollout_summaries/` (one per rollout), `phase2_workspace_diff.md`, and agent-maintained `MEMORY.md`, `memory_summary.md`, `skills/`.
- **Phase 1 (per-thread extraction)**: claims bounded eligible rollouts (interactive sources, age window, idle long enough, not already claimed, scan limits), filters to memory-relevant items, sends each to a model in parallel (concurrency cap), expects structured output `{ raw_memory, rollout_summary, rollout_slug? }`, **redacts secrets**, writes stage-1 outputs to DB. Outcomes `succeeded` / `succeeded_no_output` / `failed` (retry backoff + lease).
- **Phase 2 (global consolidation)**: single global lock; loads top-N selected stage-1 outputs ranked by `usage_count` then recency (`last_usage`/`generated_at`, honoring `max_unused_days`); syncs FS artifacts, prunes stale summaries + old extension resources; writes a git-style `phase2_workspace_diff.md`; if there are changes it **spawns an internal consolidation sub-agent** (collab disabled, no approvals, no network, local write only) pointed at the diff to update `MEMORY.md` etc.; resets git baseline on success; marks job in DB. Watermark tracking prevents re-processing.
- **Read path** (`memories/read`): injects memory developer-instructions into the prompt, parses **memory citations** (item `AgentMessage.memory_citation`, protocol `v2/memory.rs`), classifies read-usage telemetry (feeds the usage ranking above). Prompt templates: `read/templates/memories/read_path.md`, `write/templates/memories/{stage_one_system,stage_one_input,consolidation}.md`.

## 9. AGENTS.md / instructions assembly; prompt files

- **AGENTS.md** (`core/src/agents_md.rs`): default filename `AGENTS.md` (`DEFAULT_AGENTS_MD_FILENAME`); local override `AGENTS.override.md` (`LOCAL_AGENTS_MD_FILENAME`). Discovery: walk up from cwd to the **project root** (first dir containing a `project_root_markers` entry; default marker `.git`; empty marker list disables parent traversal), then concatenate every `AGENTS.md` **from project root down to cwd inclusive**, in that order; never walk past root. Fallbacks via `project_doc_fallback_filenames`; size cap `project_doc_max_bytes`. Combined with host-provided user instructions using separator `"\n\n--- project-doc ---\n\n"` (`AGENTS_MD_SEPARATOR`). `load_project_instructions`.
- **Base/system instructions come from the model catalog**, not a single file: `prompts/src/model_instructions.rs::render_model_instructions` returns `model_info.instructions_template()` (`ResolvedModelMessages::from_model`). So per-model system prompts ship as model metadata (`codex-protocol` openai_models). Empty-template warnings logged.
- **Prompt template crate** `codex-rs/prompts/` (`prompts/templates/`): `compact/{prompt,summary_prefix}.md` (§7); `permissions/approval_policy/{never,on_request,on_request_rule_request_permission,unless_trusted}.md` and `permissions/sandbox_mode/{danger_full_access,read_only,workspace_write}.md` (injected to tell the model the current approval+sandbox regime); `guardian/{classifier_instructions,policy,policy_template,node_repl_policy}.md`; `review/rubric.md`; `realtime/*`; `persistent_mode.md`. Rust-side renderers: `multi_agent_instructions.rs`, `permissions_instructions.rs`, `update_plan_instructions.rs`, `review_request.rs`, `review_exit.rs`, `guardian_instructions.rs`, `model_messages/`.
- Instruction provenance tracked (`BaseInstructionsProvenance`); app-server exposes "instruction source files currently loaded for this thread" per `thread/started`.

## 10. App-server protocol (most relevant to QMX UI)

- Crates: `app-server-protocol/` (types + JSON-RPC), `app-server/` (the server), `app-server-client/`, `app-server-transport/`, `app-server-daemon/` (long-lived daemon; `codex app-server daemon` subcommands), `app-server-test-client/`, `app-server-protocol-noop-macros/`. CLI entry `codex app-server`. Transport is **JSON-RPC 2.0** (`app-server-protocol/src/rpc.rs`: `method: String`, string|int ids). TS types generated via `#[ts(...)]` (`export.rs`, `precomputed_exports.rs`) — a client SDK is auto-derived.
- **Two protocol versions**: legacy `protocol/v1.rs` and current **`protocol/v2/`** (per-domain files: `thread.rs`, `turn.rs`, `item.rs`, `account.rs`, `model.rs`, `fs.rs`, `mcp.rs`, `plugin.rs`, `permissions.rs`, `hook.rs`, `memory.rs`, `apps.rs`, `config.rs`, `review.rs`, `realtime.rs`, `remote_control.rs`, `computer_use_config.rs`, `browser_use_config.rs`, `windows_sandbox.rs`, `collaboration_mode.rs`, …). All names camelCase on the wire.
- **Core method surface** (string method names grepped from `app-server-protocol/src`):
  - **Thread lifecycle**: `thread/start` → `thread/started`, `thread/resume`, `thread/fork`, `thread/archive`/`unarchive`/`delete` (+ past-tense notifications `thread/archived`/`deleted`/`closed`), `thread/list`, `thread/items/list`, `thread/items/read`, `thread/turns/list`, `thread/timeline/list`, `thread/search`, `thread/searchOccurrences`, `thread/settings/update(+updated)`, `thread/status/changed`, `thread/tokenUsage/updated`, `thread/revert(+reverted)`, `thread/compact/start(+compacted)`, `thread/goal/{get,set,clear,updated}`, `thread/shellCommand`, `thread/backgroundTerminals/{list,clean,terminate}`, `thread/environment/{connected,disconnected}`, `thread/unsubscribe`, `thread/approveGuardianDeniedAction`, `thread/attachment/{add,list,remove,updated}`.
  - **Turn lifecycle**: `turn/start` → `turn/started` → `turn/completed`; `turn/interrupt`; **`turn/steer`** (inject input into the running turn); `turn/settings/update`; streaming `turn/diff/updated`, `turn/plan/updated`, `turn/moderationMetadata`.
  - **Item (streaming) events** (server→client notifications): `item/started`, `item/completed`, `item/agentMessage/delta`, `item/reasoning/{textDelta,summaryTextDelta,summaryPartAdded}`, `item/plan/delta`, `item/commandExecution/outputDelta`, `item/commandExecution/terminalInteraction`, `item/fileChange/{patchUpdated,outputDelta}`, `item/mcpToolCall/progress`, `item/tool/call`, `item/autoApprovalReview/{started,completed}`.
  - **Approvals over the protocol = server→client requests** (the UI answers them): `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/permissions/requestApproval`, `item/tool/requestUserInput`. Decisions: `CommandExecutionApprovalDecision = { Accept, AcceptForSession, AcceptWithExecpolicyAmendment{…}, ApplyNetworkPolicyAmendment{…}, Decline, Cancel }`; `FileChangeApprovalDecision = { Accept, AcceptForSession, Decline, … }` (`protocol/v2/item.rs`, mapped from core `ReviewDecision`). So the host renders a prompt and returns the decision as the RPC response.
  - Account/auth: `account/{read,updated,logout,login/{start,cancel,completed},usage/read,rateLimits/{read,updated}}`, ChatGPT + API-key + Amazon Bedrock + gateway-OAuth auth modes. Model: `model/{list,rerouted,verification,safetyBuffering/updated}`. FS (host-mediated file ops the sandbox routes through the client): `fs/{readFile,writeFile,readDirectory,createDirectory,copy,remove,getMetadata,watch,unwatch,changed}`.
- **ThreadItem kinds** (`protocol/v2/item.rs::ThreadItem`, tag `type`): `UserMessage`, `HookPrompt`, `AgentMessage` (with `phase`, `memoryCitation`, `delivery`, async `questions`), `FunctionCallOutput`, `Plan`, `Reasoning` (summary+content), `CommandExecution` (with `sandboxType`, parsed `CommandAction::{Read,ListFiles,Search,Unknown}`), `FileChange`, `McpToolCall`, `DynamicToolCall`, `CollabAgentToolCall`, `SubAgentActivity`, `ImageView`, `EnteredReviewMode`, `ExitedReviewMode`, `ContextCompaction`. UserInput variants: `InputText`, `InputImage{imageUrl}`, `InputAudio{audioUrl}`.
- **Driving model for a desktop/IDE client**: connect to `codex app-server` over stdio (daemon mode available), `thread/start` (or `resume`/`fork`) → subscribe to the thread → `turn/start` with user input → consume `item/*` deltas + `turn/diff/updated` live → answer `item/*/requestApproval` server-requests as the user clicks → `turn/completed`. `turn/steer` enables the "type while it runs" box; `turn/interrupt` the stop button. `thread/shellCommand` + `thread/backgroundTerminals/*` + `item/commandExecution/terminalInteraction` back a **right-panel terminal** (interactive PTY surfaced to the UI). Errors use JSON-RPC codes (`-32602` invalid params, `-32603` internal, `-32600` with `data.reason:"serverShuttingDown"`; see `app-server/README.md`). `remote_control.rs` lets another client drive a thread.

## Ideas QMX should borrow for a Deep Agents harness

1. **Protocol-first host boundary.** Codex's whole UI (incl. the Codex-desktop app) rides on a versioned JSON-RPC app-server with explicit `thread/*`, `turn/*`, `item/*` methods (`app-server-protocol/src/protocol/v2/`). QMX should define an equivalent LangGraph-side RPC surface (thread start/resume/fork, turn start/steer/interrupt, item deltas) so the desktop UI, copilots, and background workflows all drive the agent the same way.
2. **Approvals as server→client requests, not inline blocks.** `item/commandExecution/requestApproval` / `item/fileChange/requestApproval` / `item/permissions/requestApproval` with a typed decision enum incl. `AcceptForSession` and "amend the policy" variants (`protocol/v2/item.rs`). This is exactly the human-in-the-loop pattern QMX needs for trades/config — one approval channel, auditable, with "approve for session" + "amend rule".
3. **`turn/steer` + a per-turn input queue + session mailbox** (`core/src/session/input_queue.rs`). Lets a user (or another agent) inject input mid-turn without racing the model. QMX's "type while it runs" box and inter-agent messaging should use one queue abstraction like this.
4. **Deferred tools + a `tool_search` tool** (`tools/src/tool_discovery.rs`, `handlers/tool_search.rs`, `ToolExposure::Deferred`). Keep the model's visible tool list small; let it search and pull in the rest on demand. Scales to large MCP/connector tool sets — directly relevant to QMX's "everything addable/removable" Lego vision.
5. **Per-step tool registry rebuild** (`tools/spec_plan.rs::build_tool_router`): tools are a pure function of model + features + sandbox + environment, assembled fresh each step. QMX should resolve the toolset per turn from current config rather than a static global set.
6. **Parallel tool calls behind a read/write gate** (`core/src/tools/parallel.rs`): parallel-safe tools take a shared read lock, side-effecting tools take an exclusive write lock. Simple, correct concurrency control QMX can mirror in a Deep Agents executor.
7. **12-event hook system with Claude-Code-compatible blocking semantics** (`hooks/`): exit-2+stderr blocks, structured JSON `{decision, reason, continue, systemMessage}`, plus `PermissionRequest`/`PreCompact`/`SubagentStart`/`Interrupt`. Also **MCP-tool hooks** with `${tool_input.*}` templating — hooks aren't limited to shell. QMX should adopt the same event set and the managed-dir/drift-rejection layering for enterprise control.
8. **Layered, auditable policy stack**: approval policy (`AskForApproval` incl. **`Granular`** per-class toggles) × sandbox policy (`SandboxPolicy`) × **Starlark execpolicy rules** with `allow`/`prompt`/`forbidden` and runtime `amend` on approval (`execpolicy/`). QMX's broker/risk gating wants this separation (coarse mode + fine-grained rule file + "remember this").
9. **WritableRoot with protected metadata** (`protocol/src/protocol.rs`): even under a writable root, `.git/hooks`, `.codex`, etc. stay read-only to block self-escalation. QMX should hard-protect its own config/credential paths from agent writes the same way.
10. **Compaction as a first-class task with a handoff-summary prompt** (`prompts/templates/compact/prompt.md`, `SUMMARY_PREFIX`) and auto-trigger on token thresholds, with remote-vs-local capability negotiation (`RemoteCompactionSupport`). QMX should ship an editable compaction prompt and trigger on a context-window watermark mid-turn, not only between turns.
11. **Two-phase memory pipeline** (`memories/README.md`): per-rollout extraction → DB with secret redaction and usage-ranked selection → periodic consolidation by a dedicated no-network/local-write sub-agent into a **git-baselined** `~/.codex/memories/` (`MEMORY.md`, summaries). QMX already keeps MEMORY.md by hand; this is a blueprint for automating it safely (lease-based, retryable, diff-tracked, redacted).
12. **Agent roles as config layers, not code** (`core/src/agent/role.rs`): `explorer`/`worker`/`default` built-ins overriding model + reasoning effort + instructions + skills, plus user `*.toml` roles discovered from disk. Maps cleanly onto QMX's tiered-model rules (bulk-worker/Sonnet/Opus/Fable) — express the tiers as roles the orchestrator selects.
13. **Hard multi-agent limits**: `max_threads` (`AgentLimitReached`) and **spawn-depth** caps (`core/src/agent/registry.rs`), plus a message board + agent-graph store for collaboration. QMX's background-workflow fan-out needs exactly these guardrails (and the explorer "trust the result, run many in parallel" + worker "you are not alone, don't revert others' edits" prompt norms are worth copying verbatim).
14. **AGENTS.md assembly = root→cwd concatenation with a local override + size cap + project-root markers** (`core/src/agents_md.rs`), base system prompt coming from the model catalog. QMX should treat its `docs/` + CLAUDE.md as a layered, bounded instruction stack with an explicit override file and provenance tracking.
15. **Skills discovered from multiple roots (system/user/project/plugin) with YAML-frontmatter SKILL.md, injected as a listing + pulled in on @mention or implicit script/doc access** (`skills/`, `core/src/skills.rs`). The implicit-invocation detector (model reads SKILL.md or runs a skill script ⇒ record/approve) is a clever, low-friction way to gate and meter skill use that QMX should replicate. Bonus: a right-panel interactive terminal is modeled as `thread/shellCommand` + `thread/backgroundTerminals/*` + `item/commandExecution/terminalInteraction` — reuse that shape for QMX's terminal pane.

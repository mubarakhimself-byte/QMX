## A. BMAD v6 architecture in plain words

**What it is.** BMAD is a library of named "skills" that make an AI coding tool act like a disciplined team. It has facilitators that pull thinking out of the human, planners that turn that thinking into contracts (PRD, architecture spine, spec), and builders and reviewers that execute against those contracts. The stated philosophy is that you understand what you ship instead of accepting AI output blindly (docs.bmad-method.org home).

**Layers:**

1. **Core module** (`B/core`, skills in `S/`): cross-cutting tools any module can call.
   - bmad-help (router), bmad-brainstorming, bmad-advanced-elicitation, bmad-party-mode, bmad-review (multi-lens), bmad-forge-idea, bmad-deep-recon, bmad-customize.
   - Shared deterministic scripts in `B/scripts/`: `memlog.py`, `resolve_customization.py`, `resolve_config.py`, `render_skill.py`, `config_utils.py`.
2. **Modules**: installable bundles of agents and workflows, each with a `config.yaml` and a `module-help.csv` registry.
   - **BMM** (the software lifecycle): brief, PRD, UX, architecture, epics, build, review, retro.
   - **CIS** (Creative Intelligence Suite): 6 personas and 4 facilitated workflows.
   - **TEA** (Test Architect): one persona, about 10 testarch workflows, and a large `resources/knowledge` fragment library.
   - **BMB** (BMad Builder, not installed here): the agent, workflow and module builders.
   - **GDS** (Game Dev Studio): external.
   - The installer merges every `module-help.csv` into `B/_config/bmad-help.csv` and every skill into `B/_config/skill-manifest.csv`.
3. **Agents**: persona skills such as Mary, Winston, Carson and Murat.
   - Each has a hard-coded identity, a customizable persona (role, identity, communication_style, principles), `persistent_facts`, and a **menu** of codes that dispatch to skills or inline prompts.
   - An agent is a *front door and a voice*, not where the work happens; the work lives in workflows. Evidence: `S/bmad-agent-analyst/SKILL.md` and `customize.toml`.
4. **Workflows**: outcome skills (PRD, brainstorming, design thinking, and so on). The BMB docs name three shapes:
   - Simple Utility: input/output, headless, script-driven.
   - Simple Workflow: 3–8 steps in one SKILL.md.
   - Complex Workflow: a router SKILL.md plus stage prompts (bmad-builder-docs …/reference/workflow-patterns/).
   - Strict step files are "Layer 4" progressive disclosure, kept for compliance-grade flows (…/explanation/progressive-disclosure/).
5. **Config**: `B/config.toml`, generated by the installer and treated as read-only.
   - Holds the project name, language, output folders per module, and the **agent roster** (name, title, icon, one-line voice description). Party mode can therefore cast agents that have no skill folder.
   - Overrides go in `B/custom/config.toml` (team) and `config.user.toml` (personal). The resolver merges four layers.
6. **Customization**: every skill ships a `customize.toml` that declares its *override surface*.
   - Team overrides go in `B/custom/<skill>.toml`, personal ones in `B/custom/<skill>.user.toml`.
   - Merge rules are shape-based: scalars replace, tables deep-merge, arrays keyed by `code`/`id` replace-or-append, other arrays append (docs.bmad-method.org/customize/customize-bmad/).
   - Updates never touch the custom files.
7. **"Hooks".** BMAD has no event-hook runtime. It uses declarative lifecycle slots that every skill honors:
   - `activation_steps_prepend` / `activation_steps_append`
   - `persistent_facts` (literal text, `file:` globs, or `skill:` references)
   - `on_complete`
   - `external_handoffs` (MCP routing after artifacts land; see `S/bmad-brainstorming/customize.toml`)
8. **Artifacts**: everything is written to `_bmad-output/{planning,implementation,test}-artifacts`, one run folder per session.
   - A run folder holds a deliverable (`prd.md`, `ARCHITECTURE-SPINE.md`, …), a `.memlog.md`, and optionally `addendum.md` and `reviews/`.
   - State lives in frontmatter (`status: draft|final`) or in step-checkpoint frontmatter (`stepsCompleted`, `nextStep`), so any session can resume.
9. **Rendering**: `render_skill.py` bakes the resolved config and customization into an immutable, hash-addressed snapshot of a skill.
   - Example: `B/render/bmad-build/qmx-…/090389978403dadaa1cc/` with `manifest.json` recording every resolved value and the renderer's sha256.
   - The rendered step files have no template variables left, so the run is deterministic and auditable.

**How handoffs work.** Skills do not call each other's internals. They hand off **files**:
- The brainstorm `brainstorm-intent.md` feeds the brief, PRD or spec. The PRD plus addendum feed the architecture. The spec's `<frozen-after-approval>` intent plus Code Map feed a context-free implementation subagent.
- `bmad-help` reads the catalog's `preceded-by`/`followed-by`/`required` columns and checks which `outputs` patterns already exist on disk. From that it tells the human where they are and what comes next.
- It always recommends a *fresh context window* per skill (`S/bmad-help/SKILL.md`).

## B. Mechanism catalogue

Each entry gives: what it is → why it exists → evidence → **Borrow?**

1. **Persona agent with a menu.** Fixed identity, a customizable voice, a numbered menu of codes, an icon prefix on every message, and dispatch on a fuzzy match without a confirmation ritual.
   - Why: gives the human a mental model of "who is talking" and a discoverable command surface without memorizing skill names.
   - Evidence: `S/bmad-agent-analyst/SKILL.md` (Steps 3–8), `customize.toml` `[[agent.menu]]`.
   - **Adapted.** QMX needs one Copilot with *modes* (Research, Build-workflow, Build-mini-app, Review), not six characters. Keep the menu-of-capabilities and "dispatch directly when intent is clear". Drop the theatrical personas.

2. **Activation sequence** (resolve customization → prepend steps → persistent facts → config → greet → append steps → menu). "Confirm every entry ran before proceeding."
   - Why: a predictable boot order makes overrides reliable and auditable.
   - Evidence: every SKILL.md "On Activation".
   - **Yes.** It maps onto Deep Agents middleware: a pre-model hook that loads facts and org rules, and a post-run hook for `on_complete`.

3. **`persistent_facts` with `file:` globs.** Static context the skill always carries, e.g. `file:{project-root}/**/project-context.md`.
   - Why: org rules and domain constants survive every session without re-asking.
   - Evidence: all `customize.toml`; QMX's own `B/custom/bmad-prd.toml` uses it to force the planning-only pipeline.
   - **Yes.** Workspace-level "house rules", e.g. "USD only", "risk authority = node docs", "never place live orders from the Copilot".

4. **Three-layer customization with shape-based merge** (shipped < team < user).
   - Why: users change behavior without forking, and updates never clobber edits. Keyed arrays mean you can replace menu item `BP` without copying the whole menu.
   - Evidence: `B/scripts/resolve_customization.py`, `S/bmad-customize/SKILL.md`.
   - **Yes, strongly.** Use the same pattern for QMX skills: platform defaults < org/workspace < user. The merge semantics are simple enough to implement in about 100 lines.

5. **`bmad-customize` meta-skill.** Translates plain English into a sparse override, shows a diff, waits for an explicit yes, writes the file, then verifies by re-resolving. It refuses to invent fields that the surface doesn't expose.
   - Why: non-technical users can tune behavior safely.
   - Evidence: `S/bmad-customize/SKILL.md` Steps 1–6.
   - **Yes.** A "Tune this skill" mode for QMX. The "don't invent fields; offer prepend/append or recommend building a new skill" rule is the important part.

6. **Lifecycle slots instead of hooks** (`activation_steps_*`, `on_complete`, `external_handoffs`).
   - Why: a portable way to extend behavior without code. External handoffs are skipped and flagged if the tool is missing, and local files always exist.
   - Evidence: `S/bmad-brainstorming/customize.toml`.
   - **Adapted.** QMX has real code, so implement these as real hooks (pre_run, post_artifact, on_complete, on_handoff) but keep the declarative, user-editable list form. The degrade-gracefully rule ("local artifact always exists") is worth keeping.

7. **memlog (append-only working memory).** One line per idea, decision, assumption or event. Writes are atomic via a script. It is never re-read mid-session, only on resume. Deliverables are *derived* from it.
   - Why: the conversation is ephemeral; "whatever isn't in it is gone". It also makes the deliverable regenerable and keeps the parent context lean.
   - Evidence: `B/scripts/memlog.py` docstring (three invariants: append-only, write-only/blind, crash-safe), `S/bmad-brainstorming/SKILL.md` "The memlog".
   - **Yes, top priority.** This is the right spine for long Copilot tasks: a backtest campaign, building a workflow, research. Store it per task in the Deep Agents filesystem or Store.
   - One inconsistency to avoid: the memlog docstring says "no lifecycle status", yet brainstorming flips `status: complete` in frontmatter. Choose one rule.

8. **"Nothing exists until it is a file."** Digests, extractions and sections are written to the run folder as they land. The chat is a control channel, not the store.
   - Why: survives crashes, compaction and model switches.
   - Evidence: `S/bmad-deep-recon/SKILL.md` "How you work".
   - **Yes.** Essential for long-running jobs.

9. **Resume by globbing run folders and frontmatter.** On activation, find `.memlog.md` or `prd.md` files with a non-complete status and offer resume or fresh start. TEA adds `runKey` identity and refuses to merge two runs.
   - Evidence: brainstorming step 5; `S/bmad-prd/SKILL.md` Create intent; `S/bmad-testarch-test-design/steps-c/step-01-detect-mode.md` (lines ~137–165).
   - **Yes.** "You have 2 unfinished tasks: resume?" is a core copilot UX. Keep the run-identity check.

10. **Step-file (micro-file) architecture.** One step file loaded at a time, read fully, never skipped, halting at checkpoints. Progress lives in frontmatter.
    - Why: stops the LLM from skipping ahead or summarizing a procedure away, and gives exact resume points.
    - Evidence: `B/render/bmad-build/.../workflow.md` "WORKFLOW ARCHITECTURE"; TEA `steps-c/`, `steps-e/`, `steps-v/` (tri-modal create/edit/validate).
    - **Adapted.** Use it only for compliance-grade flows: promoting a strategy to live trading, or a money-path config change. BMB itself calls this "Layer 4… the lowest level needed is best". For everyday work, a router plus references is enough.

11. **Progressive disclosure, four layers:**
    - L1: frontmatter vs body.
    - L2: on-demand references and scripts.
    - L3: intent routing to whole different paths.
    - L4: step files.
    - Why: "never load more context than the agent needs right now".
    - Evidence: bmad-builder-docs …/explanation/progressive-disclosure/; brainstorming loads `mode-*.md` only after the stance is picked, and `headless.md` is "quarantined".
    - **Yes.** It matches Deep Agents' skills model directly.

12. **Quarantined mode files.** The headless file is loaded only on a machine signal, because its behavior (the AI generates the ideas) is the inverse of interactive facilitation. "When in doubt, you are interactive."
    - Evidence: `S/bmad-brainstorming/references/headless.md`.
    - **Yes.** The general lesson: put behaviors that contradict each other in separate files, and load only the active one. Use it for QMX Copilot modes (Autopilot vs Pair).

13. **Stances / working modes.** Brainstorming offers Facilitator (the AI never supplies ideas), Creative Partner (both contribute, with mandatory authorship tags), and Ideate-for-me (autonomous, then offers to continue together). The PRD offers Fast path (batched questions, `[ASSUMPTION]` tags) vs Coaching path.
    - Why: the user, not the AI, decides how much of the thinking is theirs.
    - Evidence: `S/bmad-brainstorming/references/mode-*.md`; `S/bmad-prd/SKILL.md` "Working mode".
    - **Yes.** Map to QMX "Do it for me / Pair with me / Coach me". `[ASSUMPTION]` tags in drafts are cheap and honest.

14. **Headless contract.** No greeting or questions. Inputs come as a structured payload; output is a JSON status block (`complete|partial|blocked`, artifact paths, `assumptions[]`).
    - Evidence: `S/bmad-brainstorming/references/headless.md` "Return".
    - **Yes.** Every QMX skill should be callable by the scheduler or other agents with exactly this contract. `assumptions[]` is the key field.

15. **Advanced Elicitation.** A refinement checkpoint any skill can call at a pause. It offers 5 hand-picked methods from a 71-row catalog (categories: advanced, collaboration, competitive, core, creative, framing, learning, philosophical, research, retrospective, risk…), plus `r` reshuffle, `a` list all, `x` proceed. Each method shows its proposed changes and **waits for y/n** before applying.
    - Why: forces the LLM to re-think its last output through a named lens (pre-mortem, red team, first principles, Socratic…) under human control.
    - Evidence: `S/bmad-advanced-elicitation/SKILL.md`, `assets/methods.csv`, `scripts/pick_methods.py` (serves the catalog so it never enters context whole).
    - **Adapted.** Offer "Pressure-test this" on any Copilot artifact: strategy, workflow, mini-app spec. Make the methods quant-flavored (overfitting audit, regime-shift pre-mortem, look-ahead-bias hunt, capacity/slippage red team). Keep "never change without a yes".

16. **Party mode.** A multi-persona round-table. Modes:
    - session: one mind voices all personas.
    - auto: spawn real agents only when independent thinking changes the outcome.
    - subagent: a standing agent per persona, all sharing "one room".
    - agent-team.
    Rules: short turns, unresolved clashes, never paraphrase a persona, never tie a bow. Per-party memlog memory, custom parties and personas, and an HTML keepsake.
    - Evidence: `S/bmad-party-mode/SKILL.md`, `references/mode-subagent.md`, `party-memory.md`.
    - **Adapted / mostly no for daily use.** The theater is overkill. The useful core is "Persona-Driven Parallel Reasoning" (BMB subagent pattern 5): spawn 3–5 independent specialist reviewers (risk manager, execution trader, quant skeptic, compliance) on a decision, then weave the results. Keep the "one shared room" and "don't resolve the clash" rules.

17. **Multi-lens review** (`bmad-review`). Lenses are config entries (`applies_to`, `when`, `after` dependencies). Independent lenses run as parallel context-free subagents, and all findings go into one canonical JSON shape (`location`, `trigger_condition`, `guard_snippet`, `potential_consequence`), with **no severity from reviewers**.
    - Stances differ by lens. Adversarial must find ≥10 issues and treats zero as a signal to re-check. Verification-gap only claims what it verified. Editorial lenses treat content as sacrosanct.
    - Evidence: `S/bmad-review/SKILL.md`, `references/lens-adversarial.md`, `lens-verification-gap.md`.
    - **Yes.** A pluggable "lens" registry for reviewing user-built workflows and mini apps, e.g. a data-leakage lens, a cost/compute lens, a broker-safety lens.

18. **Triage with information asymmetry.** The parent ignores reviewer severity, because reviewers lack context. It routes each finding to one of: intent_gap (back to the human), bad_spec (amend the spec, keep KEEP notes, re-derive), patch (auto-fix), defer (append to `deferred-work.md`), or reject. It caps at 5 review loops, then escalates.
    - Evidence: `B/render/bmad-build/.../step-04-review.md` "Classify".
    - **Yes.** A disciplined auto-fix loop that knows when to stop and ask. The 5-loop cap and `deferred-work` ledger are directly reusable.

19. **Frozen intent block.** `<frozen-after-approval>`: after the human approves, only the human may change the Intent and Boundaries. The spec's Always / Ask First / Never boundary tiers tell the executor when to HALT.
    - Evidence: `B/render/bmad-build/.../spec-template.md`, `step-02-plan.md` CHECKPOINT 1.
    - **Yes.** For long autonomous Copilot jobs: freeze the approved goal and boundaries, let the agent change the plan, and route anything touching "Ask First" (spend compute budget, touch live account) to a human interrupt.

20. **Checkpoint preview** (`bmad-checkpoint-preview`). A guided human review of a change in stages: Orientation → Walkthrough (organized by *concern*, not file) → Detail pass → Testing → Wrap-up. A breadcrumb shows the current stage. Each stage is front-loaded in one message, then the AI stops talking. Every reference is a clickable `path:line`.
    - Evidence: `S/bmad-checkpoint-preview/SKILL.md`, `step-01-orientation.md`, `step-02-walkthrough.md`; `bmad-build` step-05 "Suggested Review Order".
    - **Yes.** The QMX UI can render this natively: a "Walk me through what you built" panel organized by concern, with links into the workflow canvas or mini-app code.

21. **Reviewer Gate at finalize.**
    - A cheap deterministic lint runs first (`lint_spine.py`: placeholders, duplicate IDs, missing fields, unpinned versions).
    - Then a rubric walker plus configured reviewers run as parallel subagents. Each writes a full review file and returns only a compact summary.
    - Findings are surfaced in tiers (verdict, then critical/high, then "plus N more in {file}"), each with autofix / discuss / defer / ignore.
    - Gate depth scales with stakes.
    - Evidence: `S/bmad-architecture/references/reviewer-gate.md`, `S/bmad-prd/SKILL.md` "Reviewer Gate".
    - **Yes.** "Scripts for the mechanical half, LLM for the semantic half" and "tiered, never dumped" are the right quality pattern.

22. **Stakes calibration.** One probe (hobby / internal / launch) sets rigor, length and gate depth. Length is about two pages for hobby work and as long as the requirements need for a launch.
    - Evidence: `S/bmad-prd/SKILL.md` Discovery and PRD Discipline.
    - **Yes.** "Is this a quick look, a paper-trading candidate, or going live?" should scale the Copilot's checks.

23. **Extract, don't ingest.** Source docs go to subagents, which return digests. The parent never reads raw sources wholesale.
    - Evidence: PRD "Extract, don't ingest"; deep-recon; BMB pattern 1, Delegated Data Access.
    - **Yes.** Deep Agents' subagents plus filesystem are built for exactly this.

24. **Addendum split.** Depth that doesn't belong in the deliverable (rejected alternatives, technical how) is captured to `addendum.md` *during* the conversation.
    - Evidence: `S/bmad-prd/SKILL.md` File roles.
    - **Adapted.** Keep artifacts lean and keep the "why we didn't" next to them.

25. **Artifact delegation at wrap-up.** Each requested artifact is generated by a fresh subagent whose *only* source is the memlog. The subagent returns just the file path.
    - Why: keeps heavy generation out of the bloated main thread and proves the memlog is canonical.
    - Evidence: `S/bmad-brainstorming/references/finalize.md`.
    - **Yes.** It is also a cheap test of whether your memory captured enough.

26. **Template-output checkpoints (A/C/P/Y).** After each section: save to file, show it, then offer `[a]` Advanced Elicitation, `[c]` Continue, `[p]` Party, `[y]` YOLO (stop asking and finish).
    - Evidence: `S/bmad-cis-design-thinking/SKILL.md` "Behavioral Constraints".
    - **Adapted.** Keep save-then-show and YOLO, the human's escape hatch from ceremony. A checkpoint after *every* section is too much for a copilot; checkpoint per phase instead.

27. **Energy checkpoints.** "How is your energy for prototyping?" placed between demanding phases.
    - Evidence: `<energy-checkpoint>` in the CIS workflows.
    - **No** as a ritual. **Yes** as a principle: offer a natural pause and resume point between long phases.

28. **Help router with a catalog CSV.** Columns: phase, preceded-by, followed-by, required, outputs. Completion is detected by finding output files on disk, and the router offers to run the next skill.
    - Evidence: `S/bmad-help/SKILL.md`, `B/_config/bmad-help.csv`.
    - **Yes.** A QMX "What next?" that reads the workspace (data loaded? strategy backtested? walk-forward done?) and suggests the next skill. Soft sequencing plus a few hard `required` gates.

29. **Catalog-serving scripts.** `pick_methods.py` and `brain.py` serve slices of large CSV libraries (categories, list, show, random --spread), so a 100-row library never enters context.
    - Evidence: `S/bmad-advanced-elicitation/scripts/pick_methods.py`, `S/bmad-brainstorming/scripts/brain.py`.
    - **Yes.** Use the same approach for QMX's block, indicator and template catalogs.

30. **Scripts own determinism.** Python stdlib with PEP 723 and `uv run`, with an LLM fallback when scripts can't run. "If a script contains conditional logic that determines what content means, intelligence has leaked."
    - Evidence: bmad-builder-docs …/explanation/scripts-in-skills/, …/skill-authoring-best-practices/.
    - **Yes.**

31. **Immutable rendered snapshots.** All variables resolved, hash-addressed, with a manifest of inputs.
    - Evidence: `B/scripts/render_skill.py`, `B/render/.../manifest.json`.
    - **Adapted.** Version user-built workflows the same way: a run records the exact resolved definition and hash it executed. That is needed for reproducibility of research results.

32. **Shims for deprecated skills.** Old names forward to new skills with "forwarded activation" (pre-resolved fields honored verbatim).
    - Evidence: `B/bmm/v6-shims/README.md`, `S/bmad-review/SKILL.md` step 1.
    - **Yes,** for user-built skills that get renamed or merged. Never break a saved automation.

33. **Agent memory "sanctum"** (BMB memory agents). PERSONA, CREED, BOND, MEMORY (about 200 lines, curated), CAPABILITIES, INDEX. "First Breath" onboarding calibrates the agent. Raw session logs are curated into MEMORY and pruned after 14 days. PULSE handles autonomous wake-ups.
    - Evidence: bmad-builder-docs …/explanation/agent-memory-and-personalization/.
    - **Adapted.** The two-tier memory (raw logs → curated ≤200-line memory, with curation done on autonomous wake-ups) suits the Copilot's user memory. Skip PERSONA/BOND theater.

34. **Evals for skills.** Artifact evals (output plus transcript grading) and trigger evals (does the description fire on the right queries).
    - Evidence: bmad-builder-docs …/explanation/what-are-evals/.
    - **Yes,** especially trigger evals for user-built skills, since a description that never fires is a dead skill.

## C. CIS (Creative Intelligence Suite) deep-dive

**Purpose.** CIS covers "the fuzzy front-end" of work: framing problems, ideation and narrative (CIS README, github.com/bmad-code-org/bmad-module-creative-intelligence-suite).

**Agents.** Six persona agents, each a thin skill with a menu that points to a workflow (`S/bmad-cis-agent-*/`; voices in `B/config.toml` `[agents.*]`):
- Carson (brainstorming; Osborn and improv "yes-and")
- Maya (design thinking; IDEO and Norman)
- Dr. Quinn (problem solving; TRIZ and systems thinking)
- Victor (innovation; Christensen and Blue Ocean)
- Sophia (storytelling; McKee and Campbell)
- Caravaggio (presentations; Duarte)

Core's `bmad-brainstorming` is the flagship facilitation skill; Carson just fronts it.

**Shared workflow shape** (design-thinking, problem-solving, innovation-strategy, storytelling). All four are single-file "Simple/Complex Workflow" skills with:
- an XML-ish `<workflow><step n goal>` body;
- a method catalog CSV;
- a `template.md` with `{{placeholders}}`;
- `<template-output>` markers after each step, where the work is saved and shown, then the [a]/[c]/[p]/[y] menu appears;
- `<energy-checkpoint>` between heavy phases;
- `on_complete` resolved at the end.

The output is one dated markdown doc in `{output_folder}`.

**Design thinking** (`S/bmad-cis-design-thinking/`):
- Seven steps: challenge statement → Empathize → Define (POV "[user] needs [need] because [insight]", How-Might-We) → Ideate (15–30 ideas, defer judgment, pick 2–3) → Prototype (lo-fi; "what can you fake vs build") → Test (5–7 users, observe what users do over what they say) → Next iteration.
- `design-methods.csv` has 30 methods across 6 phases: empathize, define, ideate, prototype, test, implement. Examples: Shadowing, Journey Mapping, Jobs to be Done, Crazy 8s, Provotype Sketching, Wizard of Oz, Feedback Capture Grid, Service Blueprinting.
- The facilitator picks 3–5 methods that fit the context and recommends rather than dumping them all.
- Rule: "never give time estimates".

**Problem solving** (`S/bmad-cis-problem-solving/`):
- Nine steps: define and refine → diagnose and bound (Is/Is-Not) → root cause → forces and constraints → generate solutions → evaluate and select → plan → monitoring and adjustment triggers → lessons learned (optional).
- `solving-methods.csv` has 30 methods in 6 categories:
  - diagnosis: Five Whys, Fishbone, Systems Thinking
  - analysis: Force Field, Pareto, Constraint ID, FMEA
  - synthesis: TRIZ matrix, Morphological, Synectics, Biomimicry
  - evaluation: Decision Matrix, Risk Matrix, Pilot protocol
  - implementation: PDCA, Stakeholder map, Monitoring dashboard
  - creative: Assumption Busting, Reverse Brainstorming, Six Hats
- QMX relevance: high. "Why did my strategy's live P&L diverge from the backtest?" is exactly a diagnose → root cause → adjustment-triggers flow.

**Innovation strategy** (`S/bmad-cis-innovation-strategy/`):
- Steps: strategic context → market landscape → current business model → disruption vectors / unmet jobs / whitespace → initiatives → strategic options → roadmap.
- `innovation-frameworks.csv` has 30 frameworks across disruption, business model, market analysis, strategic, value chain and technology. Each row carries `key_questions` (pipe-separated), so the facilitator asks the framework's own questions.
- QMX relevance: low for the Copilot. The `key_questions` column pattern is worth copying, though.

**Storytelling** (`S/bmad-cis-storytelling/`):
- Steps: purpose / audience / key messages → framework choice → element gathering (Socratic: "draw out their story… unless they explicitly request you to write it").
- `story-types.csv` has 25 types: transformation, strategic, persuasive, analytical (data-story, insight-narrative, research-story), and emotional.
- Each type has `key_elements` that become the question script.
- QMX relevance: the **data-story / insight-narrative** types fit "turn this backtest into a one-page investment memo".

**Brainstorming** (core, `S/bmad-brainstorming/`), the most refined facilitation design:
- **Framing held all run:**
  - Aim past 100 ideas and resist concluding.
  - Shift the creative domain every 5–10 turns.
  - **One prompt per message, no multiple-choice menus** while generating. Menus "invite lazy picking". The only exceptions are the two process choices: stance and techniques.
- **Composer page:** `assets/brain-selector.html` is a local HTML page where the user composes stance plus techniques and pastes back a prompt. The UI does the selection so the chat stays generative. QMX can do this natively in its UI.
- **Library:** 108 techniques, `brain-methods.csv`, with category, description, provenance (classic/signature/playful), `good_for` and audience. Categories include collaborative, creative, deep, structured, wild and more.
  - Flows: as-given, `invent N` (the AI invents new techniques, keepers can be saved to `additional_techniques`), and `you choose N` (favorites first).
- **Divergence and convergence are kept strictly separate.** `references/converge.md` picks *one* fitting move (Affinity Clustering, Impact–Effort, NUF test, Forced Ranking, PMI, MoSCoW). In Facilitator mode the AI structures and the user judges. "Two or three moves chained is fine; more is over-processing."
- **Wrap-up:**
  1. "Hand them the mirror first": reflect *their* odd and buried ideas back and let them connect.
  2. Then add the non-obvious connections they'd miss.
  3. Set the memlog to complete even if no artifact is wanted.
  4. Artifacts are opt-in, except in autonomous mode: an imaginative self-contained HTML keepsake ("no template on purpose"), a lean `brainstorm-intent.md` built for downstream skills, and other forms on offer. Each is generated by a subagent from the memlog alone.
- **Outputs:** `{output_folder}/brainstorming/brainstorm-{slug}-{date}/` containing `.memlog.md`, `brainstorm.html` and `brainstorm-intent.md`.

**What makes CIS good** (the intent behind it):
1. Method catalogs are *data*, not prompt text, so they're swappable, extensible and served in slices.
2. The facilitator's job is to make the human think, and the stance makes that contract explicit.
3. Every session ends in a machine-consumable intent artifact, so creativity flows into planning.

**What to drop:**
- the persona theater (jazz-musician Maya, bard Sophia);
- per-section menus;
- energy checks as ritual.

## D. BMB (BMad Builder) deep-dive: how users author agents, workflows and modules

BMB is not installed in QMX. These sources are the docs (bmad-builder-docs.bmad-method.org, home plus /reference/builder-commands/, /explanation/*) and the Mintlify reference (mintlify.com/bmad-code-org/BMAD-METHOD/reference/modules/bmad-builder). Installed skills that BMB produces show the target shape.

**Three builders, each a conversational skill:**
- Agent Builder (`bmad-agent-builder`, menu BA)
- Workflow Builder (`bmad-workflow-builder`, BW)
- Module Builder (`bmad-module-builder`, IM ideate / CM create / VM validate)

Each runs **Guided**, **YOLO** (brain-dump, minimal questions) or **Autonomous** (`--headless`/`-H`). Starting input can be a rough idea, an existing skill (edit), non-BMad code (convert), or API docs.

**Build Process (BP), six phases:**
1. Discover intent. Ask naturally whether it needs memory, autonomy or evolvability.
2. Classify and set strategy.
   - Workflows: Simple Utility, Simple Workflow or Complex Workflow.
   - Agents: stateless, memory or autonomous; plus their internal commands, external skills and scripts.
3. Gather requirements: name, stages, config variables, dependencies. Agents add identity, capabilities and "folder dominion" (what they may touch).
4. Draft and refine the outline with the user until it is ready.
5. Build: generate the folder, then **deterministic lint gates** (path standards, script portability).
6. Summary, plus an offer of **Quality Optimize**.

**Quality Optimize (QO)** runs three tiers:
- Tier 1: deterministic lint.
- Tier 2: metric pre-pass (structure, prompts, dependencies).
- Tier 3: parallel LLM scanners for structure, prompt craft, execution efficiency, cohesion and enhancement opportunities.
- Output is a severity-ranked report, then fix / checklist / discuss, or JSON when headless.

**Convert (CW)** rebuilds a foreign skill headless from its *intent* and emits an HTML before/after report with token deltas, "What changed" (bloat removed, reorganized, aligned with best practice) and "What survived".

**Output shapes:**
- **Workflow:** `SKILL.md` (lean router) + `prompts/` (stage files, for complex workflows) + `resources/` + `agents/` (subagent prompts) + `scripts/` + `templates/`.
- **Stateless agent:** `SKILL.md` + `references/` (one prompt per capability) + `scripts/` + `assets/`.
- **Memory / autonomous agent:** a lean bootloader SKILL.md + sanctum seed templates + `init-sanctum.py` / `wake.py` (+ `PULSE-template.md`). Memory lives in the **project**, not the skill: "skills are reusable; memory is the relationship".
- **Module:** `module.yaml` (shared config, committed) + `module-help.csv` (capability registry feeding bmad-help) + a **setup skill** that registers everything in one step for multi-skill modules (standalone modules self-register). Distributed as a Claude plugin with a `.claude-plugin/marketplace.json` from any git host. "Expansion" modules extend another module but degrade gracefully if it is absent.

**Authoring principles** (…/skill-authoring-best-practices/, …/scripts-in-skills/, …/subagent-patterns/):
- **Outcome-driven over prescriptive.** The test is "would the agent decide better with this information?" Keep rationale ("the why"), cut padding.
- **Description = 5–8 word summary + "Use when user says X or Y"**, with conservative triggering. The installed descriptions follow this exactly.
- **Intelligence placement.** Scripts do plumbing (validate, count, parse, diff); prompts do judgment. No regex classification of meaning.
- **One level of references.** No A→B→C chains, no vague file names, consistent terms, and graceful fallback when scripts can't run.
- **Six subagent patterns** (summarized in the sketch below).
- **Make it customizable** (…/how-to/make-a-skill-customizable/): ship a `customize.toml` that declares the override surface. Authors choose what is tunable: scalars, appendable lists, keyed menus.
- **Evals** (…/what-are-evals/): artifact plus trigger evals, run by the eval runner, before publishing and after model upgrades.

**What QMX can copy for user-built workflows and mini apps.** The Copilot plays the role of BMB:

1. **A Builder mode with BMB's six phases**: intent → classify → requirements → outline-and-refine → build-and-lint → summary-and-optimize. Classification becomes:
   - **Utility**: a single block or function. A deterministic, testable, headless-only Python node.
   - **Workflow**: a linear DAG of steps with user checkpoints.
   - **Complex workflow**: routing, branches and stages.
   - **Mini app**: a UI plus workflow(s) plus state.
   - **Agent**: when it needs memory or a schedule ("autonomous" means a scheduled PULSE-style job).
2. **Ask the BMB questions** that matter for safety and reuse:
   - Does it need memory across runs?
   - Does it run unattended?
   - What may it touch ("folder dominion" becomes data scopes, broker scopes, compute budget)?
   - Which parts must be deterministic code?
3. **Generated package shape**, one folder per user skill:
   - `SKILL.md` (description plus router)
   - `customize.toml` (exposed knobs: the user-editable parameters, matching the operator rule that configurable means UI-editable)
   - `scripts/` (deterministic nodes)
   - `references/` (stage prompts)
   - `assets/` (templates, UI)
   - `evals/`
   - a registry row (phase, preceded-by, followed-by, outputs), so the "What next?" router knows about it.
4. **A deterministic lint gate before save**, e.g. no unbound variables, no live-order call outside an "Ask First" boundary, pinned data sources, declared outputs. Then an optional LLM **Quality Optimize** pass that returns a tiered report.
5. **Convert**: import a user's notebook or script and rebuild it as a native QMX workflow from its intent, with a before/after report. This is a strong onboarding path for quants who bring existing code.
6. **Module = shareable bundle**: workflows plus mini apps plus a config schema plus a setup step, installable by other users, with expansion modules that degrade gracefully.
7. **Snapshot on run.** Use `render_skill.py`-style hash-addressed rendering so every research result points at the exact workflow definition that produced it.
8. **Trigger evals for user skills.** Users write 5–10 example requests and the Copilot checks the description fires. This catches dead skills before they rot.

Sketch of the six subagent patterns:

| Pattern | QMX use |
|---|---|
| Delegated data access | per-symbol research |
| Temp-file assembly | per-asset backtests written to files, then an assembler |
| Shared-file pipeline | stages that build on each other |
| Lead-worker | a planner writes the breakdown, workers execute it |
| Persona parallel reasoning | review panels |
| Evolutionary | parameter or strategy search with an evaluator |

## E. Ranked patterns to borrow, and patterns to avoid

**Borrow (ranked by value to a day-to-day quant copilot):**
1. **Append-only task memlog plus "nothing exists until it is a file".** Long tasks survive crashes, compaction and model swaps, and deliverables are regenerated from the log by a fresh subagent. (`B/scripts/memlog.py`, deep-recon "How you work")
2. **Resume-first activation.** Find unfinished runs by frontmatter status and run identity, and offer resume or fresh. (brainstorming step 5; TEA step-01)
3. **Frozen approved intent with Always / Ask-First / Never boundaries.** Autonomy inside the box, a human interrupt at the edge, and a review-loop cap of 5 before escalating. (spec-template, step-04)
4. **Stance / working-mode choice made up front**: do-it-for-me / pair / coach, plus a headless JSON contract with `assumptions[]` for scheduler and agent calls. Contradictory modes live in quarantined files. (brainstorming modes, headless.md; PRD Fast/Coaching)
5. **Three-layer customization with shape-based merge, plus a "Tune this skill" meta-mode** that shows a diff and asks before writing. (resolve_customization.py, bmad-customize)
6. **Declarative lifecycle hooks**: prepend, append, persistent_facts, on_complete, external_handoffs. Real hooks in code, user-editable as lists, degrading gracefully. (all customize.toml)
7. **Deterministic-then-semantic quality gate.** Lint scripts first, then parallel context-free lenses with one findings schema and no reviewer severity. The parent triages to intent_gap / bad_spec / patch / defer / reject, and the UI shows tiered findings. (bmad-review, reviewer-gate.md, step-04)
8. **"Pressure-test this" elicitation menu.** 5 fitting methods from a quant-specific catalog served by a script, with reshuffle, and never applying without a yes. (bmad-advanced-elicitation)
9. **Concern-ordered walkthrough of what the agent built**: an entry point first, clickable stops, peripherals last. (checkpoint-preview, bmad-build step-05)
10. **Catalog router** ("What next?") driven by a registry with soft sequencing and output detection on disk. (bmad-help)
11. **Stakes calibration** that scales rigor and gate depth (look / paper / live). (PRD Discovery)
12. **BMB-style Builder mode** for user workflows and mini apps: six phases, classification, lint, optimize, convert, module packaging, trigger evals. (section D)
13. **Extract-don't-ingest subagent research** and the six orchestration patterns. (PRD, BMB subagent-patterns)
14. **Divergence/convergence separation and "mirror first" synthesis** for ideation sessions. (brainstorming converge.md, finalize.md)
15. **Hash-addressed snapshots** of executed definitions for reproducibility. (render_skill.py)

**Avoid (ceremony and overkill for a copilot):**
- **Many named personas with theatrical voices** (bards, jazz musicians, emoji prefixes on every message). Fun in a planning room, noise in a trading tool. One Copilot voice with modes is enough. Use personas only inside on-demand review panels.
- **Party mode as a default conversation style**, with grudges, callbacks, fourth-wall fiction and HTML keepsakes. It is expensive and slow. Keep only independent parallel reviewers.
- **Step files for everything.** "NEVER load multiple step files", "NEVER skip". Reserve this for money-path compliance flows; BMB itself says to use the lowest level of disclosure needed.
- **A checkpoint menu after every section** ([a]/[c]/[p]/[y] after each `<template-output>`) and ritual energy checks. Checkpoint per phase, keep a YOLO escape hatch, and otherwise flow.
- **Heavy upstream interrogation.** Even the BMAD PRD warns that users "must not be held hostage by upstream probing": two or three turns to a working mode.
- **Long phase pipelines with document hand-offs** (brief → PRD → UX → architecture → epics → stories → sprint status). That is project planning, not daily copilot work. QMX itself already treats BMAD as planning-only.
- **Mandatory artifact generation.** BMAD makes artifacts opt-in in interactive modes because each is "a fresh, token-expensive generation". Copy that restraint.
- **Inconsistent state rules.** The memlog's "no lifecycle status" contradicts brainstorming's `status: complete`. Choose one model and apply it everywhere.
- **Installer and render machinery** (manifests, v6 shims, IDE-specific installs) beyond what QMX's own plugin system needs. Borrow the ideas (registry, forwarding, snapshots), not the installer.

# QMN configured producer and frontier diagnosis

**Scope:** source and governing-document diagnosis only. No runtime implementation, credentials, provider calls, or trading effects were used.

## Finding

The repository has a checked deployment preflight and a post-seal hosted-root API, but it does not have an installed producer that turns the checked deployment into the configured runtime resources and an ongoing decision frontier. The ordinary systemd unit does not set `QMN_DEPLOYMENT_CONFIG`; the supervisor reads only that environment variable. Even when an operator supplies it externally, the default installed path has no `hosted_resources_for` callback, persists a hosted-resource stand-down, and keeps readiness at 503. A test-injected resource callback can get as far as opening a sealed `HostedDecisionRoot`, after which the supervisor explicitly reports that the decision loop is unavailable.

The repository's runnable recorded-day path is TN-21 diagnostic replay in a separate process. It imports a `RecordedDay` from the one-way sealed archive, reuses reduced recorded signal-snapshot markers, produces an empty-intent diagnostic handler, never submits or fills, and writes a replay terminal record. It does not drive the configured live/paper `HostedDecisionRoot`, and its output is not authority for activation or current Book state.

## Governing constraints

- The ratified NODE spine TN-2 says the root composes one resolved node configuration, allocates writers, then fingerprints and seals. TN-3 locates the sole live session and canonical feed in the one QMN process. TN-5 describes the source path: the venue edge pushes inbound observations to the single first-writer accumulator; a synchronous per-stream driver calls QMB `run_slice`. TN-8/TN-19 require a frontier-bound governed `SignalSnapshot`, used by Book and KSA, with `decision_freshness_bound` and SQS readiness. TN-21 explicitly runs replay outside the node process and as a decision diff without submit or fill. See `_bmad-output/planning-artifacts/architecture/architecture-NODE-2026-08-28/ARCHITECTURE-SPINE.md` and [`docs/components/trading-node.md`](../../docs/components/trading-node.md).
- The ratified CONNECT spine and CT-20 require the adapter to record actual inbound venue evidence before interpretation. Position/balance read-backs are observations; adapters do not synthesize them. Reconciliation needs a declared lookback and complete actual read-back. See `_bmad-output/planning-artifacts/architecture/architecture-CONNECT-2026-09-11/ARCHITECTURE-SPINE.md` and [`docs/contracts/ct-20-venue-event.yaml`](../../docs/contracts/ct-20-venue-event.yaml).
- `docs/AGENTS.md` says the corpus is design authority, not implementation or live-operation authority; implementation comes through the factory pipeline. It also names `qmn.venue` as the sole importer/wirer of `qmf-venue`; all other QMN modules receive the port and CT-19/CT-20 values.

This diagnosis does not read or open any credential. Presence checks and live connection/read-back remain runtime gates.

## Minimum implementation seam for a recorded-input composition

The smallest truthful provider-free proof can use a named, immutable recorded-input fixture with the existing conformance `VenueClientPort`, exact registered CT references, explicit active CT-24 evidence fixture, actual QMF stores, and a fresh `VpsClock` test double. It must label that source as a fixture. It should exercise the same installed supervisor composition function, not manually construct a `HostedDecisionRoot` in the test. The flow is:

1. Install/configuration supplies one operator-pinned deployment document path under the canonical tree. Wire that path through the rendered systemd service; the current template has no setting for `QMN_DEPLOYMENT_CONFIG`.
2. A fixed, explicitly registered host composition function consumes `ConfiguredRuntimeAssessment` plus current boot/journal resources and resolves seat admission from the exact CT-33, Book/BMS definitions, CT-28 binding and active CT-24 evidence. It verifies the seat candidate and Book/BMS identities against those checked references, creates CT-13-backed reservation/decision/KSA projections and the exact OrderPath, then returns `ConfiguredHostedResources`. No package scanning, guessed defaults, caller-supplied executable callbacks, or client-selected provider identities.
3. The root owns a per-`(VenueId, account)` source driver. A recorded fixture yields timestamped CT-10/CT-20-shaped evidence through the same `RecordingAccumulator` first-writer boundary. The accumulator records and journals before values become foldable; a recorded frontier closes through the existing `CommandStreamLoop`/QMB `run_slice` path. At that frontier, configured MIS producers create one governed `SignalSnapshot` with the exact environment, feed state, SQS reading/marker, and Book `decision_freshness_bound`; Book and KSA consume that same object at its exact instant.
4. The installed supervisor retains the returned `SealedHostedRuntime` and drives the synchronous frontier source on its one node event loop. Any missing or stale snapshot, store/readback refusal, KSA restriction, cancellation, or resource mismatch persists a typed stand-down/refusal and never advances readiness. QMB replay remains a different-process diagnostic workflow.

The first acceptance fixture should have one declared stream, at least two recorded frontiers, an actual `SignalSnapshot` positive path through `HostedDecisionRoot.run_slice`, a no-entry control for a non-ready/missing SQS observation, a stale/future snapshot refusal, wrong binding/as-of identity refusal, and durable CT-13 reopen checks. It proves the composition and call chain only; it does not prove native venue connectivity.

## Native approval and read-back boundary

CT-20 position/balance read-back must be actual adapter observations, journaled before interpretation. Neither the recorded-day replay model nor the conformance fixture is native evidence. Production connection requires the operator-pinned live roster kind, the deployed proto descriptor, systemd-held credential references, cTrader session/capability verification, and actual orders/positions/balance read-back within the declared lookback. Missing credentials, missing/changed descriptor, unverified capabilities, missing native identities, ambiguous/netted attribution, and unknown command outcomes must keep the configured process alive in durable stand-down or UNKNOWN according to their existing lifecycle; none can be replaced by a fixture result or inferred from a CT-13 reference.

No credential or provider was accessed for this diagnosis. Consequently it establishes the code/documentation seam, not deployment readiness, live connectivity, or real read-back.

## Next bounded patch boundaries

1. Implement the explicit deployment-file installation/selection path: config authoring and validation must remain DevOps tooling, and the unit's pinned file reference must be readable below `QMX_ROOT` without becoming a trading command or hot reload.
2. Implement the fixed registered hosted-resource resolver against the existing assessment, CT-13/registry readers, and typed QMN factories. Preserve preflight → compose → fingerprint → seal order and current stand-down behavior. Add exact-identity negatives before sequencer opening.
3. Implement the per-stream frontier source bridge using the already existing `VenueClientPort` → `RecordingAccumulator` → `CommandStreamLoop` → QMB `run_slice` APIs and existing MIS snapshot producers. Prove it with persisted recorded fixture input through the supervisor composition path.
4. Keep actual external cTrader session approval, native CT-20 read-back and complete reconciliation as a separate deployment proof. The local source seam is implementable without calling a provider; production readiness is not established by it.

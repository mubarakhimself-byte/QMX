Every probe chat, HP0's and HP1's, runs under `common.Lockdown`. The chats run as the operator's own Windows account, where Credential Manager holds `qmx/openrouter` and the `qmx/*` broker keys, so before this a third-party model with `bypassPermissions` and the full tool set could have read them, the ship home's login and the repo. Each probe now names what its chat may run. The CLI gets only those built-in tools (`--tools`), and a PreToolUse hook denies every other call and every Bash command that is not exactly one the probe expects, such as `echo hp1-b1-marker`. `plan_options` classifies all 49 fields of the pinned SDK 0.2.166 `ClaudeAgentOptions` in `common.OPTION_RULES`. The lockdown sets 9 of them (`tools`, `allowed_tools`, `cwd`, `permission_mode`, `can_use_tool`, `add_dirs`, `setting_sources`, `plugins`, `strict_mcp_config`). A probe may set 14 of them, each through a per-field value check. The other 26 are refused, and so is any name outside the table. `test_every_sdk_option_is_locked_checked_or_refused` reads the field list from the probe venv's SDK, so an SDK upgrade that adds a field fails it until the field is classified. The CLI runs a call whose hook raised, so a raising guard or probe SDK hook returns a deny instead. A probe's own PreToolUse SDK callback (`hooks=`) may delay or deny a call, and any other output from it, such as an allow or an `updatedInput` with or without a decision, becomes a deny. Probe hooks may sit only on `PreToolUse` and `Stop`, so a `PermissionRequest` hook, which could also change a tool's input, is refused. Command hooks from settings files and plugins run in the CLI, outside that wrapper, and one that prints an allow with an `updatedInput` rewrites an allowed command (verify3 case F1). So a probe's inline `settings` may carry only `forceLoginMethod` (`claudeai`) and `cleanupPeriodDays`, and its `extra_args` only `append-system-prompt-file` with a file under `D:/Temp/qma-hp0`. `sandbox` is refused, because the SDK merges it into `--settings`.

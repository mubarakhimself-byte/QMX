# UI handoff: everything the UI session needs (running list)

> **The UI is a design, not code (operator, 2026-10-16 and 2026-10-18).** The UI has been designed and drafted, not engineered; its code will change a lot. The intent lives in the design: what each screen shows, the click-throughs with demo data, the storyboard. Read the UI as a design (run it, look at it, click through it), never take requirements from its component code or types alone.
>
> **The demo design is not final either.** Many backend capabilities were added after it was drawn. The UI session should propose redesigns where a better representation exists, and should leave some capabilities without a screen of their own when a status update, badge or line in an existing view is enough. Not everything in this list needs its own surface.

Started 2026-10-16 by the lead session, at the operator's request (ruling 47). It is kept up to date as each design lands; last brought current on 2026-10-28 against the code on `build/br4` at `1e9f695a` (PRs 207 to 228 on top of `engine/base`: sections 19 to 26 below); before that on 2026-10-22 against rulings 1-134 (the data round, §17 below; earlier: 2026-10-18 against rulings 1-118), the rerun (39 with its review and fix-check applied) the unlock pass (`research/methodology/43-whole-app-unlocked.md`, §14 below) and the studies-folded pass (`research/methodology/47-studies-folded.md`, §15 below). **Read this before wiring anything.** `UI-NOTES.md` still holds the harness event details. ## 0. Ground rules for the UI session

- QMX is a **desktop application**. The browser is only the design-time host (rulings 32, 40). Never design for a web version.
- Build with **demo mode OFF**, so unwired places say "Not connected" instead of showing sample data [10 §6.17].
- **The UI is a design, not a coded product.** Its code exists only to show the design. Backend requirements come from the screens' intent (screenshots), never from the UI code or its types.
- Demo data shows the intended shape. Don't treat its specifics as the backend contract [ruling J/UI].
- Node 22 is pinned, but the machine has Node 24. `pnpm dev` hangs, so start Vite directly [10, 23].
- Treat `BACKEND-REQUIREMENTS.md` and `handoff/MINI-APPS-AND-COPILOT-CONTRACT.md` in the UI repo as history. The real door is REST + SSE (`/api/chats`, `/api/sessions/{id}/turns`, `/live`, `/api/approvals/{id}`, `/api/usage`, `/export`) [10 §6.15].

## 1. Fix before wiring the harness (QMA v2, exists today)

1. **Block renames:** `tools→tool`, `changes→changed`, `cards→entity`, `ask→question`. Add a `needs_you` renderer. Decide whether `tool` is one call or a batch [10 §6.1].
2. **Session home:** show a home badge. A session keeps its birth home. "Open in hub" must not rewrite the home, and there must be a way back to the Lab. Replace the one-way `absorb()` [10 §6.2-6.3, 23, ruling 12]. **The backend field is now designed (engine AD-35, moved by the unlock pass):** `home: {kind: general | lab | portfolio | library | app, project_id}` is sent **in the body of `POST /api/chats`** and stored on the chat at birth; there is no separate `PUT .../home` call (that design was dropped before it was built). `GET /api/chats` returns it. Child chats inherit the parent's home; a chat created with no home reads as `general`. Every screen can open and continue any session through the same session id and turn routes; "open in its home" is the way back.
3. **Chat status words** (chat turns, not runs): add `failed`, `cancelled`, `expired` [10 §6.4]. Run statuses are a different set (§9 row 8) and have no `cancelled`.
4. **Approvals:** the backend has four **decisions**: `allow_once`, `allow_always` (not offered when a QMX tool asks), `reject` (with a message) and `answers` (the reply to an AskUserQuestion). An answer returns `resolved | already_answered | expired | invalid | unknown`. There is no `reject_once` or `reject_always`, and "for this errand" doesn't exist. Add "expired, re-run from here" [`QH/routes.py:180-205`, `QH/chat.py:230-253` on hp17, 27b F11; 10 §6.5, 20b].
5. **Sub-agents:** show start, end and result only today. Live progress arrives with the harness turn events, `delegate` v2 and the router's per-agent journal rows (engine AD-53; HARNESS-REQUESTS H1, H26, H36; §12 row 1) [10 §6.6].
6. **Harness features missing in the UI:** effort control, compaction events, stop/interrupt/steer, the model-switch cost warning, a usage page, Export per session [10 §6.12, UI-NOTES]. "Compact now": H15 was granted and built in HG1 (ruling 89, PR #92), so per-chat compaction exists for Background and Child chats; wire the button only to what that backend exposes for the chat kind on screen (fixed after 41 L1) [27b F14].
7. **Terminal:** label it read-only. It is not a shell [10 §6.13].
8. **Output:** add a Markdown renderer and diagram parts in the panel catalog. These are pure UI work [10, 19].

## 3. Coming with the workflow engine (`architecture/workflow-engine/`)

- **A Workflows screen** is needed. Today workflows have no screen of their own [23 §3]. It needs a list, versions, enable/disable, triggers, and runs.
- **One draft, two views:** the Lab editor's Graph mode and Code mode are projections of ONE draft. The saved Board is a draft. Free-form note nodes and unconnected nodes are allowed in a draft [engine AD-11].
- **Lifecycle states to show:** draft → validated → tested → published (version) → enabled ⇄ disabled → archived. A draft can only run in test mode. Selected-subgraph runs ("run just this part") are allowed [engine AD-11]. Drafts never sit on `main`; see §9 for the draft vs published badge.
- **Test runs use real models**: haiku through his plan login by default; OpenRouter only to prove another provider works (ruling 105). Show each test report and its cost. Saving a draft and running a test never ask him; publishing and enabling ask once.
- **Run timeline:** one trace per run and one span per step (status, cost, time, account, model). Steps that waited at a provider's own usage limit show `waiting (resume_at)` [engine §observability].
- **Inbox items:** one per problem, with buttons: retry, stronger model, skip step, open trace, stop, resume. Long-pause alert after 6 h (editable) [engine §failure ladder]. Only provider failures and harness-level errors reach the inbox; everything else is a digest line (§9 row 9).
- **Account pool settings:** see §12 row 5 (the Accounts page). Any number of Claude, GPT and key accounts, configured per account in the UI; QMX imposes no share, ceiling or budget of its own (ruling 106). He may set an optional per-account share or ceiling himself on the Accounts page (ruling 90); it is off by default and never set by QMX. The default strategy for workflows is least-used, never fill-first. OpenRouter is marked "provider proof only" [engine AD-12, rerun].
- **Defaults are all UI-editable.** The list is in `SOLUTION-DESIGN.md` §17.
- **Copilot builder:** the copilot asks numbered questions with suggested answers, then draws the draft on the canvas.
- **Templates:** a template is a copyable workflow. A variant is an overlay with a "variant of" link (ruling 48).
- Node kinds the palette needs: trigger, script, rule, loop, join (all/any/quorum), wait, human gate, llm, agent, sub-workflow, grader, monitor, app op, library. (`claude_workflow` is retired, engine AD-5.)

- **Nothing waits for him during a run** except an irreversible outside effect, which goes to the inbox while the run waits (`waiting`) [engine AD-16, AD-17]. Publishing or enabling a workflow asks once. Self-improvement shows "challenger vs champion" with automatic rollback [engine AD-26].
- **Where it ran:** each run card shows its placement by registry name (`pc`, `contabo`, `qmb`, or a provider row such as an Amp runner or orb, E2B, Modal, or a managed agent host like Cloudroom or Amp threads), its `agent_mode` (`runner_outside | cli_inside | host_harness`), its isolation only when he chose one (`container` or a remote placement; `local` is the default and needs no badge), and the run's `mode` badge (`live | test`) [engine AD-24/25, AD-32]. *(2026-10-28: no `contabo` or other server row ships any more. Places are This PC plus the names he gives; what each run records is §20.)*

## 4. Coming with the Library (`architecture/library-and-data/`)

- **One Library holds everything** (ruling 28). The kinds are data: each is a schema file with a class (record, definition or governed), so shelves are generated from the schemas and the UI never hard-codes a count. A bot's card is its preview, its logic is its code tab, a board is a workflow draft in board view, a template is a tag, and hypotheses ("Ideas") are a kind [library AD-3, §15].
- **Previews and detail tabs are driven by schema data.** Render them from each kind's schema, not hand-built per shelf [library AD-17].
- **Links are typed,** from a closed list (CT-07's 14 relations plus 24 Library ones; one of the 24, `ran-on`, is retired, because where a run ran is now a field on the run). Show "Used in", "Produced by", "Tested by", "Variant of" and so on as real links between items, not links to screens [library AD-4, 23 §1].
- **Versions and branches:** `main` is the trusted version and holds published versions only. His drafts sit on `refs/drafts/<item>`; agents work on their own branches. A merge conflict is an object with a side-by-side diff view [library AD-7].
- **Archive, never delete.** There is no Remove button; there is Archive with a reason [library AD-6, ruling 9].
- **Search:** text search plus the links map. Answers cite items. A "nothing found" refusal comes before any model runs [library AD-8].
- **No asks on Library writes** from workflows (ruling 57). The UI shows what landed; it doesn't gate it.
- The Library may live on his server later (ruling 56). The UI must tolerate a remote home: loading states, offline cards.

- **A "landed" feed, not a gate:** workflow results and the items workflows produce fast-forward into `main` under a per-workflow standing rule (`publish auto|hold`, default auto); new workflows, apps, pods and skills a run made arrive as drafts instead. The UI shows what landed and never gates it [library AD-18]. A copilot-chat merge of governed kinds (units, bots) or lifecycle kinds (workflows, apps, pods) into `main` asks once [library AD-9].
- **Library home can switch** between the PC and the server (`[library] primary`). The UI never knows which store answered [library AD-19].
- **New kinds to render:** `dataset` cards (every result shows what data it consumed), `memory-row`, `agent-tool` (marked unreviewed), `book`/`bms` (compiled from a pod), `model` with versions [library LLD §3].

## 6. Mini apps

- **Archive, never delete** (ruling 9). Today the UI has Remove; the backend has neither delete nor disable [10 §6.10].
- **Two mini-app data sets disagree:** Apps has 21 apps, the Library shelf has 2 with other ids [23 §5]. Use one source, the Library.
- **Per-app copilot:** the UI offers one, but the design says any copilot loads an app's pack and no app has its own copilot [10 §6.11]. The UI should drop the per-app copilot setting.
- A mini app is a plugin pack containing workflows, widgets and tools. Workflows inside it appear on the Workflows screen too.
- **A mini app is a real Claude plugin** (engine AD-55): its skills, helper agents and slash commands appear in the copilot like any plugin's; adding an app to a running chat switches its tools on at once; an app installed or updated after a chat started joins that chat at its next turn ("loads on your next message"). An app's own schedules show as workflow triggers on the Workflows screen, not on the app card (engine AD-57).

No spend ask and no QMX limit bar exist anywhere [engine AD-9, AD-16, AD-40; SD §26.3].

## 10. Operations patterns from Hermes (added 2026-10-18, study 37c)

Patterns from Hermes Agent's TUI, desktop app and dashboard that make many runs and agents readable. Sources in `research/methodology/37c-hermes-operations.md`.

1. **Live work dock** above the copilot composer: running sub-agents and workflow runs started from this chat, with name, elapsed time and latest activity; expand to a roster. Steer and Stop where the backend allows. Steer says "queued for the next checkpoint", not "read". Sub-agents still show start, end and result only until the harness emits progress (§1 item 5) [37c §12].
2. **Queued messages panel:** a message typed while the agent works shows as `queued` and can be cancelled before it starts [37c §12; harness queue].
3. **Context meter with breakdown:** % full, and a popover by category (system text, tools, skills, memory snapshot, MCP, conversation). Optional cache hit rate and tokens per second, off by default [37c §12; harness usage].
4. **Failure card names the layer:** provider, key, relay, stream, harness, engine, disk. Actions match the layer: Retry (hidden when it would fail the same way), **Retry when the limit resets at HH:mm** with a countdown and Cancel (nothing retries after he closes the window), Switch model [37c §12; error class set, 37c §7] *(new backend: closed error classes)*.
5. **"Why didn't it fire?" panel** on each trigger: ticker heartbeat age, version enabled, next fire, last 10 fires with status and reason (`silent`, `merged`, `blocked config`, `held until HH:mm`, `skipped`), open incident. The copilot answers the same question from the same read [37c §4] *(new backend: `service.explain_trigger`)*.
6. **Trigger list columns:** name, schedule in words plus the cron text, state badge, delivery, last fire (status + delivery outcome), next fire, Run now. "Passed" and "delivered" are separate badges [37c §1] *(new backend: delivery field)*.
7. **Incidents, not repeats:** one row per trigger and error signature with a count and first/last seen; Acknowledge keeps it quiet until the error changes; a passing run marks it resolved [37c §1] *(new backend: trigger incidents)*.
8. **Engine health badge** in the status bar and on the Machines list: Running, Degraded (with reason), Heartbeat stale ("looks running but nothing is scheduled"), Old code ("restart to load the update"), Safe mode (after a restart loop) [37c §1, §7] *(new backend: heartbeat row, code stamp)*.
9. **Resource banner:** only the most severe active warning (disk critical > memory critical > unexpected restart > disk low > memory low); dismissal lasts until the next engine boot [37c §7].
10. **"Last run" diff scope:** for a workflow or copilot that changed files or Library items, a view of exactly what its latest run or turn changed [37c §12; Library run branch].
11. **Pop-out a run or chat** into its own window without the sidebar, for a second monitor; live output streams into every window showing it [37c §12].
12. **Simple mode:** a chat-first layout switch that hides the status bar, rails and terminal; it changes what is shown, not what QMX can do [37c §12].
13. **Approvals:** keep the four decisions (§1 item 4). Add a visible badge whenever any auto-approve mode is on for a session, in the status bar and on session start [37c §12].
14. **Machines list:** each machine has a device name; the same agent or workflow on two machines shows as `name@machine` [37c §12].
15. **Settings, persona:** one short text box for the copilots' tone and defaults, with the "which file does what" help card beside it [37c §13] *(new backend: persona item)*.
16. **Logs page:** filter by component (engine, scheduler, relay, harness, apps) and level, live tail; analytics by day and by model (tokens, cache hit, cost estimate) [37c §12].
17. **Phone (later, ruling 34):** inbox actions as buttons with a timeout and a numbered-text fallback; one status message edited in place per run [37c §10].

## 14. The unlock pass (added 2026-10-18, ruling 118, `research/methodology/43-whole-app-unlocked.md`)

## 19. First start, install and the handover to the desktop app (added 2026-10-28, PRs 209, 210, 214, 219, 222, 228)

Read from the code on `build/br4` at `1e9f695a`; the code wins over the plans (`LOOSE-STRINGS-PLAN.md` Appendix E is the exit-code contract, `BACKUP-RESTORE-PLAN.md` Appendix E the restore contract). These are the backend's routes and lines; the card's look is the design's.

1. **Two programs, one port.** Before any QMX folder exists the desktop app runs the card: `python -m qmx_host first-start --serve --port <p> --ui-origin <origin>`. Once a folder is chosen it runs the host: `python -m qmx_host serve --home <folder> --port <p> --ui-origin <origin>`. Both use the same port (default `8766`; the default UI origin is `http://127.0.0.1:5173`), so the UI keeps one base URL. The card binds the loopback only, needs no bearer and allows `GET` and `POST` from the UI origin. Every host route needs the bearer, which the desktop app reads from the keyring entry `qmx/control-token` (it exists only after the host's first start, so the desktop app polls until it does). The UI never asks the host for it.
2. **Telling them apart.** `GET /api/first-start` answering 200 with no bearer means the card is up; only the card does that. `GET /api/health` answering `{status: "ok", pid}` with the bearer means the host is up.
3. **Exit codes the desktop app can trust** (`serve`, `start`, `status`, `stop`):
   - `0`: served and stopped cleanly (`start`: the host answers health).
   - `1`: one line on stderr: a host already runs on the folder, the place name is bad, or (`start`) the host did not become ready in 30 seconds (`status`: the recorded host does not answer).
   - `2`: one line on stderr, `QMX did not start: <why>`: a folder found and refused, a store refused (each store's line is printed above it), the engine or the Library refused to open, a mini app did not start, a staged restore that cannot finish, or bad arguments. Show the line, then offer the card, which offers restore.
   - `3`: a first start is due: no QMX folder yet, only his old data at `~/.qmx`, or an unfinished bring-in (`serve` and `start` also for a folder whose restore did not finish). Start the card.
   - `4`: the port is in use. Pick another port or stop what holds it.
   - `start` runs `serve` in the background and returns its child's code; the child's last line is repeated on stderr and kept in `logs/host.log`.
4. **The card's own exit codes** (`first-start --serve`): `0` after a handover, with the last stdout line `{"handover": {"folder": "<folder>", "port": <p>}}`; `1` when it stopped with no folder handed over; `2` bad arguments; `4` the port is in use.
5. **What the card offers.** `GET /api/first-start` answers `found` (a QMX folder this PC already has, so no first start is needed), `default` (the suggested new folder), `drives` (`[{drive, free}]`, free in bytes, `-1` when unreadable), `old` (his old folder when one is there to bring in), `choices` (in order; the first is also `chosen`), `unfinished` (`{folder, line}` of a bring-in that did not finish), `refused` (`{folder, line}` of a folder QMX found and refuses, or whose store it refuses), `restore_unfinished` (`{folder, line}` of a restore into a new folder that did not finish), `warning` (a removable drive), `second_drive` (`{path, line}`, the drive QMX would propose for a daily copy), `running` (the folder of the job that runs, or null) and `job` (the newest job's view, or null). While a job runs the offer is the one that stood when the job started; the folder of that job is left out of `unfinished` and `restore_unfinished`.
6. **The choices.** Fresh PC with old data: `bring-in`, `new`, `open`, `restore`. Fresh PC without: `new`, `open`, `restore`. A refused folder: `open`, `restore` only (his data may sit there, so never "new"). An unfinished restore: `restore`, `open`. An unfinished bring-in: `bring-in` (again, into the same folder), `open`, `restore`. A found folder: `open`.
7. **Routes.** `POST /api/first-start/new` and `/open` (body `{folder}`) answer `{folder, warning}`. `POST /api/first-start/bring-in` (body `{folder, old?, again?}`; `again: true` only for the folder where it did not finish) answers 202 with the job. `POST /api/first-start/copies` (body `{source}`) answers `{where, copies}`. `POST /api/first-start/restore/check` (body `{folder, source, copy}`) answers what the copy replaces. `POST /api/first-start/restore` (body `{folder, source, copy, confirmed, replace}`) answers 202 with the job. `GET /api/first-start/jobs/{job_id}` reads a job. `POST /api/first-start/handover` hands the folder over.
8. **Refusals the card shows.** A refusal answers 409 with `detail`, one line. QMX refuses by name, before it writes anything, a folder inside Windows' app folders (`AppData\Roaming`, `AppData\Local`), inside QMX's own program folder or checkout, a network folder or drive, a drive's root, and a folder a sync client syncs live (OneDrive, Dropbox, Google Drive, and any client Windows lists). Each line reads "`<folder>` is inside `<where>`, where a QMX folder never goes: `<why>`. Pick another folder". A removable drive is allowed with the warning "`<drive>` is a removable drive: QMX stops working whenever it is unplugged". Bringing the same old folder into a second folder is refused ("open that folder instead of copying it again"). One job at a time: a second bring-in or restore while one runs answers 409 naming the running job; a bring-in from the command line in another process makes the card answer 409 too.
9. **A job.** `{id, kind, state, step, done, total, progress, line, result}`. `kind` is `bring-in` or `restore`. `state` is `running`, then `finished` with `result`, or `stopped` with `line` (one plain line, never a traceback). `step` is the line to show now; `done` of `total` counts inside that step. Jobs live while the card runs; a reloaded card finds the newest one in `GET /api/first-start`. A job id the card no longer knows answers 404 with "read GET /api/first-start for the latest one".
10. **The loading sequence of the bring-in** (`step`, in order): "listing your old folder" (total = files in the old folder; `progress.files_hashed` counts), "copying" (`files_copied`, `bytes_copied` of `bytes_total`), "checking the copy", "moving your Library into the new one" (only when his old Library needs moving; `versions_switched` of `versions_total`), "opening the new folder's stores". `progress` also carries `files_total`. A finished job's `result` is `{finished, folder, report, facts}`, `report` being the report's lines (counts of what came in, items made by test runs counted on their own line and archived, each store's line). A stopped bring-in carries the same `result` when it got that far; its `line` says why (a file that changed while copied is named). The old folder is only ever read.
11. **The loading sequence of a restore** (`step`, in order): "checking the copy", "placing the copy's files", "checking the copy's stores"; then the card puts the copy in place, with no step line of its own, and the job ends. `done` and `total` stay 0 for a restore. A finished job's `result` is `{folder, copy, where, aside, line}`; `aside` is where the folder's own data was set aside whole (`backups/before-restore-<id>/`).
12. **Restore from the card.** A `source` today is `{kind: "folder", path, home_id?}`: the folder he names, or a folder's own place in it; `home_id` is needed only when that place holds copies of several QMX folders (the 409 line lists them). The copies answer gives each copy's `stamp` (the date, as `20261028T030000123456Z`), `why` (such as `round` or `before-upgrade`), `files`, `bytes`, `release`, `machine`, `home_id`, `folder`, `partial` and `lacks`, newest first. The check answers `{folder, copy, new, newer, partial, lacks, other_home, line}`; `newer` counts `runs`, `ref_moves`, `chats` and `price_months` newer than the copy; show `line` before he confirms. Only JSON `true` in `confirmed` restores (anything else answers 400, "nothing was changed"). `replace: true` is needed for another QMX folder's copy into a folder that holds data. A host serving the folder is refused ("QMX is running on `<folder>` (PID n); close it, then restore"). A copy taken before an upgrade adds: install the older QMX first to stay on those stores. A new folder made for a restore is marked until the restore ends, and the card offers the restore again if it was killed.
13. **The handover.** `POST /api/first-start/handover` answers `{folder, port}` for the folder of this card's own last finished choice, then the card stops within 3 seconds and exits 0 with the handover line. Before any finished choice, after an unfinished bring-in, or while a job runs, it answers 409 with the line. Twice answers the same folder. Then the desktop app starts `serve --home <folder>` on the same port and the UI polls `/api/health`.
14. **The folder itself.** A fresh QMX folder holds its label `qmx-home.toml` and five parts: `data`, `keys`, `backups`, `cache`, `logs`. QMX finds it in this order: `--home`, `QMX_HOME`, the pointer `%APPDATA%\QMX\home.toml` (which also keeps a recent list), the default folder, then each fixed drive's `QMX\qmx-home.toml`. Nothing makes a folder by itself.
15. **How refusals read across the backend** (by router): the card, `/api/backups/*` and `/api/templates/install*` answer `{"detail": "<line>"}`; the control routes (`/api/settings/*`, `/api/workflows/*`, `/api/workflow-runs/*`, `/api/triggers/*`, `/api/library/*` and the rest) answer `{"error": {"code", "message"}}`; the cTrader sign-in answers `{"detail": {"code", "message"}}`; the price door answers `{"detail": {refused, retryability, context}}` (and `line` when the door is shut, §21 row 4). A malformed body answers FastAPI's own 422.

## 20. Places (This PC and servers) and where each run ran (added 2026-10-28, PRs 208, 211, 212)

1. **The place list** is This PC (`pc`, always first and the default of every choice) plus every name he gives a `placement.<name>.*` row in `[engine]` (`GET` and `PUT /api/settings/engine`). No server row ships. A row's `placement.<name>.id` is its stable id, so a rename keeps its history.
2. **Where work goes.** A node's `runs_on` names a place or a list in preference order (default `pc`); a name not in the list is refused at validate as `placement_unknown` ("the place is not in the place list"), and an empty slot as `place_unset` ("name the place this node runs on"). A trigger's `place` (in the `POST /api/triggers` body) names the place whose engine fires it; This PC when left out, `triggers.webhook_home` for a webhook. A trigger homed on a removed place reads `blocked_config` with "the place '`<id>`' was removed" until it is listed again.
3. **Where a run ran.** Every attempt records `place`, `place_id`, `machine` (the device name) and `placed_by` (`default`, `chosen`, `spilled` or `stand_in`). The run's summary (its `workflow-run` Library object) carries `placement: {place, place_id, machine, placed_by, line}`, where `line` is what the run card says, such as "ran on pc, by default" ("as chosen", "spilled over", "standing in"). Each span from `GET /api/ops/spans/{run_id}` carries `placement`. `GET /api/workflow-runs/{run_id}` does not carry it yet (gap, §26).
4. **A server's place name** comes from setup (`--place`, or `[engine] host_name`); a server host with neither refuses to start (exit 1). This PC is always `pc`.
5. **Nothing goes to a server by default.** A host started with no settings opens no connection to any address but a model provider; every default names This PC. A cTrader connection's home is `pc` unless he names another place (§23).

## 21. Store versions and the one-line refusals (added 2026-10-28, PRs 213, 222)

1. **Every store has a version.** The stores, by the words the lines use: Library, price data, run ledger, inbox, control store, run index, mini-app catalogue, portfolio store, chats, settings, Library catalogue (an index: rebuilt, never refused). At each `serve`: the same version opens; an older store is copied first, then upgraded (`serve` also takes one quick copy of the whole folder tagged `before-upgrade`); a newer store this QMX can still read opens as it is; a newer store it cannot read is refused by name, and the host exits 2.
2. **The Library and the price data are the exceptions:** too new, they open read-only instead of refusing. Each write is then refused with the reason: "`<act>` refused: the Library opened read-only. `<line>`", and on the price door "the price data is read-only: `<line>`". A settings write to a folder whose settings are too new answers 409 `settings_too_new`.
3. **The refusal line** names the store, the version it was written as, the version this QMX reads and the QMX it needs, then the way back: "Install that QMX, or restore a copy from before the upgrade, with Restore from a backup on the start screen or `python -m qmx_host restore --home <folder> --from <folder>\backups\quick`". A file that is not QMX's, or a damaged one, is named and left as it is.
4. **A shut price door.** When the price door cannot open, every `/api/data/*` call answers 503 with `detail: {refused, retryability, context, line}`, `line` saying in plain words what is wrong and what to do. Before this it answered 404.
5. **Where the lines reach the screen today:** the exit-2 line on stderr (and `logs/host.log`), `refused.line` on the card, the bring-in report, and each refused write. No route says up front that a store opened read-only (gap, §26).

## 22. Runs and templates (added 2026-10-28, PRs 207, 216, 217, 218, 220, 223)

1. **Inputs from the screen.** `POST /api/workflows/{workflow_id}/run` takes the run's inputs as its body (an empty body runs with none). A live start checks them against the workflow's `inputs` schema; a test run is never checked. A refusal answers 422 `inputs_invalid` with one line: "the input '`<name>`' is missing, and the workflow needs it. Set it, then try again." or "the input '`<field>`' is not valid: `<why>`. Give it a value the workflow's inputs accept." A workflow whose `inputs` is not a valid JSON Schema answers 409 `inputs_schema_invalid`. The engine's own keys (`trigger`, `continuity`, `webhook`, `upstream`, `precheck`) are never checked.
2. **Inputs from a trigger.** A trigger stores inputs: set in the `POST /api/triggers` body (`inputs`), edited with `PUT /api/triggers/{trigger_id}/inputs`. A `cron`, `interval` or `manual` trigger must hold every required input; a `webhook`, `event`, `after` or `session` trigger may leave them out, since its data arrives with each fire (a webhook's body stays at `webhook.body`). An installed template's trigger whose workflow needs an input is refused at `POST /api/triggers/{trigger_id}/enable` by name until he sets it: that is an ask for a value, not a lock. A fire whose stored inputs fail (for example after a newer version changed the schema) settles `blocked_config` with a line naming the trigger and the field.
3. **Crashed runs that resume.** A run whose engine died mid-attempt reads `interrupted` ("the engine stopped with an attempt in flight"). `POST /api/workflow-runs/{run_id}/resume` resumes it, and its results now land even when it died before its first summary. A resume is refused with `resume_refused` while the run is still going or once it ended. Runs held with a wake time (a usage limit, a wait, a retry backoff) resume by themselves.
4. **Test runs kept out of search.** A test or fake run's artifacts (all but its trace) and its memory rows, and memory rows made only from them, are archived "made by a test run" or "made by a fake run": kept, but out of search, recall and every duplicate check. A fake run lands nothing. A failed live run's records stay visible, since they are his. A test run still lands its definitions on their drafts. Templates read and write his real Library, never a hidden copy.
5. **Imported old runs.** An old run whose mode was never recorded reads `unknown` and, like a test run, lands nothing on `main`. Old Library items that only test runs made come in archived with "made by test runs".
6. **Template install is a job.** `POST /api/templates/install` (body `{templates}`, a list of ids; left out installs the whole catalogue) answers 202 with the job view. `GET /api/templates/install/{job_id}` reads it: `step` ("installing `<id>`", then "all templates done"), `done` of `total`, and each finished row under `result.rows` as `{id, folder, action, detail}`, `action` being `published`, `saved draft`, `unchanged`, `test failed` or `invalid`. A failing test is a `test failed` row in a `finished` job. An unknown id answers 404 before any job starts. A second install while one runs answers 409 naming it. A job that hits a refusal ends `stopped`, its line naming the template, with the rows finished before it. A job id from before a host restart answers 404 ("run the install again"). A rerun is safe: finished templates read `unchanged`.
7. **Price data opens by default** (PR 207). The holdout is his choice per study and off unless `[data] holdout = true`; then `holdout_boundary` is the month it starts (`YYYY-MM`, 1970-01 or later) and `holdout_months` the window a new study takes (12 by default). Read and write it with `GET` and `PUT /api/settings/data`. §17 rows 2 and 12 (sealed months) apply only while it is on.

## 24. Backups as built so far (added 2026-10-28, PRs 225, 226, 227, 228)

**Backup is being redesigned as "sync to my account":** one switch, he chooses what is saved, and any storage he connects. The backup screens should wait for that design. The routes and settings below are today's contract only, so the first start's restore (§19) and the doctor row can be read correctly; do not design Settings, Data and backups around them.

1. **What runs.** The host looks every minute. The quick undo (a copy inside the folder at `backups/quick`) is made hourly and has no off switch. Each place he names gets a copy on its own schedule. A place that refused or was missing is tried again an hour later. Nothing is written outside the QMX folder until he names a place or accepts the proposed second drive. Secret files are never in a copy.
2. **Every setting under `[backup]`** (read with `GET /api/settings/backup`, which returns the section as stored with no defaults filled in; saved whole with `PUT /api/settings/backup`; the host picks a change up within a minute):
   - `[backup.quick_undo]`: `hours` (48) and `days` (7), how many of the newest hours and days keep a copy.
   - `[[backup.targets]]`, one row per place: `id` (letters, digits, `-`, `_`), `kind` (`folder`, the only kind today), `path` (a full folder path, not inside the QMX folder), `every` (`hour`, `day` or `week`; default `day`), `at` (local time `HH:MM`; default `03:00`; a PC that was off copies at its next start), `keep` (`{daily, weekly, monthly}`; default 14, 8, 12), `on` (default true). Copies go to `<path>\QMX-backup\<home_id>\`.
   - `leave_out`: paths inside `data/` left out of every copy, such as `exports/**`.
   - `[backup.drill]`: `every` (`week` or `month`; default `month`) and `sample` (200 files). Saved, but nothing runs the drill yet.
   - `[backup.keys]`: saved for the sealed key copy, which is not built.
   - The keys `remote`, `bucket`, `node`, `interval_seconds`, `enabled` and `repository` belong to the mini apps' volume backup and the weekly snapshot (`/api/backup/weekly`, `/api/apps/{app_id}/backup`, `/api/apps/{app_id}/restore`), not to this program.
   - A bad row is refused on save with 400 `invalid_backup_settings`, the line naming the row and what to fix (for example "backup place 'usb': at must be a time such as 03:00").
   - The free room a machine keeps on its drive is `[engine] disk.floor_gb` (a twentieth of the free space measured at start when unset).
3. **Routes under `/api/backups`** (all behind the bearer; a refusal answers `{"detail": "<line>"}`, 409 unless noted):
   - `GET /api/backups`: `folder`, `running` (the round's job or null), `refused` (a line when the folder is not a QMX folder or `[backup]` cannot be read; then `places` is empty), `line` (the "no copy on another drive" line when he named no place), `proposal` (`{path, line}` of the proposed second drive, or null), `quick_undo_bytes`, and `places`: the quick undo first, then each place, each `{id, where, every, path, at, on, same_drive, last, newest_complete, concern}`. `last` is `{at, result, line, stamp, partial}`, `result` being `copied`, `unchanged`, `refused` or `skipped`. `same_drive` true means the place does not survive the disk. `concern` is the line when the place needs him.
   - `GET /api/backups/targets/{target_id}/copies`: each copy, oldest first, `{stamp, readable, why, files, bytes, release, machine, partial}`, or `{stamp, readable: false, line}` for a damaged one. `quick` names the quick undo. An unknown place answers 404.
   - `POST /api/backups/run` (body `{target}` optional: only that place, due or not): 202 with a `backup` job. A round already running answers 409 saying who started it; so does a round from the command line.
   - `GET /api/backups/jobs/{job_id}`: the job. Its `step` lines, in order: "stores", "library logs", "files", "price months", "files written once", then "sending the copy to `<path>`" per place. A finished job's `result` is the round: `{kind, stamp, why, result, seconds, bytes, places}`, each place with its `id`, `where`, `result`, `line`, `stamp`, `files` and `bytes`.
   - `POST /api/backups/targets/default/accept`: his yes to the proposed second drive; writes one `second-drive` row (daily at 03:00) and answers `{target, line}`. Refused when he already named a place, or no drive fits.
   - `POST /api/backups/targets/{target_id}/carry-on`: his choice to keep sending to a place the guard refused (it holds another QMX folder's copies); answers `{line}`.
4. **The doctor row.** `GET /api/doctor` carries a `backups` line (`{name, ok, detail}`): for the quick undo and each place, "newest whole copy from `<age>` ago" or "no whole copy yet", the quick undo's size, and "and it needs you: `<line>`" where one does. It is `ok` only when he named a place and none needs him.
5. **Inbox incidents.** One open incident per place that needs him, under the trigger `backup:<place id>` (`backup:quick` for the quick undo, `backup:settings` when `[backup]` cannot be read), with the signature `refused`, `partial` or `away` (a disk missing for seven of its intervals) and the title "Backups: the backup place `<id>` needs you". The next whole copy there resolves it; a place removed from Settings has its incident resolved. These sit in the inbox's incidents, which `GET /api/inbox` does not list (gap, §26); `concern` on `GET /api/backups` carries the same line.
6. **Restore** is only from the first-start card (§19 rows 11 and 12) and the command line: `python -m qmx_host restore --home <folder> --from <backup place> [--copy <date>] [--yes] [--replace] [--create]`, which lists without `--copy`, shows what the copy replaces and changes nothing without `--yes`, and exits 0 (listed, shown or restored), 1 (a host serves the folder) or 2 (refused). `python -m qmx_host backup [--target <id>]` runs one round in the foreground and exits 0 or 1.
7. **Not built:** restore from Settings, cancel, the pause after a restore and its carry-on (`/api/backups/restore/*` in the plan), the drill on a schedule, copies off-site through rclone (a `source` of kind `rclone`), and the passphrase for the sealed key copy (`/api/backups/passphrase*`, `/api/first-start/keys`). After a restore today nothing pauses server sync or schedules.

## 25. Monitoring (added 2026-10-28, PR 208)

1. **One setting, `[telemetry] send_to`,** decides where this machine's monitoring goes, for every sender: each chat's Claude Code program, the engine's exporter and Hindsight's tracing. `off` (the default, also when unset) sends nothing. `this-pc` sends to OpenObserve on this machine's loopback (`http://127.0.0.1:5080/api/default`). A place name sends to that place's collector over the tailnet (`http://<place>:4318`). No sender holds an address of its own. What a chat sends carries no prompt text.
2. **Read and save** with `GET` and `PUT /api/settings/telemetry`. A chat reads it at each launch; the engine and Hindsight read it once when the host starts, so a change reaches them at the next start.
3. **The control the screens lack:** the design has no place to set it. Its screen is Settings, Developer, "Deep logs" (design 62), with three choices: off, On this PC, On a server.
4. **Not built:** QMX does not yet download and run OpenObserve on This PC (local-first phase LF10), so `this-pc` reaches a viewer only if one runs there. The save does not check the value: a wrong one is stored, and every sender logs one warning and sends nothing (gap, §26).

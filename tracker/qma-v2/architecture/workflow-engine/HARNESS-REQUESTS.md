# Harness requests

The engine uses only the names exported by `qma/harness/__init__.py` on `qma/hp17` [retrieved]. The account pool is the one sanctioned extension (ruling 39) and is designed in `SOLUTION-DESIGN.md` section 7, not requested here. Everything below is a request for the operator to grant or refuse; the engine has a fallback for each, so none blocks the first build.

| Id | Request (smallest form) | Why the engine needs it | Fallback if refused |
| --- | --- | --- | --- |
| H1 | Export `Harness.wait_turn(sid) -> TurnEnded` (the existing internal `Chat.next_end()`), or make `live()` yield a terminal item. | The engine must know when a Background turn ended and read its result; `live()` yields deltas only and never signals the end [retrieved chat.py:889-897]. | Poll `GET /api/chats/{sid}` for `turn: idle` and read the last `text` block from `ControlService` sessions; slower and racy on long turns. |
| H2 | `NewChat` gains optional `output_format` (JSON schema), `tools` (allow-list) and `max_turns` for Background and Child chats, passed through to the SDK options the harness already builds. | `llm` and `agent` nodes need schema-checked JSON, a tool allow-list per node and a per-node turn cap; today `max_turns` is one global `[budgets]` value [retrieved launch.py:176-188]. | The engine validates the final text as JSON itself with a repair retry, states the tool list in the prompt, and relies on the global cap; weaker and costlier. |
| H3 | A relayed single request without a CLI: `Harness.complete(profile, account, messages, schema) -> text` served by the relay for key and GPT profiles only (plan excluded, so no QMX process on the plan path). | A one-turn `llm` node today costs a CLI process (170-610 MB) and the Claude Code system prompt [retrieved DESIGN "Processes and memory"]. | Keep `llm` nodes as one-turn tool-less Background chats (the bound rule, AD-13). |
| H4 | A per-chat switch for `CLAUDE_CODE_DISABLE_WORKFLOWS` on `NewChat` (plan profile only), default off. | The optional `claude_workflow` node kind launches the Claude Code Workflow tool inside one chat; the harness sets the flag to `1` for every chat [retrieved launch.py:239]. | The node kind stays unavailable; the engine's own fan-out covers Claude-only sweeps. |
| H5 | `NewChat.title` or a new `NewChat.tag` carried into `ChatRecord` and `GET /api/chats`, so a chat can be found by `run:node:attempt`. | After a crash the engine must find the chat that belongs to an attempt to resume or interrupt it. | The engine keeps its own `attempt -> session_id` table in the ledger (it does anyway); H5 only removes a second lookup. |
| H6 | `Harness.usage()` returns readings per account once the pool exists (part of the pool extension; listed so the UI contract is explicit). | Admission control and `least_used` selection read per-account windows. | None needed; this lands with the pool. |

| H7 | Per-chat sub-agent definitions and caps on `NewChat` for Background chats: `agents` (SDK `AgentDefinition`s with `model`, `tools`, `maxTurns`), `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (3-5) and `max_budget_usd`; spawn depth stays the harness default of 1. | AD-4: an agent node's helpers must be capped and budgeted per node, not per harness (ruling 52, study 29 §1.1). | The engine states helper roles in the prompt and relies on the harness's global defaults; no per-node cap. |
| H8 | A per-chat extra MCP server on `NewChat` for Background chats: the engine's **sandbox tool server** (`sandbox_bash`, `sandbox_write`, `sandbox_python`, `sandbox_tool_*`), passed through the existing `vet_mcp_servers` path and denied any money act, together with per-chat `disallowed_tools` for `Bash`, `Write`, `Edit` and `NotebookEdit` (the H2 allow-list covers the rest). | AD-25 `runner_outside`: the agent loop and credentials stay in the harness, the sandbox only executes tool calls that arrive over a remote call (Rivet principle). This is the central request of the amendment. | The fallback `cli_inside` mode: the SDK and CLI run inside the container with `qmx-egress` injecting a key-provider key; key accounts only; wider blast radius. |
| H9 | The relay reachable from the Docker network with a per-attempt grant for a non-chat caller, so `qmx-egress` in the fallback mode can be the relay's remote face instead of a second proxy. | AD-25 `cli_inside`: one key-injection path rather than two. | A separate `qmx-egress` service in `qmx_engine.workers` that reads keys by ref and injects them; the pool still picks the account. Not needed at all while every node runs `runner_outside`. |

| H10 | **Relay routing by model id** (AD-29): `resolve_model` grows from a family refusal into a model-to-provider table built from the `[providers]` rows; one chat may hold several provider grants; the pool leases per `(session, provider)`; usage is teed per provider. Part of the load-balancer exception (ruling 39). | Mixed providers inside one agent (ruling 62): main on Kimi, sub-agents on DeepSeek, judge on GLM in one process. | Engine fan-out across provider-specific agent nodes (always available, no harness change). |
| H11 | **Relay reachable on the tailnet with run-pass bearers** (AD-28): the relay listens on the tailnet address as well as loopback, accepts a signed run pass as bearer for non-chat callers (containers, provider threads), checks placement, scope, TTL, the source allow-list and the revocation list, and resolves keys from the local keyring or vault copy. Replaces H9. | One key path for every mode and placement; keys never leave the relay host. | A separate `qmx-egress` service doing the same with its own key reads (two readers per host). |
| H12 | An **OpenAI chat-completions translator lane** for `KeyProvider` rows flagged `wire: openai_chat`, reusing the shape of `qma/gpt/translate.py`. | OpenCode Go serves GLM and Kimi only in that format [retrieved `25` §5.4]; ruling 63 says the pool must take OpenCode. | Reach GLM and Kimi directly through Z.ai and Moonshot rows; OpenCode rows stay out of the candidates. |
| H13 | **Per-machine plan homes and `qmx node login`** (AD-28): a plan account row carries `machine`; the CLI's `/login` is opened on that machine once; the pool refuses a plan lease for any placement that is not an owned, signed-in machine. Part of the pool extension. | Plan work on Contabo and an owned Amp runner (rulings 55, 69) without any token leaving his machines. | Plan accounts serve the PC only; the server runs on key providers alone. |
| H14 | **Per-chat `model_scope`** on `NewChat` (the providers a Background chat may address), enforced by the relay. | A node's pass and chat must not reach providers its role table does not name. | The relay allows every configured provider for every chat; the engine logs, does not enforce. |

Not requested, on purpose: any change to the money gate, settings-in-code, the relay's egress stop, the boot scrub, the launcher, verbatim prompts, or the plugin lock. The engine lives with all of them as they are. The account pool (AD-12) is the sanctioned extension and is designed in SOLUTION-DESIGN section 7; it now also covers one pool per harness instance (PC and `qmx-node`), relay routing by model id (H10), the tailnet-reachable relay with run passes (H11) and per-machine plan homes (H13), all under ruling 39. DESIGN.md's "the relay is the only reader of provider keys at run time" is kept per host (SOLUTION-DESIGN §19).

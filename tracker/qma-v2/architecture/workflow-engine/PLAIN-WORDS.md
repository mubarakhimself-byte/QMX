# The workflow engine, in plain words

**What it is.** One machine inside QMX that runs jobs you set up once and then leave alone: "every six hours, look for new papers and write me a note", "every weekday morning, build my brief", "take this idea through the funnel and stop before paper trading". Every job is drawn as boxes and arrows on the Lab's graph canvas. A box can be a script (free, no AI), a rule, a wait, one AI call, a whole AI agent with a few helpers, a data kernel that chews through big tables, a check that grades the result, or another job. A job can also be just one agent, or no AI at all. Templates are jobs with sensible defaults; you or the copilot copy one and change it.

**How a job gets made.** You describe it roughly in chat. The copilot asks you a few numbered questions, each with a suggested answer, so "yes" is enough. It then draws the draft on the canvas. Before anything goes live, the draft is checked (do the boxes connect, is every setting there, nothing touches money) and then test-run with sample data and real, cheap models, so you see it actually works. When the test passes and you say yes once, the draft is frozen as version 1 and a schedule is switched on. Nothing is ever deleted; old versions and old runs are archived and stay in the Library.

**Where agents live.** Your Contabo server is the always-on home: the Library, the key safe, market data, monitoring, the scheduler, and a few agents kept warm. When you need more agents at once, the engine rents them from a provider (Amp, Cloudroom, Cloudflare, E2B, Modal, whichever is cheap and reliable; none is paid for yet and none is locked in). Your PC runs about three at a time. The thinking part of an agent, with its permissions and its conversation, stays in QMX on a machine you control; only the commands it wants to run go into a throw-away box that is destroyed after the step. Some providers insist on running the whole agent in their own machine; that is allowed for cheap burst work with key-based providers only, and the engine still keeps the diary and the results. Backtests never share a machine with agents: one dedicated QMB machine does them, and agents just ask it.

**Keys once, everywhere.** You type a key once in Settings on your PC. It is stored in Windows' credential store, and an encrypted copy goes to a small safe on your server. No agent and no rented machine ever receives a key. Each step gets a short-lived pass instead, good for that one run, that one machine and that one budget; a small relay on your PC or server adds the real key to each model call. Change a key in Settings and every machine uses the new one within a minute; delete it and every machine stops within a minute. If your server is unreachable, running work continues on the copies the relays already hold; nothing new starts there until it is back. If a pass were stolen, the thief could at most spend that run's remaining budget and write junk into that run's folder; never read a key, never touch your main Library, never touch money. Your Claude plan sign-in stays on the machines you own: you sign in once per machine, and it never goes to a rented one.

**Mixed models in one job.** One agent can run on Kimi while its helpers run on DeepSeek and the judge on GLM, in the same conversation; the relay sends each call to the right provider by the model's name. Any provider that speaks the Claude-style API joins by a web address and a key, no code.

**What happens when it runs.** The engine keeps a diary of every step: what started, what came out, how long it took, what it cost, and on which machine. If the computer restarts in the middle, the engine reads the diary and carries on from the first unfinished step. Finished steps are never done twice, so you never pay twice for the same AI work. Before building anything, a step first asks the Library "was this exact thing built before?" and reuses it if so.

**Nothing waits for you.** A job never stops to ask you a question while it runs. The only exception is a step that would do something outside QMX that cannot be undone, like sending a message; that one waits for an answer in your inbox. Everything else, including writing to the Library, just happens.

**When something fails.** The engine tries a few things in a fixed order, by itself: try again, use another account, use another model, then ask a cheap "doctor" AI to look at the step. If all of that fails, the run is parked and an item appears in your inbox: what broke, what was tried, what it cost, where it ran, and a link to the provider's own page for that machine. The next scheduled run starts fresh anyway.

**Watching the machines.** You do not need a fleet screen in QMX. The copilot can open each provider's own dashboard for you. QMX itself shows on every run card where the step ran, whether that machine is healthy, what it has cost, and a link out. A live picture of a desktop appears only when you open it.

**Using a desktop or a browser.** When a job needs to click around a website or a desktop app, a small driver (Cua) is loaded for that step only, with a list of what it may touch that the agent cannot widen: which apps, which websites, for how long. Broker and trading-platform windows are always off limits. Web and Linux apps run on a rented Linux desktop; Windows apps like MT5 run on your PC or on a Windows virtual machine on your server. Every click is kept as a screenshot in the run's trace.

**How it remembers and improves.** Every run notes what it learned. A nightly job proposes one small change, replays it against past failures and successes, and only an improvement that breaks nothing takes over; it rolls itself back if it does worse. You set one rule per job once; nobody asks you per change, and the version you approved by hand is never overwritten.

**Where everything is stored.** Jobs, versions, run summaries, produced files, traces, memory notes and agent-made tools all live in the one Library, on your PC now and on your server as the main copy later. The engine's own step diary, schedules and inbox live in a small database file beside QMX on each machine that runs it.

**What the copilot, the Lab canvas and the chat have in common.** They are three views of the same engine. The canvas edits the draft as a graph or as code, the copilot builds and explains, the chat shows previews and run cards. None of them has its own rules.

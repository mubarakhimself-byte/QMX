## Findings

### 1. [critical] `who=ANY` thread rows let an agent spawn or hijack a thread with a higher permission mode (self-approval by delegation)
**Location** `sketch/qmx_control/agent_ops.py:22-30` (`threads_create`, `threads_send`, `threads_steer`, `threads_interrupt`, `threads_fork`, `threads_archive` all default `Who.ANY`); `sketch/qma2/model.py:213-222` (`ThreadSpec.profile`, `origin`, `parent` are caller-supplied); `sketch/qma2/config.py:92-100` (`Profile.mode`); `sketch/qma2/policy.py:123-125` (`effective_mode` applies only to sub-agents).
**Finding** The agent catalog is derived from `who=ANY` rows, so `mcp__qmx__threads_create` and `mcp__qmx__threads_send` are agent tools. `ThreadSpec` carries `profile`, and a profile carries `mode`. Nothing caps the new thread's mode at the caller's mode, binds `parent`/`origin` to the calling thread, or scopes `threads_send`/`threads_interrupt`/`threads_archive` to threads the caller owns. An agent in `default` mode calls `threads_create(profile=<bypass profile>)`, then `threads_send` the real task there; or sends a turn into a thread the operator already put in `bypassPermissions`. `threads_interrupt` on the operator's thread expires his pending approvals. The money rule still runs on the tool surface in the new thread, so money cannot move this way, but the invariant "an agent must never raise its own permission mode" (`harness.py:184`) and "agents cannot answer approvals" are both defeated: bypass mode *is* every approval answered yes. In `default` mode the first `threads_create` asks the operator, but `suggest_rule` for MCP tools is the exact name (`policy.py:192-195`), so one "Always allow" on a benign `threads_create` makes every later one, including the bypass-profile one, silent.
**Suggestion** In `ControlAgentOps.call`, force `origin=AGENT`, `parent=<calling thread>`, and `mode = effective_mode(caller.mode, profile.mode)`; reject `threads_send/steer/interrupt/archive/fork` unless the target thread's lineage includes the caller; and never offer an ALLOW_ALWAYS rule for `mcp__qmx__threads_*`. Put this in the type: a `ThreadSpec` built by an agent should be a distinct `ChildThreadSpec` with no `profile`/`origin` fields.

### 2. [critical] Approval delivery on the Claude engine only works in `default` mode; the SDK source says so, and the sketch mirrors the mode anyway
**Location** `sketch/qma2/host/claude.py:42-43` (`permission_mode=mirror(spawn.mode)`), `:130-132` (`mirror` "always explicit"); `HARNESS.md` open question 4; pinned SDK `claude_agent_sdk/types.py:2158-2175`.
**Finding** The pinned SDK's own docstring for `can_use_tool`: it "is *not* invoked for tool calls already permitted by ... `permission_mode` (e.g. `"acceptEdits"` / `"bypassPermissions"`)" and "a `PreToolUse` hook returning an *allow* decision also skips this callback". So when QMX mirrors `acceptEdits` to the CLI, a `NeedsOperator` for an Edit (e.g. the protected-path rule, `policy.py:138`, which the design says asks "even in bypass, like Codex") is swallowed by the CLI's own mode before `can_use_tool` runs. The design treats this as a U2 probe with a fallback; the SDK source already answers it, and the fallback ("mirror only `plan`, keep other modes control-side") is the required design, not a contingency. As sketched, protected-path asks and hook `ask`s are silently auto-approved under `acceptEdits`/`bypass` on the Claude engine while the OpenAI engine asks, which breaks "identical by construction".
**Suggestion** `mirror()` returns `"default"` for everything except `plan`; `policy.decide` owns the mode semantics on both engines. Drop probe 3 of A8. Separately, define `_can_use_tool` for a `tool_use_id` with no Pending entry: it must return `PermissionResultDeny`, never fall through.

### 3. [warning] `CallOp` grant is bound to a `tool_use_id` only, not to the gated name and input
**Location** `sketch/qma2/harness.py:274` (`_granted: set[str]`), `:296-297`; `sketch/qma2/wire.py:190-198` (`CallOp.name`, `CallOp.args` supplied by the host).
**Finding** The invariant "a host cannot reach a QMX op without passing the policy point" holds only for the id. A host can `Gate(Read, {...})`, receive Allow, then `CallOp(tool_use_id, name="propose_order", args=...)` or re-send different `args` than the ones the hook or operator edited. The control side has no record of what was allowed, so it routes on the host's word. This is the one place where the "host holds only a pipe" model lets the pipe assert policy facts.
**Suggestion** `_granted: dict[str, tuple[str, digest]]` and the actor executes the op with the *stored* allowed input, ignoring `CallOp.args`; or drop `CallOp` and have the actor run QMX ops directly on Allow and return the result in the verdict for `ToolSource.QMX` calls (one fewer message, no grant table).

### 4. [warning] The host's fd 1 is only rebound at the Python level; any child or C-level write corrupts the link
**Location** `sketch/qma2/host/__main__.py:44` (`wire_out = os.fdopen(os.dup(1), "wb"); sys.stdout = sys.stderr`); `sketch/qma2/wire.py:4-5` ("nothing else in the host may write to fd 1 ... its tool subprocesses do not inherit the pipe").
**Finding** `sys.stdout = sys.stderr` rebinds Python's object; OS fd 1 is still the pipe. Every `subprocess` the OpenAI host starts without `stdout=PIPE` (a tool handler, an MCP stdio server QMX "connects itself", `AgentTool`), and any C extension `printf`, writes JSON-breaking bytes into the link. The claim that tool subprocesses "do not inherit the pipe" is a convention, not a structure.
**Suggestion** After `os.dup(1)`, `os.dup2(2, 1)` so fd 1 is stderr for the whole process tree; the wire handle is then the only route to the parent.

### 5. [warning] The single-task actor as sketched deadlocks on `Await` and head-of-line-blocks parallel gates
**Location** `sketch/qma2/harness.py:260-266` ("Mailbox-driven; one asyncio task"), `:292-294` (`Ask(Await) -> reply(await self._pending[aid])`), `:304-318` (`gate` awaits hooks).
**Finding** If `on_up` runs inline in the mailbox task, `Ask(Await)` parks the task on a Future that only `resolve()` (another mailbox message) can set: deadlock. Even without that, `Ask(Gate)` awaits `policy.evaluate`, which runs hook subprocesses (up to 60 s each); Claude issues read-only tool calls in parallel, so the second Gate, `TurnEnded`, `Usage` and `Interrupt` all wait behind the first hook. The "sole writer" property is about state mutation, not about serialising every await.
**Suggestion** Spawn one task per `Ask`; keep the actor loop for state transitions only, with the Future resolution and `_granted` mutation done on the loop thread. Say this in the harness docstring, because the current text invites the deadlock.

### 6. [warning] Hook-timeout budgets nest the wrong way on the Claude engine
**Location** `sketch/qma2/host/claude.py:109-119` (`_pre_tool_use` awaits `link.gate`); `sketch/qma2/hooks.py:139` (`timeout_s` per handler); pinned SDK `types.py:616-618` (`HookMatcher` timeout "default: 60").
**Finding** The in-code PreToolUse callback must return within the SDK matcher timeout (60 s). Inside it, QMX runs the operator's own command hooks (Claude default 60 s each, run in parallel) plus two money checks, a Writer group-commit and a pipe round trip. A single slow hook makes the SDK time the callback out; a timed-out hook is a non-blocking error in Claude's contract, so the CLI proceeds to the normal permission flow and, with no rules and `default` mode, calls `can_use_tool` for an id that has no Pending row. The sketch does not define that case (see finding 2); as written it is a path where a hook that was supposed to deny times out into an operator prompt or, worse, an unhandled branch.
**Suggestion** Set the SDK matcher timeout above the sum of QMX hook budgets (or make QMX hook timeouts a function of it), and make the unmapped `can_use_tool` case a hard deny with a `tool.finished(denied, source=LIMIT)` event.

### 7. [warning] `BearerGate` is global ASGI middleware; the cookie-authenticated operator routes and `/console` are 401 before `resolve_principal` runs
**Location** `sketch/qmx_control/server_changes.py:57-61` ("BearerGate keeps its role ... the console's same-origin calls carry the cookie instead"); real code `qmx_control/server.py:93-117`, `:238` (`app.add_middleware(BearerGate, token=token)`).
**Finding** `BearerGate.__call__` rejects every `http` scope without a valid bearer. `GET /console`, `POST /api/operator/pair`, the OAuth callback and every `who=OPERATOR` row called with only the cookie are blocked. Either the console also holds the bearer (which collapses the two principals back into one and lets any token holder be the operator) or BearerGate gains a path allow-list that the sketch does not specify.
**Suggestion** Replace `BearerGate` with `resolve_principal` as the one dependency: bearer → CLIENT, cookie → OPERATOR, else 401; mount MCP behind the bearer only. Delete the middleware rather than carving exceptions into it.

### 8. [warning] "Tool processes get `tool_env`, which carries no keys" is false on the Claude engine, and the U1 live check cannot run as scoped
**Location** `HARNESS.md` tension 1 ("Tool and hook processes get `tool_env`"); `sketch/qma2/secrets.py:17-18`; `units.md` U1 live check ("env dump inside a Bash tool call shows no `ANTHROPIC_*` or `QMX_*`"), U1 scope ("deny the rest").
**Finding** On the Claude engine, Bash children are spawned by the CLI from the CLI's env, which is `host_env`: it contains `CLAUDE_CONFIG_DIR`, i.e. the path of `claude-home/.credentials.json`. `MoneySurface.credential_paths` covers that file for Read/Bash pattern matches only (speed bump); `python -c open(...)` reads the operator's claude.ai session token, which is the exact thing the terms say QMX may not "intermediate". This matches vanilla Claude Code, but the design text claims otherwise. Separately, the U1 stub gate denies Bash, so U1's own env-dump check cannot execute until U2.
**Suggestion** Reword tension 1 to "on the OpenAI engine"; move the env-dump check to U2; add `redact` coverage for the claude-home credential file's contents (exact-match against the file) so a leaked token cannot land in items, blocks or exports, which is what A6 actually needs.

### 9. [warning] `PLATFORM_BASICS` is missing variables Windows shells need
**Location** `sketch/qma2/secrets.py:48-54`.
**Finding** The allow-list omits `SYSTEMDRIVE`, `PROGRAMFILES`, `PROGRAMDATA`, `ALLUSERSPROFILE`, `USERNAME`, `COMPUTERNAME`, `NUMBER_OF_PROCESSORS`, `PROCESSOR_ARCHITECTURE` and, importantly, `PSMODULEPATH` (all present in this laptop's environment). Without `PSMODULEPATH` the `PowerShell` tool's module autoload fails; without `PROGRAMFILES`/`SYSTEMDRIVE` git-bash and many installers misbehave. The host-side Claude CLI and every tool inherit this list.
**Suggestion** Add them, and make the allow-list per-OS (a Windows set and a POSIX set) rather than one union.

### 10. [warning] Job Object assignment order is unstated; a child created before assignment escapes the kill-tree
**Location** `sketch/qma2/harness.py:245-248` (`_HostSupervisor`), `sketch/qma2/host/__main__.py:46-47`.
**Finding** `subprocess.Popen` on Windows starts the child running; job membership is inherited at process creation, so anything the host spawns before `AssignProcessToJobObject` returns is outside the job. The host spawns the CLI only after reading `Spawn` from stdin, which gives a natural barrier, but the sketch never says "assign to job, then write `Spawn`". If a builder writes `Spawn` in the same call that creates the process, the CLI and its tool tree can survive `kill()`.
**Suggestion** Document and test the ordering: create host → assign job → write `Spawn`. The U1 live check "kill one host, the other keeps streaming" should also assert that the killed host's CLI pid is gone.

### 11. [warning] The 50% background cap is computed from a number the Claude engine never reports
**Location** `sketch/qma2/router.py:52-56`; `sketch/qma2/model.py:505-507` ("Claude emits these only on change"); H1 fact 10; `HARNESS.md` A9, open question 7.
**Finding** `pick` drops the Claude subscription when `five_hour.utilization >= 0.50`. The only source of `utilization` is `RateLimitEvent`, which fires on *status* change (allowed → allowed_warning → rejected). Between 0% and the warning threshold the stored utilization is whatever the last status change said, possibly hours old or absent. The router cannot tell 10% from 49%, so the cap is unenforceable until `get_usage` (Q7) is proven; U5's "done when" (a background chat above the cap runs on OpenRouter) cannot be shown. Also, `pick` runs only at turn boundaries, so a background turn that starts at 49% runs to completion past the cap.
**Suggestion** Either make Q7 a U5 prerequisite probe with a stated fallback (background threads use Claude only while status is exactly `allowed` and the last event is younger than N minutes), or drop the percentage from the UI text until it is real.

### 12. [warning] On Windows the two engines expose different shell tool names, so "rules and hook matchers written once" breaks
**Location** `sketch/qma2/host/tools.py:7` ("Bash (POSIX) / PowerShell (Windows)"); `HARNESS.md` A1 ("The kit uses Claude's tool names, so one table serves both"); call site 4 (`"matcher": "Bash"`).
**Finding** Claude Code on Windows exposes both `Bash` (git-bash) and `PowerShell`. The OpenAI kit exposes only `PowerShell` on Windows. A `deny: Bash(git push *)` rule or a `PreToolUse` matcher `Bash` written for the Claude engine matches nothing on the OpenAI engine on this laptop; `git push` goes through `PowerShell` unmatched. `BUILTIN_EFFECTS` also needs rows for `PowerShell`, `apply_patch`, `AskUser`, which are not Claude names, contradicting A1's "one table".
**Suggestion** Ship both shell tools in the kit on Windows (Bash via git-bash when present), and have `matches_rule` treat `Bash`/`PowerShell` as one `shell` family for rule and matcher purposes, with `shell_split` choosing the grammar.

### 13. [warning] Crash recovery "re-projects" into an append-only store with no idempotency key: duplicate or missing blocks
**Location** `HARNESS.md` tradeoffs ("two-file write (row first, then block); recovery re-projects"); `sketch/qma2/harness.py:73-75` (`Sink.block` has no key); real `qmx_control/service.py:324-335` (`sessions_append` computes `MAX(seq)+1`).
**Finding** Items in harness.db are idempotent on `(thread, source_key)`; blocks in control.db are not. After a crash between the harness.db commit and `sessions_append`, recovery cannot know whether the block landed, and the item→block seq mapping is not stored. Re-projecting duplicates blocks; not re-projecting loses them.
**Suggestion** Store the block's `seq` on the item row after `sessions_append` returns, and re-project only items with `block_seq IS NULL`; or put the item's `source_key` into the block content and have `ControlSink.block` skip when the last block for the session carries the same key. Also note the stated rationale for the separate file ("a second writer connection on control.db would recreate the WAL-bug precondition") is already false today: `ControlService` opens a fresh connection per call from the FastAPI thread pool and the maintenance thread; the real reason is ownership and migration, and the doc should say that.

### 14. [warning] Claude-engine MCP servers are not pinned to the Spawn set; a repo `.mcp.json` can claim the reserved `qmx` namespace
**Location** `sketch/qma2/host/claude.py:49` (`mcp_servers={..., "qmx": ...}` with no `strict_mcp_config`); `sketch/qma2/config.py:87` ("`qmx` is reserved; the loader refuses it"); old recipe `native_claude.py:262` (`strict_mcp_config=True`); H1 fact 3 (`~/.claude.json` still loads with `setting_sources=[]`).
**Finding** The loader refuses the name only in files QMX reads. The CLI also reads the project's `.mcp.json` and `claude-home/.claude.json`. A repo-supplied server named `qmx` yields tools named `mcp__qmx__*`; `source_of()` maps them to `ToolSource.QMX`, and for `propose_order` `catalog.spec()` returns the real `ProposalToolSpec`, so the call is classified `Proposal` (money-exempt) while the CLI executes it against the repo's server. The design's identity check is sound only if the CLI's tool list equals the catalog.
**Suggestion** Pass `strict_mcp_config=True` (the old recipe did), and have the actor refuse the `Started` message if `tools` contains any name the catalog does not know (the old recipe did this too, `native_claude.py:300-306`).

### 15. [warning] `accounts.claude_status` refuses on `ANTHROPIC_*` in the *control* env, which is spurious with an allow-listed host env and fails on this laptop
**Location** `sketch/qma2/accounts.py:56`; `sketch/qma2/secrets.py:57-72`.
**Finding** The refusal is copied from the old recipe, where the SDK merged `os.environ`. With `host_env` an allow-list, the control process's env is irrelevant to the CLI. This shell has `ANTHROPIC_BASE_URL` set (any terminal inside Claude Code does), so starting qmx-control from it makes the U1 sign-in panel report `api_env_present` for no reason.
**Suggestion** Delete the control-env check; keep the assertion inside `host_env` (`secrets.py:70`), which is the one that matters.

### 16. [warning] `units.md` was not amended; builders reading it get U1's old scope and a check that A6 says is wrong
**Location** `research/architect/candidate-1-opus/units.md:26-54`; `HARNESS.md` A5, A6, A8.
**Finding** A5 moves the store, SSE route, console panels and restart resume to U1b, but units.md's U1 "Done when" still requires the console, tool cards and "restart QMX, sends 'what did I ask you first?'". Its live check still says "Grep of `~/.qmx` finds no token", which A6 corrects (the token is in `~/.qmx/claude-home/.credentials.json` by design). The U2/U4 parallel lane also hides a dependency: U4's "done when" ("He adds his OpenRouter key in the console") needs `put_api_key(..., proof: OperatorProof)`, and the operator principal is U2 scope.
**Suggestion** Rewrite U1/U1b/U2/U4 rows in units.md (or an `units-amended.md`) rather than relying on readers to apply A5-A10 by hand; move `accounts.put_api_key` and the pairing flow into U1b or make U4 depend on U2.

### 17. [warning] Three A8/Q4-Q6 probes spend live Claude turns on facts the pinned SDK source already settles
**Location** `HARNESS.md` A8, open questions 4-5; `sketch/qma2/host/claude.py:45` ("option spelling: probe in U1"), `:121-126` (FIFO fallback); pinned SDK `types.py:230-236`, `:46`, `:2158-2175`.
**Finding** `ToolPermissionContext.tool_use_id` is documented as "Always a non-empty string when delivered to a `can_use_tool` callback"; `exclude_dynamic_sections` exists at `types.py:46`; mode shadowing is in the `can_use_tool` docstring (finding 2). The `(name, input digest)` FIFO correlation fallback is dead code. A10 budgets 15 live turns per unit; these cost turns for nothing.
**Suggestion** Keep only the two probes the source cannot answer (hooks firing with `setting_sources=[]` + plugin dir; skills loading from a local plugin). Delete the FIFO fallback.

### 18. [warning] Pending approvals pin hosts forever and the `max_live_hosts` cap has no policy
**Location** `sketch/qma2/harness.py:105` (`max_live_hosts: int = 8`), `:333-336` (`_ensure_host` reaps only idle hosts); `sketch/qma2/host/link.py:30-33` (`await_decision` "No timeout").
**Finding** A thread waiting on an approval is `Running`, so it is never reaped; eight forgotten approval cards hold eight CLI processes (A7 says measure; Anthropic's figure is ~1 GiB each) and the ninth `send` has no defined outcome: error, queue, or evict. Days-long sessions are the stated goal, so this will happen.
**Suggestion** Define the cap behaviour (`HarnessError("no_host_slot")` with the list of pinned threads) and let the operator's console show "waiting N hours" with an expire button; or expire approvals after a configurable window and surface a retry.

**Suggestion** For `python|node|pwsh|bash|sh -c|-e` suggest the exact command, not a prefix.

### 22. [nit] `ControlAgentOps.catalog` carves a per-argument exception into a row-derived list

If agents have "no reason to write" blocks at all, make `sessions_append` `who=OPERATOR|CLIENT` and delete the exception.

### 23. [nit] Windows path spellings defeat the Bash/MoneySurface path match more than the doc admits
**Location** `sketch/qma2/money.py:166-171`; `sketch/qma2/policy.py:184-189` (`normalize(PurePath)`).
**Finding** On this machine the same file is `C:\Users\...`, `/c/Users/...` (git-bash), `%USERPROFILE%\...`, `~/...` and `$env:USERPROFILE`. `normalize` takes a `PurePath` and handles 8.3 names, not the git-bash `/c/` form or env expansion. The speed bump is already labelled a speed bump; the U2 check ("read the qmx/ctrader password from the keyring") should include at least one git-bash spelling so the limit is recorded, not hidden.

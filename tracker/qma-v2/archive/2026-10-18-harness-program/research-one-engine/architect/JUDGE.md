## Factual errors and overclaims

### A (thin native)
1. **The settings hooks claim contradicts A's own default.** §3 says "Settings-file hooks in the QMX home run natively for all 33 events". But `build_options` passes `setting_sources=[]` until S7, and then the user-tier `settings.json` does not load at all. Its hooks, its permission rules and the "always" rules QMA writes into it (§3 step 4) are inert. 02a §6 states that settings move with `CLAUDE_CONFIG_DIR`. Only skills, agents and commands are UNCONFIRMED. A gates the whole user tier on the unconfirmed part.
2. **The broker scope is stated as fact.** The `money.py` docstring says "The token QMX reads from the keyring is minted read-only at the broker". Nothing in the grounding says so. design.md admits it comes from the runner's own knowledge. The docstring should be conditional on M1.
3. **"Unrepresentable" is an overclaim.** §3 says Type System Discipline made "the unprobed GPT launch unrepresentable". `ProbePassed` is a plain frozen dataclass, and only a CI grep stops someone else from constructing it (§2 "Rules enforced by import-linter").
4. **A omits that the background cap can act on stale data.** `BackgroundCap.allows(ledger)` relies on `RateLimitEvent`, which fires only when the status changes (02b F2). 03 GB-9 calls this cap "best effort". A does not say so.

### B (gateway)
1. **B misstates the policy rating (the most serious error in the arena).** B §3 says the relay is something "02b A rates gray-leaning-allowed". 02b A puts "QMA code reading, copying, storing, or **relaying** the Claude OAuth token itself" under **Clearly barred**. Only "a local router" in general is gray there. 01 §7 requirement 1 adds "QMX never holds or passes his Claude token." B's central mechanism sits in the barred row.
2. **"No str or bytes copy is kept" is false.** `split_headers` takes the raw header list as bytes after the HTTP server has parsed it (`server.py`). The token sits readable in the ASGI scope for the whole request, so QMA's process does read it. Sealing it afterwards does not change that.
3. **B leaves out 02b C item 2.** Anthropic "doesn't support routing Claude Code to non-Claude models through any gateway". That is B's headline feature. B cites C items 1, 3 and 5 but never this one.
4. **"Verbatim" conflicts with the wire gate.** B claims the plan lane is "Verbatim … streams without buffering" and says "No body edits on the plan lane". Yet the server pipeline runs every lane's response through the tap (`server.py` docstring, "response tee … wire gate"), and the tap holds `tool_use` blocks, swaps them for text and rewrites `stop_reason` (`tap.py`). That edits Anthropic's plan responses, against the gateway protocol rules B itself cites (02b C5).
5. **The OperatorProof claim is wrong.** It says agents "never hold one, so they cannot answer their own approvals" (`api.py`). Same-user Bash can read `qmx/control-token` from the keyring. A states this honestly ("Tradeoffs" bullet 1). B lists `propose_order … answered only with an OperatorProof` as money layer 6 regardless.
6. **Two behaviour claims have no source:** "a 403 `permission_error`, which the CLI does not retry", and "live CLIs ride its restart on their own retries". Neither appears in 02a or 02b.
7. **The module map lists files the sketch does not have.** `store.py`, `tools.py`, `approvals.py` and `settings.py` are named in `qmx_harness` (B §2) but missing, so no types back the approval rendezvous or `harness.db`.
8. **B has no process cap**, although it cites the 170 to 610 MB figure (B §3 "Problem").

### C (boundary)
1. **"Guard nothing that the boundary has not already removed" is false** (C §3 "Money safety"). Two cases. First, `ThreadSpec.extra_mcp` runs operator-added MCP servers inside the zone with env from the zone. A broker MCP with its own key would be unguarded, because C deleted the in-zone money hook and its descriptor check. Second, C risk 3 admits that loopback services are reachable on Windows and macOS, where they are only reported.
2. **C contradicts the grounding's scope decision without saying so.** 03 GB-7 already decided "BACKLOG, existing U10 (`os_account`) … No sandbox in v1 per R28 … the speed bump he accepted" (also 01 R21). C presents the zone as v1 core and calls R28 a question of reading (risk 4). It never cites GB-7.
3. **Practical omissions that affect the "talk like Claude Code" sign-off.** In repos he owns, Git refuses to work for another account until `safe.directory` is set. Agents have no Git or `gh` credentials, so they cannot push. On Linux, files the zone writes are owned by `qmx-agent`, and the default ACL in `share()` grants only `qmx-agent` (`zone_setup.py`). An inherited deny on a whole volume root such as `D:\` is applied to every file on the drive, so it is not a quick step, and the QMX worktrees live on `D:\`.
4. **"No QMA process reads it, stores it or forwards it"** (C §1.1) has an exception that C states only further down. The macOS `PrepareKeychain` fallback has QMA store the password of the keychain that holds the Claude token.

## Recommended base: A (thin native)

It is the only candidate that passes every hard rule as designed:
- The CLI owns sign-in and QMA never touches the token.
- There is no API path.
- It runs on all three OSes with a single `/login`.
- It runs Claude Code's own engine with nothing rebuilt on top.

It matches the grounding's decisions: 03 GB-4 (the delegate tool), GB-7 (no zone in v1), G1 and G2 (native rules and hooks), and 04 §2.

**How I checked my own bias toward the smallest design.** A wins on policy and size, not on safety. Its money score (2) is the lowest in the arena next to B's. A's money story is honest, and that honesty is what makes it a speed bump, which the operator accepted for now (R21). It does not make it a proof. The base should therefore ship with a plan to close that gap (graft C1 below), not with A's layer 1 treated as settled.

B loses on the policy rule, not on engineering. C loses on operator cost and on scope against GB-7, not on safety.

## Grafts

**From B:**
1. **Scrub the parent environment at boot and add the canary check.** Run `scrub_process_env` (`sketch/qmx_harness/env.py`) once in qmx-control before the SDK loads. A then no longer depends on the open E1 question (does `""` count as unset, A risk 3). Add B's L1 canary to A's S17: a fake `CLAUDE_CODE_OAUTH_TOKEN` canary, an echo server, and a grep of every QMX file, log and database.
2. **Split operator text from injected text in the type.** Use `OperatorText | InjectedText` (`api.py`), with `verbatim_prompts=True` for any text QMA builds from tool output, news or files. A applies verbatim only to `Child` chats. Background and scheduled turns need it too (02a §15).

(Kept in reserve: B's alternative 1, "a gateway for key traffic only", as a later move if per-request usage for key providers becomes worth a process. It never carries plan traffic.)

**From C:**
1. **Measure the boundary verdict, and make the OS-account zone the U10 upgrade path.** Add C's inside-out `run_probe` as a live check: an agent tries every `qmx/*` keyring entry, `settings.toml`, the control token and loopback listeners, and the result drives A's `MoneyPosture`. Keep the harness seam ready so a later zone or remote worker slots in behind the same `Harness` API. C's `ThreadSpec` route split (`Direct | ViaDoor`) is the right shape for that.
2. **Bind approvals to an args digest, use a closed Effect type, and cap whole-agent memory.**
   - A `qmx` tool needs a declared `Effect` with no money-act member (`model.py`), in addition to name matching. HOW gotcha 11 says names alone are not enough.
   - A `propose_order` or MANAGE approval is bound to the args digest and consumed once (C Z5; 03 CO-6).
   - A Windows Job Object or a systemd `MemoryMax` caps all CLI children together, not only each chat count (C §3 "RAM").

## Ideas to reject

| Idea | From | Why |
|---|---|---|
| Plan traffic through a QMX gateway, sealed or not | B | 02b A clearly bars "relaying" the token, and 01 §7 requirement 1 says QMX never passes it. The sealing starts after the HTTP parse. First-party feature parity is unknown (B R2), and the gateway becomes one point of failure for every chat. |
| Wire gate that rewrites `tool_use` in model responses | B | It edits Anthropic responses, risks a 400 on the next turn (B R3), and goes against "do not buffer" (02b C5). The PreToolUse hook already covers sub-agents and every mode (02a §3, §4). |
| Cross-provider sub-agents in one CLI process | B | 02b C2 says Anthropic does not support it. It needs signature provenance hacks and a shared `ENABLE_TOOL_SEARCH`. A child chat through `delegate` is the documented safe floor (02b Verdict C, 03 GB-4). |
| Removing every in-zone money check | C | Defence in depth is cheap. The operator ruled "hooks, not prompts" (01 hard rule 5). `extra_mcp` and loopback services slip past the boundary. |
| A mandatory elevated zone in v1 | C | It goes against GB-7 and R28 and the accepted speed bump (R21). Sign-in on macOS is at risk (M1). It costs him the most daily friction of the three (Git, credentials, file ownership). It belongs in the U10 upgrade. |
| Deny entries on every non-system volume root | C | They are invasive, slow to propagate over a whole drive, and touch his own drives. |
| A QMA-held keychain password on macOS | C | It sits too close to "store" in 02b A item 4. |
| `setting_sources=[]` gating all of `settings.json` | A | It silently disables UI-editable rules and hooks (01 §7 requirement 8). 02a §6 documents that settings move with `CLAUDE_CONFIG_DIR`. Probe skills and settings separately, and load `["user"]` for settings unless S7 shows they leak. |

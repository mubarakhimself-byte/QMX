# V2: why this shape, and when not

**What it buys.** All four unit origins with no special case, because "no pod" is the empty pod. Pod-life questions become fields. One edit reaches 200 units under one click and moves no logic fingerprint. Shared caps are real and atomic per place. A scalper's brake runs in its own call while a day stop runs across the pod, and the same row contract covers both. One chain, one row, one trail on every screen. Lab, paper, QMB and node drive one evaluator.

**What it costs.** The most contract of the shapes: about 21 new public types, 51 PRs (could reach 58), and a first filled paper entry only at slice 10. About nine PRs do nothing for a lone unit. A backtest of one pod member can't see its group, and the merge-lane replay that fixes it arrives late. The trail crossing two stages and a queue is designed, not proven.

**Against the others, fairly.**
- **F1 A (compiled in plus a thin group)** is simply better if pods stay single-unit presets for months. Less code, the unit truly alone, and a thin group handles caps. It loses on pod-of-members, the stage switcher and one document to compare, and would need two fingerprints anyway.
- **F1 C (live group above units)** has one rank table and is plainer to explain. It leaves the unit's sockets and five shipped halts unused. A scalper's brake ends up far from the scalper.
- **F2 C (find, track, correct)** is better on the evidence on disk: `E5`'s test found learner and applier added machine and little gain, and worse intraday (MODEL, one tuning by that file's author, but the point stands). Here the split costs little, because the built engine already holds both halves and a slow learner is just an anchor block. It buys bands he can see and a home for herding rules. If the fold drops one fork, drop this one.
- **F7 C (two chains)** matches my two stages more naturally, and only the receipt is harder. F7 A wins only because one list keeps order explicit.
- **F5 A (node closes targets)** works today. F5 B waits on R24, so until then this shape behaves like A with a stamp.

**One finding any version should take.** Today a unit's entry waits on the runtime thread for the venue and its stop, and units run one by one, so entries delay other units' exits, and a busy bell can trip the 30 s watchdog (`runtime.py:1183-1190`, `:3013-3016`, `healing.py:64`). Two passes per bar and a time budget fix that in any shape.

**Is it too much machine?** The core can be held to size by four rules: one placement field with one reader, a group stage that only cuts, controls firing outside the chain, slow blocks that only publish readings. It can't be made small. If a builder needs a fifth rule or a second placement reader, the machine has started to grow.

**What would make me abandon it.**
- Slice 3's `replay_size` can't reproduce sizes from one row without other units' journals.
- A group stage on the node adds latency that matters once R24 gives venue timings.
- After slice 8 nobody has built a pod using a group row. Then fold to F1 A with a thin group and keep `Amount`, the chain, settle and the two passes.
- The worker-thread budget proves unreliable on Windows, so a hang still costs the node.

**PROBE, mechanism only:** split chain equals one pass over 20,000 states; no shared-cap overrun over 2,000 runs; a hung link at 57 ms with the exit already gone; 200 real dummy steps about 68 ms. Scripts in `D:\Temp\v2-pod`.

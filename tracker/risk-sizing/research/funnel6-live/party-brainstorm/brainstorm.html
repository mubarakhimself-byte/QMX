The live side, widened

Headless brainstorm, 30 Oct 2026. 120 ideas, 10 techniques, one domain each. Built from .memlog.md. Nothing here is chosen. Tap a domain to fold it.

  • The node exists for one state, lid closed; the rule first-run-on-my-PC already fails for QMN today because QMN is Linux and systemd only.
  • Ruling 135 and PC first collide only if run means run with the live key; the brain/arm split and demo rehearsal are the two shapes that keep both, with different costs.
  • Data route and execution route as two roles of one connection is the smallest concept that covers futures, perps and proxy-data units.
  • The simplest journal is one row shape over a few streams with one writer each; the open fight is the store of record, not the fields.
  • Nobody stands in for the trading server under ruling 135 as written; that is new and needs a lead or operator answer.
01

Node setup

First Principles Thinking · 13 ideas

  1. B001 A trading server is one more kind in the shipped connect dialog, reusing its runner: his cards first, then checked rerun-safe steps, one place row written last.
  2. B002 Provider-API wizard: he pastes a provider token once, QMX creates the server, installs, then deletes the token. Token lifetime is a number.
  3. B003 No-token wizard stays the default: he rents by hand (today's card), QMX does everything after the address.
  4. B004 Cloud-init paste: QMX prints one text block, he pastes it into the provider's user-data box, the server builds itself and calls home over the private network.
  5. B005 Region picker by measured latency: the wizard times a round trip to each broker's trade host from candidate regions before he pays.
  6. B006 One image, two roles: the QMX host package gains a trading role, instead of a separate QMN deploy with its own paths and observability.
  7. B007 Places gain a can-trade capability beside can-run, so placement vocabulary covers trading servers without a new concept.
  8. B008 Node passport: the connect self-test (kill-switch latency, demo test trade, broker connect, clock skew, disk, feed freshness) lands as a Library item he can reread.
  9. B009 Size suggestion: the wizard reads how many units and data kinds are admitted and proposes a server size; the size table is a number.
  10. B010 Retire-a-node wizard: units move back to paper on the PC, the node's own broker app grant is revoked, the server is deleted through the provider.
  11. B011 Node updates only when flat or between sessions, reusing the shipped sync-before-update pattern.
  12. B012 Second node = clone this node in another provider; no second wizard.
  13. B013 Start the cTrader app registration on day one of the wizard, before he rents anything, because Spotware's approval has no published timeline.
02

Pc first

Assumption Reversal · 11 ideas

  1. B014 The Linux node runs on the PC under WSL2 Ubuntu, so the PC rehearses the exact node; needs research on systemd and Unix-socket support there.
  2. B015 The node ships as a container image; Docker Desktop on the PC and Docker on the server run the same image.
  3. B016 Port the node's Linux-only doors (Unix socket with peer credentials, systemd notify) to something that also runs on Windows, so the PC runs it natively.
  4. B017 Shadow mode on the PC: the full node stack reads live prices, decides, journals would-have-done rows, places nothing.
  5. B018 Twin run: PC and node run the same units for N days; journals are diffed; a divergence is a bug. N is a number.
  6. B019 Encode the two-day lesson as a release check: a node release ships only after it ran on the PC for X hours. X is a number.
  7. B020 Home-node mode: live trading runs on the PC while it is on and the server stands in when the PC goes dark (fits rulings 136-139, breaks 135).
  8. B021 Reverse: the PC never trades live; the node is the PC's always-on half (today's 135).
  9. B022 A small home box on a UPS that agents cannot reach holds the live key: his hardware, local first, but power cuts still hit it.
  10. B023 Write the exact PC-versus-node difference list: same code, config and data paths; only key, host name and broker app differ. Anything else on the list is a bug.
  11. B024 A Rehearse-on-this-PC button beside Send-to-trading-server on every unit page.
03

Failure and recovery

Chaos Engineering · 14 ideas

  1. B025 Every live order carries its stop at the broker, so a dead node never leaves an unprotected trade.
  2. B026 Venue dead man's switch where offered (Hyperliquid scheduled cancel): the node heartbeats the venue and silence cancels resting orders.
  3. B027 Reconcile on restart: the broker's positions and deals win; unit journals are rebuilt from them; orphans get flagged rows.
  4. B028 Power-cut drill on the PC in demo: pull the plug, restart, check every journal and position reconciles.
  5. B029 Outside watcher: the PC when on, a free uptime pinger when off; one alert per incident to his phone.
  6. B030 Passive second node in another provider, holding no live key until his click moves the key there.
  7. B031 Laptop-off is the normal state: the PC link is optional on the node, shown as unreachable since a time.
  8. B032 Node outbox: journals queue on the node and sync when the PC returns, even after a week away.
  9. B033 Disk-full order on the node: tick recording gives way before journals; journals never half-write.
  10. B034 Broker weekend maintenance as scheduled venue-down events in the market journal, so nothing reads them as faults.
  11. B035 Token-refresh drill: refresh the cTrader sign-in on one machine on demo and prove the other machine is not logged out.
  12. B036 Client order id = the trade's trace id, so a retried send never doubles a position.
  13. B037 Provider outage playbook card: what keeps running at the broker, what he does by hand, written in five lines.
  14. B038 Clock drift check in the node passport and every hour: venue time vs receive time vs local clock.

Live feeds

Cross-Pollination · 13 ideas

  1. B039 Feed pool per machine: one subscription per symbol, many readers, and a lease per broker app and environment so PC and node take turns.
  2. B040 Record everything subscribed: live ticks and books become history, which Hyperliquid's ~3.5 days of candles makes necessary.
  3. B041 Tick-first feeds for market-state sensing, because 1-minute closes take about 44 minutes to show a volatility jump.
  4. B042 Futures routes to compare: Rithmic via a futures broker, CQG, Interactive Brokers, Tradovate; data separately from Databento.
  5. B043 Ask whether any cTrader broker lists exchange futures, or only futures-based CFDs that expire early.
  6. B044 Hyperliquid data with no key at all (public websocket); trading through an API wallet.
  7. B045 Crypto perps feeds through CCXT's websocket layer, since the shipped CCXT adapter is spot only.
  8. B046 Feed quality per symbol per hour in the market journal: gaps, stale minutes, out-of-order, duplicates dropped.
  9. B047 Stamp venue time and receive time on every message, and keep both.
  10. B048 Trading-hours calendar as data per instrument and venue, not code.
  11. B049 Units declare data kinds (ticks, depth, tape, open interest, funding); the pool subscribes only to what admitted units declared, which also bounds data fees.
  12. B050 Paid feeds earn their place: switched on when a unit backtested on that vendor's history passes; free until then.
  13. B051 Last-value cache per symbol so a restarted unit reads current state at once and warm-up comes from recorded partitions.
05

Data route vs execution route

Morphological Analysis · 11 ideas

  1. B052 A connection has two separable roles, data and execution; a unit binds one data route per data kind and one execution route.
  2. B053 Proxy-data unit: trade the US500 CFD on cTrader while reading CME futures tape from a vendor; every journal row says signal venue and execution venue.
  3. B054 Basis watch: the market journal records the gap between the proxy market and the traded one per minute.
  4. B055 Same-venue data preferred, proxy as a declared fallback the unit was tested with.
  5. B056 Execution route ranking per instrument from measured spread plus fees by hour, answering is it the broker or the time.
  6. B057 Several brokers for one instrument: the market journal compares them; his admission names which broker a unit uses.
  7. B058 The grid instrument class x data source x execution venue x machine as the permutation table agents and he can read.
  8. B059 Data licence terms on the connection row (personal use, display, non-display); research whether algorithmic use of CME data costs more.
  9. B060 Data stays up when a broker is down: a separate data route keeps market sensing alive during a broker outage.
  10. B061 Data-only connections with no account (Hyperliquid public, Binance public files) as first-class rows.
  11. B062 Execution-only check: a broker whose data is unused still feeds its own spread and fill rows to the market journal.
06

Journals and schemas

SCAMPER Method · 13 ideas

  1. B063 One event row shape for every stream: id, at, stream, subject, kind, world, links, body; nothing else required.
  2. B064 Four streams with one writer each (unit, market, router decision, guard), plus a fifth node journal for start, stop, update, self-test.
  3. B065 Eliminate the separate guard stream: guard verdicts are rows of the one shape with stream = guard.
  4. B066 Seen-but-not-taken rows carry one reason from a small closed list (spread, guard, already in trade, session, data stale, size below minimum) plus free text.
  5. B067 Missed trades are computed afterwards by replay and written by the replay, never live.
  6. B068 Events by default; every decision per bar only on request and time-boxed; the box length is a number.
  7. B069 Journal before dispatch, as the node's shipped dispatcher already does.
  8. B070 World on every row (backtest, paper, demo, live, synthetic), taken from the trade kind.
  9. B071 Calibration receipts as journal rows: what moved, from what, to what, driven by which rows.
  10. B072 Schema version on every row; readers accept old versions; no migration of history.
  11. B073 Monthly Parquet partitions per unit journal with one Library card pointing at them.
  12. B074 The broker's own deal history as a cross-check stream: broker says vs unit says.
  13. B075 Session and hour performance is a derived view over rows, never a stored column.

Security and keys

TRIZ Contradiction · 10 ideas

  1. B098 Demo-rehearse everything on the PC; only the live key lives on the server (lead's candidate).
  2. B099 Treat the harm as placing trades, not withdrawing: trade-only, no-withdraw keys still count as live keys.
  3. B100 A separate Windows account or a VM on the PC that agent shells cannot reach holds the live key; research how strong that wall is.
  4. B101 Hardware-backed unlock: the live key opens only for the trading process with his presence (Windows Hello or TPM); research.
  5. B102 Live mode switch on the PC: the live key exists only while the agent harness is stopped; weak, listed for completeness.
  6. B103 Broker-side account limits (max size, daily loss) where a broker offers them, as the guard that holds even if a key leaks.
  7. B104 A tiny live canary sub-account on the PC as the PC-first proof of the live path; a money call for him.
  8. B105 Define agent-reachable precisely: the trading server must not share the SSH path the PC already holds to the worker server.
  9. B106 Brain and arm split: the arm holds the key and sends orders on the server; the brain (units, feeds, guards) runs anywhere, the PC included, with a full copy on the server so units still stand alone.
  10. B107 Live key typed on the server only, sign-in code delivered there (shipped ruling text), PC shows the account read from the server's reports.

Wildcards

Trickster's Gambit · 13 ideas

  2. B109 Broker's free VPS for active clients as the node; usually Windows with MT5.
  3. B110 Node in the broker's own data centre region (London LD4, New York NY4) for fewer hops, not for speed games.
  4. B111 UPS plus 4G failover router at home so the PC rarely goes dark; the node only for long absences.
  5. B112 Small ARM board as the home node; fog whether the Python stack and QMN run there.
  6. B113 The journal is the PC-node protocol: admissions go as rows, the node answers with rows; no second channel.
  7. B114 Hash-chained flight recorder on the node so he can trust what happened while away.
  8. B115 Rent by the hour: spin the node up only for the sessions units trade; skeptic expects 24/7 crypto to kill it.
  9. B116 Nodes by venue: a crypto node near Hyperliquid's API servers, an FX node near the cTrader broker; research where those are.
  10. B117 A node cost readout: monthly server and data cost beside what the node's units earned.
  11. B118 The node never holds the Library: it holds journals and an outbox; the PC stays the one Library writer.
  12. B119 Phone as the panic button: one action that tells the node to stop new entries everywhere, guard-logged.

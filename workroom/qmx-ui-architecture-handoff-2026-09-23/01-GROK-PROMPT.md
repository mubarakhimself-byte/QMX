## Produce architecture that can guide implementation

Treat QMX as a platform for exploring, constructing, testing, reusing and operating capabilities. Capabilities/apps/workflows can be visual, headless or mixed. Their UI presence is independent of where execution occurs, whether an app is open, and whether a conversation is active. Both trading and non-trading data/ML work belong. Paper trading applies where trading behavior warrants it, not to every mini-app.

Preserve the original differentiated layouts. Main copilot: sessions/history, conversation and tabbed work area. Mini-apps: app-specific navigation above a substantial working canvas and optional right copilot. Authoring/ML: graph and code/detail views within that family, with meaningful expansion and return. The common platform rail stays coherent across these interiors. A permanent generic secondary sidebar and prose cards are not replacements for working widgets. Clarify the remaining behaviors instead of making the user design each one.

Start with Svelte + TypeScript, shadcn-svelte and Svelte Flow. Use reusable open-source primitives and a thin QMX-owned layer for QMX behavior. Specify SvelteKit versus Svelte/Vite, versions, chart/table/code/diff/terminal choices and adapters based on evidence. Qt is excluded. Tauri is a candidate requiring evaluation of Python process lifecycle, local files, provider integration, webviews, packaging and remote operation. Rust/C++ only justify changes at measured or concretely demonstrated boundaries. Keep backend compute separate from rendering; speed claims need workload evidence.

Distinguish the design system, component library, screen compositions, extension/contribution contracts and backend services. Define ownership, state flow and versioning without inventing duplicate core services. Include json-render as a possible controlled component renderer and MCP Apps as hosted interactive resources with host communication; neither implicitly grants application authority. Examine Svelte compatibility, host lifecycle, sandboxing, failures, accessibility and fallback. App-to-app/workflow-to-workflow composition should use identified contracts rather than UI automation. Include authoring versus app-use authority, provider/credential setup, CLI proxy questions, local/VPS placement and operational observability.

For every proposed UI capability, show the path from user intent through component state and command/query to its backend owner, progress/result and recovery. Classify dependencies as **reuse, adapt, add, or unresolved**, with code/doc evidence. Inspect middleware, API/event transport, data storage, auth, worker lifecycle and packaging where affected; do not prescribe a new database or service merely because a new screen needs information. Keep read-only display, commands with side effects, versioned definitions and running instances distinct.

Review the supplied reference sites purposefully when a specific interaction remains unclear. They are mental models; commercial dashboard kits and n8n are not requested dependencies. Use original screenshots and actual interaction observations, not just marketing prose. Record what you could not access. A neutral dark shadcn-svelte baseline is sufficient; no paid design tools or quest for a proprietary DESIGN.md is needed. Produce a provisional QMX visual/component convention compatible with later aesthetic refinement.

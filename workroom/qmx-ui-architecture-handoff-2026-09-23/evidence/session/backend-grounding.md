### Transport and persistence

- The composed QMA process is one asyncio daemon, sole SQLite writer, with a CT-40 listener (`qma-daemon/src/qma/daemon/process.py:1-8,70-74,92-99`). It explicitly says there is no separate HTTP experiment service and QMB's JSONL stays separate from QMA SQLite (`:3-8,70-78`). The QMA process entry is `qma-daemon/src/qma/daemon/__main__.py`.
- Wire transport is split: command payloads mutate and are acknowledged immediately over JSON-RPC 2.0 WebSocket; effects settle asynchronously (`qma-wire/schemas/command.v1.schema.json:4-5`). Query payloads read durable snapshots over HTTP GET (`query.v1.schema.json:4-5`). Default listener host is `127.0.0.1` (`qma-wire/src/qma/wire/listener.py:32`); authentication is required and a non-loopback bind requires WSS plus HTTPS and explicit operator-recorded configuration (`listener.py:1-6,145-170`).
- `ProductSessionService` mints journal/SQLite product-session rows; its durable fields include profile, `app_instance_id`, `context_revision`, grant IDs, selected refs, account scope, and resume cursor (`product_session.py:178-198,1156-1185,1236-1267,1392-1420`). Reconnect restores these request/session facts, while tabs remain attachment/chrome only (`:1-24`). Session scope/profile/app binding is concrete backend behavior; tabs, widgets, and workspace layouts are not persisted.
- QMA does provide persistent mission/task graph/experiment state and plugin/ledger projections. The inspected files do not establish frontend layout persistence. No desktop browser/localStorage or app shell implementation was found in this source tree.

## Practical limits for UI/UX discovery

Use the command/query schemas, scope-path law, procedures/task graphs, contribution discovery, product-session profiles, and grant boundaries as existing backend affordances. Scope-path and app-profile are separate axes: an empty QMA wire scope is daemon-global (`qma-wire/src/qma/wire/envelope.py:38-47,73-79`), whereas `ProductSessionProfile` binds one product interaction as `app-use` or `authoring` (`product_session.py:271-278,645-676`). Do not infer a dedicated “global agent” profile or a Copilot scope selector from these primitives.

The backend also contains an SCN-0019 three-record change path, but only as `ChangeRequestFixture` (explicitly named “app-use change-request fixture” at `qma-daemon/src/qma/daemon/staging/change_request.py:1-10,524-538`). In that fixture, app-use mints an immutable request over bounded runtime-input patches and target base hashes; package-source edits, grant widening, and account retargeting are refused (`:282-337,663-765`). Authoring validates; applying requires an authoring session plus operator principal and a still-valid base (`:797-869,871-958`). `InstalledAppSnapshot` captures the v1 package/version/source hash, config revision, grants, running jobs, and account scope (`:462-490`). The module is explicitly a fixture, and the CT-40 schemas list no change-request operations; report this as a fixture model/boundary, not as a production edit API.

The remaining gap is specifically the user-facing host: no rendered mini-app UI, widget SDK/contribution point, MCP Apps store/execute behavior, persisted workspace chrome, or current Copilot UI was found. A frontend for these backend primitives cannot be claimed from this repository snapshot; current UI/runtime needs separate source discovery.

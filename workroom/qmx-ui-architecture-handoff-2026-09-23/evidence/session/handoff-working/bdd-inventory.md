## Coverage relevant to product shape

- **Visual, headless, and mixed apps:** `P1-CAP-001` requires a headless package to be discoverable through catalog, CLI, node, and app doors without a navigation pane; `P1-OP-001` requires equivalent operation semantics across direct/CLI/node/app doors. `P1-APP-001..008` cover cross-app artifact and operation use, partial composite failures, shared-provider instance choice/version pins, missing components, identity versus display labels, and shared-parameter cycles. These specify surface parity and composition rules; they do not specify a rendered layout or prove a real visual app.
- **Graph/node workflows:** `P1-WF-001..007` cover selected executable subgraphs, semantic port mismatch, `zip`/keyed/Cartesian join behavior, bounded nested cycles, layout-only edits, version pinning, and duplicate schedule triggers. P2/P1 completion cases add partial outputs and checkpointed resume. There is no concrete visual graph-editor journey, code-node authoring/expansion or execution contract, code preview, debugger, or sandbox UX.
- **Scoped copilot sessions:** `P1-SES-001..006` and `P2-SES-007..011` cover concurrent workflow/strategy/ML sessions, reconnect independent of tab identity, app-use-to-authoring change requests, no nested grant escalation, history not retargeting commands, specialist ownership, stale credentials/targets, unchanged grants across refresh, and approval after reconnect. `P2-SES-008` and `P2-SES-011` are near-duplicate reconnect/approval behaviors (same core oracle, with different wording); reconcile or intentionally retain both rather than treating all IDs as distinct interaction patterns.
- **Local / remote / VPS placement:** `P1-PLC-001..006` and `P2-PLC-007` cover missing GPU/entitlement preflight, portable staging of local files, UI closure while a server-owned job continues, coordinator loss, backup/restore verification, and cross-store restore consistency. They do not define a first-run local-versus-VPS choice flow, provider onboarding, cost/quota comparison UI, or specific VPS lifecycle screens.
- **Cancellation and recovery:** operation cases cover unknown external outcomes, state-sensitive cancellation, expiry, partial artifacts, durable resume, no blind retry, and interruption distinct from cancellation. Workflow/recovery cases cover partial branches, duplicate-free checkpoint resume, worker/coordinator loss, staging interruption, and verified restore.
- **Startup, Library, and credentials:** package/catalog cases cover install/discovery, atomic activation and index rebuild, failed migration recovery, dependency and in-flight version pins, refresh/grant boundaries, and export/import honesty. Credential coverage is mainly secret-free export plus stale/revoked credential refusal; first-run setup/bootstrapping, provider login/connection, secret entry/rotation, and reconnect UX are not specified. “Library” behavior is represented as catalog/package/artifact identity and lineage rather than a dedicated Library screen or its browse/search/preview/pin journey.
- **Data, ML, and streams:** cases cover provider disagreement and attribution, source revisions without rewriting old results, truncation versus empty/unavailable, complete model weights, non-trading artifacts, heterogeneous time alignment/leakage, model comparisons and promotion lineage, stale source entitlement, replay/live transition, duplicates/gaps, bounded-buffer overload, shared feed cancellation, and UI disposal preserving durable consumer ownership. They specify integrity/evidence expectations but not detailed builder/studio visual interactions.
- **Paper/trading only where it bears on full-application composition:** the set protects default Book/BMS behavior, calls for a complete non-Book composition validated/simulated without dummy Book/BMS, constrains shadow/active intelligence, account targeting, sequential command-owner transfer, residual/partial/unknown order handling, stale-process authority, and rollback truth. It has no explicit paper-trading setup/session journey, order-ticket UI, paper-to-live promotion screen, or broker-credential onboarding scenario. Do not infer these from the generic simulation/handover cases.

## Execution boundary and evidence caution

The five files are marked `@draft @specification_only`; the Grok handoff explicitly says Gherkin is specification, not proof of execution. Root `pyproject.toml` configures pytest to collect `adws/tests`; root development dependencies and `uv.lock` provide pytest but no Cucumber, Behave, or pytest-bdd runner. No QMX step definitions tied to these five architecture files were found in the relevant project configuration/source paths. This establishes no visible QMX feature-file runner binding from the inspected evidence, not a universal claim that no other test mechanism exists. The challenge `TEST-AND-MUTATION-PLAN.md` records the required catalog-to-feature ID reconciliation as behavioral trace integrity while stating that it does not prove `.feature` execution. No tests were run for this inventory.

The inventory does not establish implementation, readiness, or ratification. For the UI handoff, treat the scenarios as behavioral constraints and create explicit visual/headless/mixed-app journeys for the uncovered interaction details before claiming those flows are specified or verified.

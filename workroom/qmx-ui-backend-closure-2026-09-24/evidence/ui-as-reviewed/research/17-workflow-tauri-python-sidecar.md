# Research result

**Status: Partial**

Tauri 2 is a capable but optional desktop host for a Python-first QMX app: a privileged Rust Core plus OS WebViews can wrap the UI, spawn a bundled Python sidecar, gate local files and secrets, and ship Windows MSI/NSIS installers with signed updates—none of which a normal system browser talking to a local qma-daemon gets by default. Ratified QMX architecture does not require Tauri; the designed local client path is an authenticated JSON-RPC 2.0 WebSocket (commands/events) plus HTTP GET to a single Python qma-daemon, Qt is already excluded, and UI presentation/packaging remain undesigned (GAP-0081). Official v2 docs do not provide sidecar health checks, auto-restart, or a daemon supervisor, nor automatic updater rollback, extra Python compute speed, or a chart renderer beyond the OS WebView. This check is dated 2026-09-23: the current stable crates are tauri 2.11.6 (GitHub tag `tauri-v2.11.6`, created 2026-09-19) and tauri-cli 2.11.5; newest published for both is 3.0.0-alpha.2, which is not stable v2. [S5]

### Process model
Each Tauri v2 app has a Rust Core process as the entry point and the only component with full OS access; it orchestrates windows, IPC, tray, and notifications but does not render UI. One or more OS WebView processes draw the interface using libraries dynamically linked at runtime and not shipped in the executable: WebView2 on Windows, WKWebView on macOS, webkitgtk on Linux. [S1][S6] A sidecar is not a third role in that Core/WebView diagram. It is an optional bundled external binary—docs cite Python CLI or API servers via PyInstaller—listed in `bundle.externalBin` (with a `-$TARGET_TRIPLE` suffix per architecture) and spawned as a child through the shell plugin. [S2][S12]

### Python sidecar and daemon lifecycle
Start a Python-first extra process by declaring the binary and spawning it with `Command.sidecar` / `app.shell().sidecar(...).spawn()` (or `execute()`), under a capability that sets `sidecar: true` on `shell:allow-execute` and/or `shell:allow-spawn`; allowed arguments are constrained in that same capability. Documented child APIs are spawn/execute, stdin write, kill, and exit observation (`Terminated`/`close` with exit code and signal); shell permissions include `allow-execute`, `allow-spawn`, `allow-kill`, and `allow-stdin-write`. [S3] Official v2 docs do not provide sidecar health-check, auto-restart, or daemon-supervisor APIs. The process plugin’s `exit`/`relaunch` apply only to the current Tauri app process; long-lived sidecars are told to use other IPC (localhost, stdin/stdout, sockets) instead. [S4]

### Local filesystem and credentials
Frontend filesystem access goes through the fs plugin and needs both a capability permission and an explicit path scope; path traversal (`..`) is rejected, and a command permission alone (for example `fs:allow-exists`) opens no path. [S7] By default `fs:default` grants recursive read (and mkdir) of AppConfig, AppData, AppLocalData, AppCache, and AppLog, and denies webview data folders (Windows `$APPLOCALDATA/EBWebView` and Linux webview data under `$APPLOCALDATA`). Rust-side I/O is `std::fs` / `tokio::fs`, not the frontend fs command API. [S8] Official v2 secret storage is the Stronghold plugin (IOTA Stronghold): initialize it with a password hash function that must return 32 bytes, load snapshots with `Stronghold.load(path, password)`, and treat Vault as write/update/delete only (no secret reads; procedures manipulate stored secrets). Frontend use still needs a capability such as `stronghold:default`; secrets should not be handled in the frontend. [S9]

### Multiple webviews and IPC boundaries
ACL capabilities bind plugin/core commands to window and/or webview labels. A webview or window that matches no capability has no IPC; a matching window label enables the capability on all of that window’s webviews; multiwebview windows should use the `webviews` list instead of `windows` for finer control. Overlapping capabilities merge; security boundaries use window labels, not titles. Adding extra webviews onto one window via `WebviewBuilder` / `window.add_child` is documented as unstable-only. [S10]

### Remote VPS while keeping local files
Talking to a remote host from the WebView is not open by default. JS HTTP via the http plugin needs an explicit URL allow/deny scope (`http:default` enables fetch operations but no origins until configured). Remote pages may use Tauri IPC only if a capability sets `remote.urls` (local app URLs default to enabled; giving remote sources local system access is called out as a caution). [S11] Local files stay behind the fs plugin’s permission-plus-scope model above; they are not implied by allowing remote HTTP.

### Windows installers, updates, and rollback
Windows apps package as WiX Toolset v3 Microsoft Installers (`.msi`, created only on Windows) or NSIS setup executables (`-setup.exe`, cross-compilable from Linux/macOS). [S13] Installers default to downloading and running the WebView2 bootstrapper if the runtime is missing; apps may instead embed the bootstrapper (~1.8MB), embed an offline installer (~127MB), ship a fixed runtime (~180MB), or skip install (the app will not work without a preinstalled runtime). Updater bundles use DownloadBootstrapper regardless of that setting. [S14] Authenticode signing is not required to run (unsigned downloads can hit SmartScreen; Store listing requires signing). Extra installer/uninstall steps are app-supplied NSIS hooks or a full custom NSIS/WiX template. [S18]

In-app updates on Windows reuse the normal NSIS/MSI installers plus sidecar `.sig` files when `bundle.createUpdaterArtifacts` is true. The updater requires a minisign public/private key pair and “This cannot be disabled.” [S15] Windows installation is configured with `plugins.updater.windows.installMode`: `passive` (default, progress UI, no interaction), `basicUi` (requires user interaction), or `quiet` (no UI; cannot self-elevate, so only user-wide or already-admin installs). `install` / `downloadAndInstall` exits the app on Windows after launching the installer. Check/download/install and when to relaunch are otherwise left to app code. [S16] Official updater docs do not provide automatic rollback. Default version checks require a greater SemVer; rolling back is left to the app/server by overwriting `version_comparator` so the server-sent version is installed. Separately, `bundle.windows.allowDowngrades` defaults to true for a second installer run (set false to block older versions). [S17]

### Tauri vs a browser talking to qma-daemon
QMX does not pin or require Tauri 2. Non-Python clients, including a future UI, attach over qma-wire; UI chrome, packaging, and qma-ui-contract beyond a stub remain a later sitting (GAP-0081). [S19] The designed local path is authenticated JSON-RPC 2.0 over WebSocket for commands and events plus HTTP GET queries to the single Python qma-daemon (no CLI; mutating acts arrive over that wire). Unauthenticated or plaintext non-loopback bind is a hard startup refusal. [S20] Working notes dated 2026-09-23 exclude Qt and treat Tauri as an unevaluated desktop candidate versus browser or Electron; they do not select Tauri as required, and a runnable browser frontend does not settle browser-only delivery. [S21]

What Tauri uniquely supplies is a privileged Rust core (windows, tray, notifications), capability-gated native APIs (filesystem, shell, dialogs, updater, and so on), frontend-to-Rust command IPC, and optional embedding of Python binaries as sidecars—none of which a normal system-browser page gets by default. [S22] That command IPC is a JSON-RPC-like `invoke` to Rust functions with JSON-serializable args/returns; it is not QMX’s qma-wire daemon protocol. Sidecar docs describe bundling and running Python executables, not faster Python compute. [S24] Tauri also does not replace or accelerate chart rendering: the Core does not draw UI; an OS WebView executes HTML/CSS/JavaScript, and Tauri acts as a static web host of those assets. [S23]

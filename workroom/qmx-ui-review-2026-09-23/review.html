R4 · High

Make the app/view contribution contract usable by independent builders

Optional navigation, views and copilot settings remain request blobs. The candidate does not bind how a pack supplies them, how the host discovers a renderer and compatible schema, or how lifecycle/failure isolation works. Checking an embedded action against any grant in a session also leaves its intended contribution/instance context ambiguous.

Why it matters: A pack author and shell author can both comply yet disagree on the same app descriptor. A generated view can accidentally select authority from a broader session instead of acting through its host-bound context.

Required correction: Define a versioned request-DTO schema and host ingestion/loading path without making view:* a grant or minting a new contribution point. Bind each mounted native/generated/iframe view to host-owned instance, contribution, session and action context. Reuse parent GrantRecord matching on contribution, instance/config, op/version, effect, parameter ceiling and account scope; do not create view-specific grants or another registry. Untrusted specs/frames supply declared actions and schema-valid inputs; host-derived grant, target and caller fields must not be renderer-selected. Specify supported slots, compatibility, mount/dispose, unsupported-renderer fallback and error isolation. Pin the MCP Apps protocol profile and explicitly decline unsupported app-provided-tool negotiation.

Closure evidence: Provide one widget-heavy app, one graph/code app and one headless pack example against the same contract. Include two instances with overlapping op names/grants, malformed metadata, disabled contribution, adapter mount failure and a frame attempting a different target. Show who refuses each case.

Disposition: Complete the host/pack contract; retain existing authorization rather than adding a parallel permission system.

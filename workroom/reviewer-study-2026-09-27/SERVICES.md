# Reviewer and verification service study

**Checked:** 2026-09-27. Product pages and pricing can change; recheck before purchase. This is a read-only comparison for QMX (~200k+ LOC Python/backend, planned Svelte/TypeScript UI), where the desired job is a deep, evidence-backed audit against approved architecture, docs, epics and requirements. Findings should become validated GitHub issues; a separate agent can implement fixes later. No service was installed, connected, trialed, or purchased for this research.

## Recommendation

No evaluated managed service is documented as a turnkey, comprehensive architecture/spec audit of all existing code that also validates findings as GitHub issues. Managed reviewers analyze PR changes with broader repository context; CodeRabbit additionally offers a separately priced full-codebase security scan, while Devin and Warp Factory can orchestrate broader agent tasks. These modes do not establish complete functional conformance against every approved document. A careful unattended audit needs explicit scopes, approved documents as inputs, exact evidence locations, independent validation/reproduction, deduplication, and automated GitHub issue export. Human input is reserved for consequential ambiguity in policy, authority, or conflicting specs.

For a first, low-cost screening, CodeRabbit public repositories receive free reviews, while Greptile offers a free individual tier. CodeRabbit does not state an OSS-license test; Greptile OSS access is conditional, so check QMX license and use before applying. Greptile’s free individual tier is another no-cost evaluation path (50 credits monthly for one active developer), with OSS eligibility a separate application. Qodo offers a 14-day, no-card trial and a promising requirement-gap / full-repository PR review story, but ongoing use is paid and metered. Cursor Bugbot is explicitly diff-focused and has usage charges; it is a PR gate, not the requested audit. TestSprite is complementary for behavior validation against a running app and supplied PRD/API docs, not source-wide architecture analysis. Devin Review is another PR review surface; Devin’s broader agent can act on tickets and test apps, but that is a delegated engineering agent workflow, not a read-only audit service by default. Warp’s documented Code Review panel is for local Git diffs and agent edits, so it is not an out-of-box whole-repo architecture/spec auditor. Warp Factories are an Early Access orchestration product for fleets of agents; Factory availability is not guaranteed.

Practical split: use a repository-aware reviewer to examine bounded, auditable scopes and link findings to exact source lines; use TestSprite/Reticle or the existing app test setup to prove user-facing behavior; then validate each candidate issue against the architecture/spec and reproduce it before filing. Keep reviewers in advisory mode and disable autofix/auto-merge while the audit is read-only. Service claims about catching bugs or context quality are vendor claims, not independent guarantees.

## Notes for an unattended evaluation

1. Prepare a read-only audit brief that names the canonical approved architecture/spec documents and says which are authoritative when they conflict. Require each candidate finding to include violated invariant/requirement, file and line evidence, concrete failure scenario, severity, confidence, and a validation/reproduction idea.
2. Pilot bounded representative areas (auth/data access, API boundary, background jobs). Run an independent second pass, deduplicate, and automatically reproduce or test candidates before issue creation. Preserve evidence/confidence fields to suppress weak items; request human input only for consequential spec conflicts. Do not infer coverage from repo indexing or review count.
3. For unattended GitHub issue export, produce structured candidates, independently validate against approved documents and code, attempt reproduction or a focused check, deduplicate, and create issues containing evidence, confidence, severity, and validation results. Escalate only consequential ambiguity over which spec or policy controls. These products generally post PR comments/findings; no verified one-click “validated full audit findings → GitHub issues” workflow was found across the set.
4. For UI/backend behavior, run a separate live-app journey check. TestSprite can derive/exercise from PRD and OpenAPI; QMX’s supplied Reticle instruction requires user-facing changes to be proved on the running app using Reticle. These checks validate behavior, not architecture completeness.
5. For a solo developer, paid costs should be judged by review units/run count, not seat price alone. On a codebase this size, ask vendors whether indexing limits, excluded/generated files, rate caps, private-code retention, and PR/file thresholds apply before relying on a “large repository” claim.

## Source claims vs. inference

**Documented:** the service scope, inputs, integrations, deployment availability, and prices described above are from each vendor’s official pages. Their performance and quality claims (such as bugs found, full context, review accuracy) remain vendor claims.

**Inference:** a diff-oriented reviewer with a repository index may help find cross-file defects, but that is insufficient evidence that it has audited all existing code against every architecture document and epic. An app explorer can expose runtime mismatches in reachable flows, but cannot prove all code invariants. “GitHub integration” alone does not mean a product files reviewed/validated audit findings as GitHub issues. Those distinctions drive the fit ratings above.

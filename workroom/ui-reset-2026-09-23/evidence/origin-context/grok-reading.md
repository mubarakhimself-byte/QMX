## Overall reading

The most consequential operator intent is adaptability: QMX is meant to host different compositions over time, with Book/BMS treated as the current default portfolio-management, risk, and sizing implementation rather than the framework’s sole possible implementation. A replacement or versioned stack must be adopted coherently through authoring, backtest/optimization, MIS, trading-node, paper, and live paths. The operator explicitly distinguishes that from an immediate live swap: paper first, then sequential cutover; no live-position hot swap. Research and sensing are not a substitute trading system, and dummy Book/BMS records are rejected. This correction appears in the operator’s own extended message and the assistant’s acknowledged recast (lines 1099–1105, especially 1101 and 1180–1184), then in the proposed Documentation Factory handoff (1213–1230). Treat it as the strongest expression of intent in this snapshot.

The Stage A candidate was explicitly not ratified; even after Stage C reconciliation the assistant says it is not ready for an operator acceptance gate (980–994, 1059–1063). The export describes proposals and inspected-at-a-pinned-revision claims, not a delivered, integrated product. Its own final transfer prompt warns against describing proposed connections as implemented and names in-memory TaskGraph, proposed ContributionHit, absent product sessions, and unsupported QML→QMB→QMN integration (1229–1230).

## Architectural and UX/component boundaries

The candidate frames QMX as a construction kit over existing libraries, not a sixth application or “sixth COMP.” The Experimentation Board is a UX projection/layout, not a registry or new durable object kind. QMF remains the single framework/toolbox. The initial ledger says capability discovery may be added without turning hypotheses into Artifact Library objects (211–215); the Stage A summary makes the construction-kit and Board boundaries explicit (530–532). The four discovery rails are intentionally typed and distinct: existing Artifact kinds (`fp1`), cited Knowledge, plugin contribution identity (`plugin_id:local_id`), and QML research hypotheses outside the facade. Contribution discovery should not mint `fp1` artifacts (362, 531, 1016).

Keep authoring and execution concepts separate. A Board draft is layout; a Graph Template is a reusable authored procedure; a Task Graph represents one Mission execution. An ungoverned library call does not become a Mission, and a Stage 0 graph does not execute. Cycles need DAG validation, not merely direct reverse-edge detection. Workflows should reuse and extend QMA’s Graph Template → Mission Compiler → RoutineScheduler → CT-47 path rather than create a second scheduler. The report explicitly identifies gaps in the then-current implementation: cycle checking was incomplete, TaskGraph lacked persisted edges/successor traversal, and TaskGraphStore, occupancy, and Routines were in memory (363, 372). Proposed durable Task Graph state/outbox belongs in QMA daemon SQLite by named amendment; QMB’s JSONL ledger stays unmerged, and Graph Templates are plugin-contributed and rebuilt on load (367).

Product sessions are another distinct boundary. Authoring and app-use sessions carry host/wire authority and are not QMA’s execution `Session`; sessions own context and grants, not tabs. App-use can neither edit implementation nor grant itself authority. A proposed change request stages a change for a separate authoring session to review/apply (364, 703–705, 1218–1219). The eventual handoff also corrects that specialists remain available and that “PM” on the trading floor means Portfolio Manager (1219–1221); a display/role-label change must not silently perform an identity migration (368).

For shared operations, the candidate calls for a transport-independent typed interface with effect class and output shape (`value`, artifact reference, job handle, or stream). Durable files use content identity, not machine-local paths. JSON Render and MCP Apps are presentation adapters for DTOs; they confer no authority. JSON Render is a catalog/UI renderer whose host implements actions; MCP Apps provide sandboxed tool HTML while the host grants tools, and native panes remain native (366, 573–576). Native panes are not to be replaced wholesale with embedded mini-app content. The snapshot’s final prompt favors Svelte+TS? No: that is a current user preference outside this historical evidence. This export itself does not establish a final web-host framework decision; avoid reading “JSON Render” or MCP Apps as a frontend-stack choice.

## Mini-apps, libraries, workflows, ML, and copilot

The architectural vocabulary is contribution/package-oriented: discoverable contributions can expose descriptors/capabilities; workflows compose those capabilities; the Board helps arrange authored work; graph templates define reusable procedures; a Mission/task graph is a particular run. Discovery results remain distinct from durable artifacts and hypotheses. A later review addition records the Library-chrome question as OD-03, recommending ContributionHit display but not treating it as a blocker (1016, 1049). This is a proposal, not evidence that Library search already includes packs/tools.

Data and ML work need not be a bot, trading-wrapped, or forced into the Book path; this correction is repeated in the operator’s Stage B corrections and the final handoff (628–633, 701–708, 1213–1217). Yet a reusable research hypothesis or sensing capability should not be represented as a complete alternative trading system. A true alternative policy composition must own accounting and risk/sizing and support its intended lifecycle across the trading chain. Candidate reconciliation first held venue admission as an unresolved OD-01; the operator’s later explanation says the architecture question was misframed and that the stack must be adaptable end to end, with sequential paper/live adoption (992, 1037–1049, 1180–1184). Therefore, reports should preserve both the early unresolved state and the later correction rather than repeat the abandoned “personal approval for any alternative” framing.

Copilot is proposed in two distinct product modes: authoring and app-use. It discovers host-granted contribution descriptors; app-use cannot change implementation or apply its own change requests. The authoring mode is the governed place for implementation changes. This is an authority boundary, not a claim of an existing copilot subsystem; product sessions are explicitly absent at the inspected pin (364, 703–705, 1230). QMA `Session` is also explicitly not the product session (271, 364).

Donor references were selectively adopted, with clear non-adoptions: borrow Hermes manifest/schema/handler separation and config/state distinction, but not missing-dependency warning-and-continue or in-process full trust; borrow n8n’s separation of descriptor/graph/run and draft/published, but do not embed n8n because of its license; use JSON Render only as catalog UI and MCP Apps as sandboxed presentation; mutmut is optional testing-strength evidence only, WSL/POSIX on Windows and never `apply` on a shared worktree; OpenBB providers do not equal widget/app declarations, and its runtime is not adopted (571–578). Mutmut is never a product dependency (366, 577, 708, 1224).

## Corrections, rejected ideas, and evidence limits

Rejected or corrected ideas include: a sixth QMX component/framework; treating the Experimentation Board as a registry; treating hypotheses or contribution hits as ordinary `fp1` artifacts; equating an ungoverned call/research/sensing graph with a Mission or alternative trading system; using dummy Book/BMS records; embedding n8n; giving app-use self-grant or code-application authority; and hot-swapping live positions (211–215, 362–368, 573–578, 1182, 1213–1228). Stage A’s initial conclusion that venue-touching alternatives should stay refused pending L36 is superseded as a framing question by the operator’s correction, while L36 is still described as the default authority chain and is to be amended so Book/BMS are default role implementations, not the only possible implementations (1037–1049, 1180–1184, 1226–1228). No final ratification or implementation follows from this export.

The pinned implementation evidence was `270e992` and docs `b8b4d21`; the older `8510c03` absence baseline was called stale (212, 531–539). At that pin, bounded QML tests passed, QMN conformance tests passed with one skip, and QMA tests could not run because its nested virtual environment was invalid; source inspection was not a test pass (361). Later statements explicitly say TaskGraph remains in-memory, ContributionHit/product sessions are proposals/absent, and QML→QMB→QMN is unsupported integration (1055, 1230). Thus capability composition, cross-library adoption, persistence, session grants, and copilot flows are architecture intent or proposed connections, not demonstrated running behavior. The report should not infer a completed end-to-end workflow from a candidate, linter pass, Gherkin scenarios, or selected package tests; the snapshot itself says BDD/Gherkin is specification, not proof that feature files execute (628–633, 707, 1223).
